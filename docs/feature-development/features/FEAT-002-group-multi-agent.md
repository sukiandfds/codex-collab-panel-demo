# FEAT-002：项目群聊与多 Agent 协作

当前产品定义更新时间：2026-08-17 12:48 +08:00

## 当前产品定义：员工参与项目群聊

本节是本功能当前有效定义。历史方案和开发记录不得覆盖本节；总产品定义见根目录 `PRODUCT_DEFINITION.md`。

### 归属关系

- 工作项目拥有项目文件、项目群聊和完整公共群聊记录。
- 员工自己的项目始终拥有员工直属单聊，以及该员工参与各项目群聊的长期会话。
- 一个员工在一个项目群聊中对应一个普通、持久、可继续的会话，即 `一个员工 × 一个项目群聊 = 一个长期会话`。
- 员工参与多个项目时，每个项目群聊会话相互独立，但全部归属于员工自己的项目。
- 员工可以访问和操作目标工作项目路径内的文件；访问、修改或删除目标文件不改变会话归属。
- 工作项目可以保存员工公开发布到群聊的消息，但不能把员工的长期会话或 Runtime Thread 列为该工作项目的普通会话。

### 第一次和后续调用

- 员工第一次被某个项目群聊调用时，在员工自己的项目下创建该群聊对应的长期会话。
- 初始体验与普通 Codex 新会话一致，默认几乎没有聊天上下文；可以读取目标项目根目录的说明文件，但不自动加入此前全部群聊历史。
- 工作项目保存完整群聊记录。用户要求查看最近或历史内容时，员工可以通过目标项目读取该记录。
- 同一群聊后续再次调用同一员工时，继续原会话，并把该员工上一次回复之后到本次调用之间新增的群聊内容按原顺序补入上下文。

### 回复和状态

- 用户在工作项目群聊中指定员工工作，实际结果由员工自己的项目下面对应群聊的长期会话生成。
- 最终回复只生成一次：员工会话中的最终回复原样发布到工作项目群聊，不重新总结、不二次生成。
- 中止或失败必须显示清晰状态，不得伪装成完成。
- 将任务理解、阶段性文本、停止前有效文本和停止位置发布到群聊属于后续能力；命令等底层过程是否公开以后单独定义。

### 当前保留与未来能力

- 项目群聊归档、删除或员工退出时，当前不自动删除、迁移或重新归属员工自己的对应会话。
- 每日群聊压缩、长期摘要、员工每日复盘、通用经验、项目经验和雷点沉淀均为未来能力，当前不视为已实现。

### 2026-08-17 12:48 +08:00 | Codex Desktop 员工会话混入问题暂缓

- 现象：Desktop 只打开 negus 主仓库时，仍会把 `employees/*` 下由 negus 创建的员工 Thread 显示为 negus 普通项目会话。
- 已验证根因：现有员工 Thread 虽然 `cwd` 位于员工目录，但会话来源仍记录为 `vscode`；Desktop/App Server 的普通列表默认读取 `cli` 和 `vscode` 来源，项目没有可用的子目录会话忽略配置。
- 已排除方案：`.gitignore` 无效；只设置 `clientInfo`、`serviceName` 或 `threadSource: "system"` 不能改变会话来源分类；本轮也不移动员工目录或拆分 `CODEX_HOME`。
- 暂不采用：把员工会话设置为 `sessionStartSource: "appServer"` 可能同时阻断用户以后在 Desktop 单独打开员工项目并继续原会话的路径。
- 当前决定：不改代码、不迁移现有 Thread，暂时接受该显示问题只影响 negus 项目；员工 Thread 的 `cwd` 不得改成实际工作项目路径。
- 后续优先方向：评估父 Git 仓库下的“系统模块目录 + 员工模块目录”，Desktop 日常只保存系统模块目录，GitHub 仍由父目录统一管理。实施前必须先验证同一 Git 仓库子目录的会话隔离和兄弟目录访问行为。
- 完整问题证据、官方调研结论和用户原话见根目录 `PRODUCT_DEFINITION.md` 的“Codex Desktop 混入员工会话：现象、调研与暂缓决定”。

## 当前快照

- 项目群有真实成员、持久化群消息和四个真实 Codex Agent：项目经理、研究、开发、审查。
- 用户当前发送普通群聊消息，并可选择或 `@` 一个或多个 Agent。“商讨”仅保留未来入口：指定员工进行有限轮次的相互讨论，最后由项目经理 Agent 发布一个收敛结果；当前尚未实现。
- Agent 收到必要群聊上下文后回复；用户明确指定多个 Agent 时按顺序各执行一次。旧的自动邀请和自动追加讨论已删除，未来“商讨”使用独立流程。
- 员工的最终公开回复可以通过明确 `@员工名` 顺序唤醒其他员工。当前临时限制为同一轮每名员工最多执行一次，以避免互相 `@` 形成循环；后续根据实际协作需要调整。
- `@` 识别以员工注册表中的当前名称和历史别名为准；菜单只插入当前名称，前端选中态、发送目标和服务端路由使用相同的完整名称边界规则。
- 页面显示 Agent 当前阶段、增量回复、在线成员和附件。
- 当前不是无限自主 Agent 社会，也没有正式账号、权限、持久化任务队列和冲突仲裁。
- 当前 v0.4.1 是可运行原型，不代表目标协作底座已经完成；正式 Task、AgentRun、ActivityEvent 和审批账本仍待开发。
- 初版重点是一台电脑上的多个模型和多个 Agent 协作，不先做多电脑自动调度，也不把 Orca 作为底座依赖。
- M1 已加入客户端消息 ID、服务端消息顺序、请求重试幂等和前端临时/正式消息对账；代码与构建检查通过，服务端尚未重启加载和真实设备验收。
- v0.4.2 已将群聊侧栏、顶部、输入区、加载反馈和移动端布局调整为单人页的界面语言，同时保留成员、Agent、`@`、商讨预留入口和成果审核；本轮没有修改单人页文件。
- 消息整体样式、富文本、消息操作、历史消息、流式回复、指令等候队列、模型与上下文明确暂缓，继续作为本功能的待开发项目。
- 对话与群聊已改为同一应用内切换，共用稳定页面外壳、手机视口和基础导航；两边业务状态、数据缓存和执行逻辑继续隔离。
- Agent 单聊和独立员工项目页都可以看到该员工的成长事实与建议；建议审批中的后台读取不会把新状态覆盖回旧状态，审批写入失败会保留为可重试状态。

## 用户可见结果

用户从一个群聊入口发送消息。未点名时，项目经理判断自己直接回答、创建 Worker 任务或请求补充信息；明确 `@` 时由目标 Agent 直接响应。被安排的 Agent 在群里汇报进度、结论、交付物、风险和待确认事项。当前原型已经能展示部分 Agent 回复，但正式任务账本、可恢复队列、统一汇报和审批状态尚未完成。

## 目标与边界

目标：在单人 Codex Web 的消息、实时事件、附件、断线恢复、停止/追加和失败反馈标准之上，建立可靠的单机多 Agent 项目协作中心。群聊不是另一套质量更低的对话系统。

当前不解决：

- 无限自动讨论或无限 Token 使用；
- 多项目、多租户、企业权限与正式成员账号；
- 多电脑之间自动抢任务、远程自动执行和设备调度；
- Orca 的整体迁移、Fork 或产品层接入；
- 把群聊状态强行合并进单人 Turn 状态；
- 保证群聊完整上下文出现在 Codex Desktop 当前页面。

## 架构与数据链路

```text
GroupApp / useGroupRoom
  -> /api/group/*
  -> group-room-store (房间、成员、消息)
  -> multi-agent-service (目标 Agent、上下文、有限轮次)
  -> Codex app-server threads
  -> realtime-hub /events
  -> Agent 状态、增量文本、群消息
```

单人页的 `threadId/turnId` 状态和群聊的房间/Agent 队列属于不同功能域。目前只共享稳定的附件、实时连接和导航 UI。

## 开发计划与关键决策

- 先完成一个真实项目群，不扩展多个群和组织管理。
- 默认由项目经理 Agent 接收未点名消息；明确 `@` 时按目标 Agent 调度。
- 先建立消息幂等、房间事件顺序和可恢复任务账本，再增加项目经理分派和更多模型。
- 每个路由决定、Task、AgentRun、进度事件和最终结果都要能追溯到原始群消息。
- 上下文只包含完成当前讨论所需的群消息和角色责任，限制轮次避免 Token 无边界增长。
- Worker 只接收任务摘要、关联文件、已有决策、验收标准和必要证据；完整过程单独记录。
- Agent 完成后在群内汇报，项目经理按需汇总；没有新增价值时不重复回答。
- 停止、失败、重试、等待用户、待审批和部分完成必须具有明确状态。
- 真实任务与测试分开，自动验证不向群历史发送污染消息。
- 单人和群聊可以有不同运行对象，但应共用已经验证的消息呈现、过程事件、附件、断线恢复和错误反馈标准。
- 项目经理分工、多 Agent 讨论、审查和任务队列属于群聊特有能力，按 M1-M9 阶段逐项实现；不能用这些特性替代基础能力对齐。
- 长期采用模型无关的 Agent/Provider 边界：职位、模型供应商、模型和工具能力分别配置，不把“项目经理/研究/创意/开发”等角色写死为 Codex。
- 不默认把每条消息广播给所有模型；由项目经理或明确 `@` 路由到必要角色，共享提炼后的任务上下文，控制 Token、费用和重复输出。
- 外部模型接入前必须验证 API 能力与网页版体验是否一致；不能因为豆包网页版检索强或 Grok 更大胆，就直接假定其公开 API 具备相同检索、引用和上下文能力。
- 采用分层 Agent：项目经理使用高能力模型负责澄清、拆解、冲突处理和结果审核；边界明确的执行任务交给更快、更低成本的专业 Worker；审查 Agent 只在风险或质量要求需要时调用。
- Worker 只接收任务摘要、关联文件、已有决策、验收标准和必要证据，不复制完整群聊；返回结果摘要、产物位置、风险和待决问题，完整过程单独留档。
- “使用子 Agent”不自动等于节省 Token；只有精准路由、限制轮次、限制上下文并使用合适成本模型时才可能降低总成本。

### 2026-08-06 | 初版单机多 Agent 路由规则

- 当前主场景是一台电脑上的多个模型和多个 Agent，不根据真人在线人数改变路由规则。
- 用户未明确指定时，默认由项目经理 Agent 接收并判断：直接回答、创建 Worker 任务或请求补充信息。
- 用户明确 `@` 某个 Agent 时，由目标 Agent 直接响应；项目经理只在需要汇总、冲突处理或用户要求时介入。
- 项目经理分发任务后，各执行 Agent 需要在群内提供进度，不能只在后台执行后一次性返回结果。
- 用户可以针对某条 Agent 对话继续追问，后续消息应保留与原对话的关联。
- 多电脑协作和 Orca 接入暂不进入初版，只保留未来 Runtime Adapter 扩展边界。
- 以上是已确认的产品方向，不代表当前代码已经实现；消息账本、任务恢复和统一汇报仍待开发。
