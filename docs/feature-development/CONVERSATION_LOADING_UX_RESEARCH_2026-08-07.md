# 对话内容加载、状态更新与定位稳定性调研报告

## 1. 调研目的

本次调研不是普通代码审查，重点是回答用户实际操作时看到了什么：

- 内容多久出现；
- 内容是否先显示旧版本、随后整体替换；
- 翻看旧消息时阅读位置是否漂移；
- 状态更新、流式内容和窗口变化是否造成几帧闪屏；
- 多个单人对话来回切换时是否保留内容和位置；
- 单人对话与项目群聊切换时是否重新加载整页；
- 消息返回顺序、重复消息和乐观消息确认是否稳定。

最终目标是建立一套产品体验规则，再按问题集中涉及的文件分组，后续一组一组确认和修改。

## 2. 先给结论

### 2.1 远程提交的总体判断

远程最新提交的方向部分正确，但不能直接视为内容加载问题已经解决。

远程提交明确改善了三件事：

1. 单人对话和群聊可以在同一个 App 中切换，普通对话不再因为进入群聊而销毁；
2. 群聊增加本地快照和乐观消息，首次进入和发送反馈更快；
3. 群聊实时消息增加按序号、时间和 ID 的排序与去重。

远程提交没有解决三件核心问题：

1. 普通对话向上加载旧消息时仍然发生大幅定位漂移；
2. 普通对话中仍有多套自动滚动、锚点补偿、页面激活恢复逻辑竞争写入位置；
3. 首屏就绪条件仍然没有形成清晰的状态机，远程还删除了启动页最长等待兜底。

### 2.2 产品结论

推荐的产品行为不是“等待所有历史加载完再打开”，也不是“本地缓存一出来就立即把正文交给用户，然后后台整段替换”。应当区分两种入口：

1. 刷新网页或重新打开应用属于前端重启。Logo/Slogan 可以作为当前页加载占位，正常情况下等待服务器返回当前对话最近一页并完成稳定渲染后消失；
2. 普通页内切换不重新等待服务器，优先显示目标对话自己的缓存内容和阅读位置，再在后台同步；
3. 服务器请求超时或失败时不能无限停留在 Logo/Slogan。有可靠缓存就显示缓存并后台重试，没有缓存就显示现有错误和重试入口；
4. 更早历史在用户向上翻看时按需加载，实时同步和后台校验不能整页替换内容或改变用户正在阅读的位置。

用户已经离开底部后，新消息、流式文本、状态更新、图片或布局变化不能主动滚动页面或明显改变用户的阅读锚点。助手最终答案增长造成的轻微画面推动记录为后续优化，不阻塞本轮；只有用户仍在底部或使用现有“下滑到最下方/回到最新位置”入口时，才恢复自动贴底。

- 重点采样 `scrollTop`、`scrollHeight`、可见消息文本和页面 URL；
- 同时检查相关提交差异和实际渲染逻辑。

### 4.2 构建验证

- 本地 TypeScript 检查通过；
- 本地直接调用 Vite 构建通过；
- 远程工作树直接调用 Vite 构建通过；
- 项目封装的 `build-web-ui.ps1` 曾被 pnpm 的 `esbuild` 安装脚本策略拦截，但这不是源码编译错误，直接使用已有依赖构建成功。

### 4.3 验证边界

本次没有进行以下测试：

- 人工网络限速下的完整首屏时间曲线；
- 逐帧视频或像素级闪屏录制；
- 大规模群聊历史消息向上分页的实际操作；
- 真实群聊多 Agent 同时流式回复的长时间运行。

因此，报告中“定位漂移”是运行时直接测得的事实；“几帧闪屏”在部分位置属于由多个滚动写入推导出的高风险，需要后续用逐帧录制确认具体表现。

### 4.4 环境干扰

运行期间 `/api/session/context` 出现过 503，远程服务的 app-server 也出现过同一 Codex thread 的 active writer 冲突，普通会话内容随后通过 JSONL fallback 继续读取。

这会影响上下文状态接口的稳定性，但本地版和远程版使用相同数据源和相同异常条件；普通会话旧消息定位漂移在两版中均可复现，因此该相对结论仍然有效。上下文状态 503 不作为本报告中的 UI 速度结论。

## 6. 运行时关键证据

### 6.1 普通会话向上加载的定位漂移

测试会话为“快速了解项目结构”，两版使用相同真实数据。

本地版采样：

| 时间阶段 | `scrollTop` | `scrollHeight` | 可见消息 |
| --- | ---: | ---: | --- |
| 设置到顶部下方 | 80 | 31777 | 08-05 14:21 |
| 0–160ms | 80 | 31777 | 08-05 14:21 |
| 约 300ms 后 | 3333 | 34848 | 08-05 11:20 |
| 约 1 秒后 | 3333 | 34848 | 08-05 11:20 |

远程版采样：

| 时间阶段 | `scrollTop` | `scrollHeight` | 可见消息 |
| --- | ---: | ---: | --- |
| 设置到顶部下方 | 80 | 17685 | 08-06 16:41 |
| 0–600ms | 80 | 17685 | 08-06 16:41 |
| 约 1 秒后 | 2574 | 18926 | 08-05 18:49 |

这说明问题不是单纯“旧消息加载慢”，而是旧消息插入后虚拟列表重新测量和滚动补偿没有保持同一个阅读锚点。

### 6.2 普通对话的滚动写入来源

当前普通对话视图至少有以下滚动动作：

1. 首次加载完成后滚到底部；
2. 新的流式文本出现时滚到底部；
3. 执行状态活动变化时滚到底部；
4. 最后一条消息变化时滚到底部；
5. 窗口高度变化时重新贴底；
6. 加载旧消息后执行锚点补偿；
7. 远程提交新增页面重新激活后的滚动位置恢复。

这些动作分别由不同的 effect、`requestAnimationFrame`、`useLayoutEffect` 和 `ResizeObserver` 驱动，缺少一个统一的“本次内容变化原因”和“唯一滚动决策”。

### 6.3 单聊和群聊切换

本地版：

- `group-main.tsx` 独立创建 React root；
- 通过不同 HTML 入口切换；
- 普通对话组件卸载，返回时重新初始化。

远程版：

- `group-main.tsx` 复用 `main.tsx`；
- `App.tsx` 同时维护普通对话和群聊 surface；
- 通过 `visibility`、`pointerEvents` 和 `zIndex` 切换；
- 普通对话仍在内存中，切换速度和状态保留更好。

远程方向应保留，但“surface 保留”不能代替“每个对话独立保存阅读位置”。

### 6.4 群聊消息顺序

本地群聊实时创建消息主要按事件到达顺序追加。

远程新增 `groupMessageState.ts` 后：

- 优先使用服务端 `sequence`；
- 没有序号时使用创建时间；
- 最后使用消息 ID 稳定排序；
- 同 ID 或同 `clientMessageId` 的消息原地替换；
- 乐观消息确认后不会重复追加。

这是远程提交中可以直接保留的处理方向。

## 7. 产品体验目标

### 7.1 首次打开

- 立即显示固定尺寸的应用外壳；
- Logo/Slogan 只作为当前页加载期间的占位，不设置为了动画效果而强制停留的最短时间；
- 刷新网页或重新打开应用时，正常情况下等待服务器返回当前对话最近一页并完成一次稳定渲染；
- 服务器请求超时或失败时，有可靠缓存就显示缓存并后台重试，没有缓存就显示现有错误和重试入口，不能无限停留在 Logo/Slogan；
- 普通页内切换优先显示目标对话自己的缓存内容和阅读位置，再后台同步；
- 缓存和服务器新版本应在原位置合并，不能表现为两次整页正文切换；
- 不等待全部历史消息；
- 当前对话首屏稳定后立即移除 Logo/Slogan，不要求用户继续观看；
- 当前对话首屏稳定是指当前可见区域已经有可读内容且位置稳定，不要求服务器返回全部历史内容。

已确认的产品决策：Logo/Slogan 只是辅助当前页加载的占位。刷新网页或重新打开应用时等待服务器首屏稳定；普通页内切换先显示缓存。Logo/Slogan 没有强制最短展示时间，异常超时只用于兜底，不能让用户无限等待。

### 7.2 用户阅读旧内容

- 用户向上滚动后，自动滚底立即失效；
- 旧消息只向顶部增加；
- 以第一条可见消息 ID 和顶部像素偏移作为锚点；
- 加载完成后锚点消息和用户视口保持一致；
- 只允许一个滚动事务修改 `scrollTop`；
- 加载图标不能占用会导致内容整体下移的正文位置。

### 7.3 新消息和流式内容

- 用户在底部时，流式内容可以自动贴底；
- 用户离开底部后不自动滚到底部，保留现有的“下滑到最下方/回到最新位置”入口，不新增提醒控件；
- Markdown、图片、附件或执行状态高度变化造成的无操作位置漂移仍属于本轮需要控制的滚动风险；
- 助手工作过程的展开/折叠，以及最终答案增长造成的轻微画面推动，记录为后续开发项，不作为本轮验收阻塞项；
- 用户使用现有入口回到最新位置后，才恢复自动贴底。

### 7.4 对话和 surface 切换

- 每个单人对话独立保存内容缓存和阅读锚点；
- 单聊和群聊各自保持消息、加载和滚动状态，不能在用户界面上互相串扰；实时连接是否共用由实现复杂度决定，不作为产品验收条件；
- 切换 surface 不重新加载整页；
- 切换回已加载内容时立即恢复原位置，后台同步不重新滚到底部；
- 请求返回顺序不能让旧对话覆盖当前对话。

## 8. 问题分组和后续处理顺序

每组只保留 1–3 个核心问题。组内问题共享主要文件和验收方式，后续逐组确认，不把多个体验问题混在一个大改动里。

### 第 1 组：首屏就绪、缓存和启动页

优先级：P0

集中文件：

- `web-ui/src/main.tsx`
- `web-ui/src/App.tsx`
- `web-ui/src/features/conversations/hooks/useProjectConversations.ts`
- `web-ui/src/features/conversations/hooks/useConversationSession.ts`
- `web-ui/src/features/conversations/data/conversationSnapshot.ts`

问题：

1. `snapshotLoading`、`loadingList`、`loadingSession` 没有被定义成清晰的首屏状态机；
2. 前端重启和普通页内切换没有明确区分：重启应等待服务器首屏稳定，页内切换应优先显示缓存；
3. 远程版删除启动页最长等待兜底，异常时可能一直等待。

验收重点：刷新网页或重新打开应用时，服务器当前页首屏稳定后 Logo/Slogan 立即消失；普通页内切换先显示目标缓存；缓存与服务器内容原地合并，不能整页跳变；异常时不能无限停留在 Logo/Slogan。

### 第 2 组：旧消息加载和阅读定位

优先级：P0

集中文件：

- `web-ui/src/features/conversations/components/ConversationView.tsx`
- `web-ui/src/features/conversations/components/ConversationView.module.css`
- `web-ui/src/features/conversations/state/conversationMerge.ts`

问题：

1. 向上补充旧消息后，虚拟列表重新测量导致用户视口大幅漂移；
2. 手动锚点补偿没有和虚拟列表布局变化形成单一事务。

验收重点：在顶部下方 80px、300px、接近顶部三个位置加载旧内容，第一条可见消息和其相对顶部距离都不能改变。

### 第 3 组：状态更新、流式内容和闪屏

优先级：P0

集中文件：

- `web-ui/src/features/conversations/components/ConversationView.tsx`
- `web-ui/src/features/conversations/realtime/useConversationEvents.ts`
- `web-ui/src/features/execution/hooks/useCodexExecution.ts`
- `web-ui/src/features/group-chat/components/MessageTimeline.tsx`

问题：

1. 同一内容变化可能同时触发自动滚底、流式滚动、执行状态滚动和尺寸修正；
2. 远程版新增激活恢复后，恢复位置和滚到底部存在竞争写入；
3. 内容高度变化和消息数量变化没有统一的滚动事务。

验收重点：连续记录 16ms 帧间的 `scrollTop`，用户离开底部后不得出现无操作位置变化。

当前决策：本组暂不修改助手工作过程的展开/折叠行为。助手最终答案在用户向上阅读时，后续开发目标是只增加底部内容并尽量保持当前画面不动；当前允许轻微位置推动，不作为本轮修改范围。

本轮边界：多套滚动写入竞争、用户无操作时的位置变化和几帧闪屏风险仍需处理；仅助手工作过程的展开/折叠，以及最终答案增长造成的轻微推动延后开发。

### 第 4 组：多个单人对话切换和请求竞态

优先级：P1

集中文件：

- `web-ui/src/features/conversations/hooks/useConversationSession.ts`
- `web-ui/src/features/conversations/hooks/useConversationCatalog.ts`
- `web-ui/src/features/conversations/state/conversationMerge.ts`
- `web-ui/src/features/conversations/realtime/useConversationEvents.ts`

问题：

1. 会话缓存可以复用内容，但没有保存每个会话独立阅读位置；
2. 快速切换时虽然会中止请求，但全局 loading/sync 状态仍可能被旧请求的结束逻辑影响；
3. 已加载会话切换后容易统一回到底部，而不是回到用户上次阅读位置。

验收重点：A 会话上滑后切到 B，再切回 A，内容、可见消息和阅读位置都保持；连续快速点击多个会话不能串内容。

已确认的产品规则：每个单人对话独立保存自己的阅读位置。重启网页或应用后是否恢复位置暂不作为本轮要求，重置位置也可以接受。

### 第 5 组：单聊与群聊 surface 切换

优先级：P1

集中文件：

- `web-ui/src/App.tsx`
- `web-ui/src/group-main.tsx`
- `web-ui/src/features/group-chat/GroupApp.tsx`
- `web-ui/src/components/ViewSwitcher/ViewSwitcher.tsx`

问题：

1. 本地版多 HTML 入口会销毁普通对话页面，远程版改为同页保留但滚动恢复仍不完整；
2. 两个 surface 各自的实时更新、加载状态和滚动状态需要完全隔离；
3. 返回 surface 时不能出现先滚到底部再恢复旧位置的中间帧。

验收重点：单聊上滑、进入群聊、等待群聊更新、返回单聊，原来的消息和阅读位置保持不变。

已确认的产品规则：群聊切换与单人对话切换使用同一套体验。进入目标 surface 后先显示目标自己的缓存内容和阅读位置，再后台更新；切换过程不应像重新启动页面。

### 第 6 组：消息缓存、排序去重和实时时间线

优先级：P1

集中文件：

- `web-ui/src/features/conversations/state/conversationMerge.ts`
- `web-ui/src/features/conversations/state/optimisticMessage.ts`
- `web-ui/src/features/conversations/realtime/useConversationEvents.ts`
- `web-ui/src/features/group-chat/hooks/useGroupRoom.ts`
- `web-ui/src/features/group-chat/data/groupSnapshot.ts`
- `web-ui/src/features/group-chat/data/groupMessageState.ts`
- `web-ui/src/features/group-chat/realtime/useGroupEvents.ts`
- `web-ui/src/features/group-chat/components/MessageTimeline.tsx`

问题：

1. 单聊和群聊都需要明确缓存、乐观消息和服务端消息的版本边界，旧缓存不能覆盖更新内容；
2. 单聊和群聊都应保证一条消息只显示一次，并使用一致的稳定排序和确认替换规则；
3. 用户阅读旧消息时，实时消息或内容高度变化不能改变当前阅读位置。

验收重点：分别在单聊和群聊中验证乱序事件、重复确认、乐观消息和用户上滑阅读；消息顺序、去重结果和阅读位置都保持稳定。

已确认的产品规则：排序、去重、缓存消息和服务端消息合并是单聊与群聊共同遵守的体验标准。实现可以通过共同架构能力复用，也可以由各自模块分别实现；以行为一致和维护成本更低为准，不强制挤进同一个文件。用户上滑阅读时不新增“有新消息”提示，保留现有的“下滑到最下方/回到最新位置”入口。

后续验证：慢网首屏逐帧录制、多人或多 Agent 同时实时更新、长时间流式输出暂不阻塞当前修改，后续单独测试并补充证据。

## 9. 推荐的逐组处理方式

后续每组按同一顺序推进：

1. 先确认这一组的用户目标和不可接受体验；
2. 再确认现有代码路径和最小修改边界；
3. 明确 1–3 个问题分别如何验证；
4. 修改后只验证这一组，不把其他组的问题混入；
5. 验证通过后再进入下一组。

推荐处理顺序为：

1. 第 1 组：首屏就绪、缓存和启动页；
2. 第 2 组：旧消息加载和阅读定位；
3. 第 3 组：状态更新、流式内容和闪屏；
4. 第 4 组：多个单人对话切换和请求竞态；
5. 第 5 组：单聊与群聊 surface 切换；
6. 第 6 组：消息缓存、排序去重和实时时间线。
