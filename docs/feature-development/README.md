# 功能开发记录规范

这套文档是本项目长期维护的功能开发记忆，主要供 AI 助手阅读。它不替代 Git 历史、源码和原始日期日志，而是把分散信息整理成“一个功能从计划到多个版本”的连续记录。

## AI 阅读顺序

开始开发前只按以下顺序读取，避免一次加载全部历史：

1. 阅读 [`FEATURE_INDEX.md`](./FEATURE_INDEX.md)，确认功能编号、当前状态和对应文件。
2. 阅读本次相关的一个或多个 `features/FEAT-*.md`。
3. 阅读 [`PROCESS_ISSUES.md`](./PROCESS_ISSUES.md) 中状态为 `active` 的普适问题。
4. 只有需要证据、复盘或定位旧实现时，才沿功能文件中的链接读取原始日期日志和 Git 提交。

## 文档分层

| 层级 | 作用 | 更新方式 |
| --- | --- | --- |
| `FEATURE_INDEX.md` | 展示所有功能当前状态、最新版本和入口 | 功能新增、状态或版本变化时更新 |
| `features/FEAT-*.md` | 记录一个功能的目标、架构、计划、问题和版本历史 | 每次相关开发结束时更新 |
| `PROCESS_ISSUES.md` | 记录能跨功能复用的开发方法、误判和防再犯规则 | 发现普适问题后立即更新 |
| 根目录日期日志 | 保存当日原始过程与详细证据 | 保留旧文件，不再作为主要入口 |
| Git | 保存可核对的代码变化 | 功能记录引用提交，不复制完整 diff |

## 功能文件固定结构

每个功能文件必须按以下顺序组织：

1. YAML 元数据：功能编号、状态、版本、更新时间、所有权和关键路径。
2. 当前快照：现在能做什么、不能做什么、用户会看到什么。
3. 目标与边界：本功能要解决什么，本轮明确不解决什么。
4. 架构与数据链路：只写已核对的真实结构；推断必须标记为“待验证”。
5. 开发计划与决策：记录打算怎么做，以及为什么选择这条路径。
6. 问题记录：每项问题必须分类为 `特例` 或 `普适`。
7. 版本时间线：按时间正序追加，不覆盖旧版本。
8. 下一步：只记录尚未完成且仍有效的工作。

## 问题分类

### 特例

只影响特定功能、算法、输入类型、第三方版本或局部实现的问题。例如：某种 Markdown 图片路径无法渲染、某个算法对特定数据效果差、某个 Agent 提及规则漏掉中文输入法组合态。

### 普适

会影响多个功能或以后开发方式的问题。例如：没有先理解架构就修改、数据和 UI 混改、验证工具选择错误、服务端改动后没有重启、一次补丁范围过大。

分类判断标准：如果经验可以写成“以后开发其他功能也必须遵守”，归为 `普适`；否则归为 `特例`。普适问题除写入功能文件外，还必须登记到 `PROCESS_ISSUES.md`。

## 问题记录字段

| 字段 | 要求 |
| --- | --- |
| `issue_id` | 功能特例使用 `FEAT-xxx-Ixx`；普适问题使用 `PROC-xxx` |
| `发现时间` | 使用 `YYYY-MM-DD HH:mm +08:00` |
| `分类` | 只能是 `特例` 或 `普适` |
| `状态` | `active`、`mitigated`、`resolved`、`deferred` |
| `现象` | 用户或开发者实际看到什么 |
| `根因` | 已验证事实；不确定时写“待验证”，不能伪装成结论 |
| `错误路径` | 哪个判断或方法造成了时间浪费 |
| `正确路径` | 下次最短的处理方式 |
| `防再犯触发器` | 遇到什么信号时应立即执行什么检查 |
| `证据` | 源码、原始日志、命令结果或提交 |

## 版本记录字段

每次相关开发结束后，在功能文件底部追加一条版本记录：

```markdown
### 2026-07-25 23:58 +08:00 | v0.1.0 | implemented_pending_review

- 计划：本轮原计划怎样开发。
- 实际：最终改了什么。
- 偏差：计划和实际为什么不同。
- 问题：关联 `FEAT-xxx-Ixx` / `PROC-xxx`；没有则写“无”。
- 验证：实际运行的基本检查和结果。
- 用户可见变化：用户会看到或操作到什么。
- Git：提交哈希；未提交时明确写 `uncommitted`。
```

版本号只表示单个功能的演进，不等同于整个产品版本。功能行为发生变化时增加次版本；仅修复问题时增加补丁版本。

## 强制更新时机

以下任一情况发生时，当前 AI 助手必须在结束工作前更新对应功能文件：

- 完成一次功能开发或修复；
- 实现方式与原计划不同；
- 发现新问题、误判或性能阻塞；
- 问题从 `active` 变为 `resolved` 或 `deferred`；
- 用户验收改变了功能结论；
- 产生新的提交、回滚或替代实现。

只更新日期日志、不更新功能记录，视为记录未完成。不得改写旧版本使历史看起来从未发生；更正旧结论时应追加新记录并说明被替代内容。
