# 项目进度页与项目管理工具调研

## 1. 调研目的

当前项目已经有一个项目进度页初版。初版主要读取功能开发索引，展示功能名称、版本、状态、更新时间和简短结论。本轮调研要回答三个问题：

1. 主流项目管理工具实际记录哪些信息；
2. 哪些信息是项目进度页的最低必要内容；
3. 哪些信息是 AI Agent 项目特有的，不应直接照搬普通项目管理工具。

本报告只用于确定数据和产品范围，不代表本轮已经修改页面或代码。

## 2. 调研范围与证据边界

本轮优先读取官方产品说明和官方帮助文档，关注真实的数据对象、进度字段和更新机制，不以营销页面的视觉布局作为功能证据。

### 2.1 已读取的官方来源

| 工具 | 来源 | 可确认的内容 |
| --- | --- | --- |
| Jira | [Getting started with Jira](https://www.atlassian.com/software/jira/guides/getting-started/overview) | 项目、工作项、Scrum/Kanban、Timeline、依赖、工作流、报告和仪表盘 |
| Linear | [Projects](https://linear.app/docs/projects) | 项目负责人、项目图标、开始日期、目标日期、里程碑、Issues、文档、进度图 |
| Linear | [Initiative and Project updates](https://linear.app/docs/project-updates) | 健康状态、按时间排序的更新、目标日期/成员/里程碑变化、进度报告 |
| Asana | [Project management](https://asana.com/features/project-management) | 负责人、截止时间、List/Board/Calendar/Timeline/Gantt、里程碑、依赖、自定义字段、状态更新、目标、Portfolio、报告和资源管理 |
| OpenProject | [Manage projects](https://www.openproject.org/docs/user-guide/projects/) | 父子项目、项目描述、项目标识符、公开/内部可见性、任务/问题、时间和成本报告、预算、Gantt、看板 |

### 2.2 访问限制

- ClickUp 帮助中心本轮返回 `403`，没有把其页面内容作为事实依据。
- Notion 帮助页和 Asana 部分帮助页存在连接或动态加载限制；Asana 功能页和其他工具的官方页面已足以支持共性字段结论。
- 本报告总结的是多个工具的共同产品模式，不声称存在一份所有工具共同遵守的正式字段标准。

## 3. 工具定位对比

### 3.1 Jira：工作项和流程驱动

Jira 的核心不是一张静态项目表，而是围绕项目中的 Work Item/Issue 建立工作流。常见结构是：

```text
项目 -> Epic/大型工作 -> Story/Task/Bug -> 子任务
```

它强调：

- 可配置状态和工作流；
- 负责人、优先级、标签、组件和版本；
- Scrum/Kanban 看板；
- Timeline 和依赖关系；
- 报告、仪表盘和历史数据；
- Issue 与代码、发布、文档和其他工具的关联。

Jira 适合复杂团队和跨部门流程，但字段和状态很多。我们的项目不能一开始复制完整 Jira，否则会把当前 Demo 变成重型工作管理系统。

### 3.2 Linear：项目、里程碑和更新驱动

Linear 的项目对象相对集中，项目可以关联多个团队的 Issues 和可选文档。官方文档明确提到：

- 项目名是必填信息；
- 建议设置项目负责人和项目图标；
- 支持开始日期和目标日期，并允许按年、半年、季度、月份或具体日期表达不确定性；
- 项目包含 Issues、可选文档、里程碑和进度图；
- 项目有健康状态和更新记录；
- 更新按时间顺序排列，并记录目标日期、成员、里程碑等属性变化；
- 项目更新可以作为面向团队和管理者的进度报告。

Linear 对我们最有参考价值的不是界面，而是“项目状态 + 里程碑 + 时间线更新”三者的组合。用户不需要阅读每个 Issue，也能先看到项目现在是否健康、最近发生了什么、下一步是什么。

### 3.3 Asana：多视图和跨团队计划驱动

Asana 将同一组项目任务提供多种视图：

- List：适合逐项检查工作；
- Board：适合看工作流状态；
- Calendar：适合检查日期；
- Timeline/Gantt：适合计划里程碑和依赖；
- Portfolio：适合同时查看多个项目；
- Goals/Reporting：适合连接项目和组织目标。

Asana 的共性字段包括负责人、截止时间、里程碑、依赖、自定义字段和项目状态更新。更高级的计划还包括资源、预算和报告。

对我们而言，最值得借鉴的是：同一份数据可以服务不同使用场景，但首屏不应同时塞入全部视图。移动端应优先显示状态、当前任务、风险和下一步，时间线和详细依赖放到二级页面。

### 3.4 OpenProject：层级、项目治理和成本记录

OpenProject 是开源项目管理工具，项目对象支持：

- 父项目和子项目；
- 项目描述和稳定标识符；
- 公开或内部可见性；
- 任务/问题跟踪；
- Gantt、看板、时间记录、成本报告和预算。

它对我们的价值主要在于两个方面：

1. 项目不是孤立的任务列表，可以有清晰的父子层级；
2. 进度、成本、时间和项目范围是不同维度，不能用一个百分比代替所有信息。

当前项目只有单项目范围，不需要马上实现完整父子项目和预算，但数据结构应避免以后只能存一张功能表。

## 5. 项目更新、风险和决策

### 5.1 项目更新

Linear 的 Project Updates 对我们很有参考价值。每条更新应是一个有时间点的快照，而不是覆盖旧内容的当前状态。

建议固定使用以下结构：

```text
更新时间
状态：正常 / 注意 / 阻塞 / 已完成
已完成：本次真实完成的结果
正在进行：当前仍在处理的工作
下一步：下一项明确动作
风险与阻塞：影响目标的事项
需要确认：必须由用户或负责人决定的问题
证据：相关提交、文件、对话或运行记录
```

这样新人或其他 Agent 只读最近一条更新，就可以了解当前情况；需要复盘时再进入历史更新。

### 5.2 风险记录

风险不能只写在一段描述里，至少需要：

- 风险 ID；
- 风险描述；
- 影响程度；
- 发生概率；
- 风险负责人；
- 预防或缓解措施；
- 当前状态；
- 最后评估时间。

本项目尤其需要记录：服务半失效、实时事件丢失、Desktop/Web 并发、固定公网入口、Windows 弹窗、Agent 成本和上下文过大等风险。

### 5.3 决策记录

决策记录与普通评论不同。建议至少记录：

- 决策 ID；
- 要解决的问题；
- 可选方案；
- 最终选择；
- 决策人或授权来源；
- 决策时间；
- 影响的功能和文件；
- 后续复查条件。

例如：“暂不实现 Desktop 热刷新，只先提供 Web 单向同任务提示”就是一个应该保存的产品决策，而不是普通聊天消息。

## 6. AI Agent 项目必须增加的字段

普通项目管理工具主要记录人的工作项；我们的项目还需要记录 Agent 的真实执行状态。

### 6.1 Agent 运行记录

```text
runId
turnId
agentId
agentRole
provider
model
workItemId
status
startedAt
lastRealEventAt
lastHeartbeatAt
completedAt
currentSummary
waitingReason
errorCode
recoveryReason
sourceConversationId
artifactIds
```

### 6.2 建议的内部状态

```text
queued
running
waiting_input
waiting_approval
blocked
completed
failed
interrupted
```

项目页面不必把所有状态都显示成复杂标签。内部状态可以详细，用户看到的健康状态可以收敛为：

```text
正常 / 注意 / 阻塞 / 已完成
```

### 6.3 必须分开的时间字段

以下时间不能混成一个 `updatedAt`：

- `lastRealEventAt`：最后一次真实执行事件；
- `lastHeartbeatAt`：连接或服务心跳；
- `lastSnapshotAt`：最后一次权威状态查询；
- `completedAt`：真实完成或中断时间；
- `updatedAt`：页面数据被写入的时间。

当前项目曾经把 tracker 更新当成任务仍在运行的证据，这是错误的。项目进度页必须保留这些字段的区别，否则“页面有更新时间”仍然不能证明 Agent 在工作。

## 7. 我们当前初版与行业模式的差距

| 维度 | 当前初版 | 行业常见做法 | 需要改进的方向 |
| --- | --- | --- | --- |
| 项目目标 | 有功能结论，缺少稳定目标卡片 | 项目目标、负责人、阶段和健康状态固定展示 | 增加项目概览区 |
| 进度 | 主要显示功能状态和版本 | 里程碑、任务、依赖、目标日期 | 增加里程碑和工作项层级 |
| 实时状态 | 有部分执行状态，但仍存在终态和 Turn 交接问题 | 状态更新和历史快照清晰分开 | 接入权威 Run 生命周期 |
| 更新 | 依赖文档和开发日志 | 有时间序列的项目更新 | 增加固定格式的更新记录 |
| 风险 | 分散在问题台账 | 项目页有可见风险和阻塞 | 增加风险摘要和跳转入口 |
| 决策 | 主要存在对话和文档中 | 决策可追溯并关联工作项 | 增加决策记录 |
| 成果 | 已有 Artifact 能力，但入口分散 | 工作项关联文档、提交、发布和结果 | 统一成果物和证据链接 |
| Agent | 能看到部分过程，缺少统一 Run 记录 | 普通工具没有直接对应能力 | 增加 Agent/Run 专属层 |
| 移动端 | 信息容易堆叠 | 首屏只显示高价值摘要，详细内容下钻 | 采用摘要卡 + 二级详情 |

## 8. 推荐的 M1：可用项目进度页

M1 只解决“用户打开页面后，能否在几十秒内知道项目现在发生了什么”。

### 8.1 首屏结构

```text
项目名称                     [正常/注意/阻塞]
项目目标 · 当前阶段 · 负责人 · 最后更新时间

当前正在发生什么
Agent/负责人 · 当前任务 · 当前摘要 · 最后真实活动 · 等待原因

里程碑
里程碑名称 · 状态 · 目标日期 · 完成度 · 阻塞原因

最近更新
已完成 · 正在进行 · 下一步 · 风险/需要确认

风险与决策摘要              成果物与证据
```

### 8.2 M1 必须有的字段

- 项目名称、目标、当前阶段；
- 项目健康状态和最后有效更新时间；
- 一个或多个里程碑；
- 工作项标题、状态、优先级、负责人和更新时间；
- 当前 Agent Run 的真实状态；
- 最近一条固定格式项目更新；
- 当前风险、阻塞和需要确认事项；
- 相关文档、提交、Artifact 或对话链接。

### 8.3 M1 明确不做

- 完整 Jira 工作流编辑器；
- 复杂甘特图和资源负载；
- 预算、工时和财务管理；
- 多组织、多租户和复杂权限；
- 自动让所有 Agent 同时发言；
- 展示原始内部推理或完整系统日志；
- 新建一套独立于 Codex Run 的伪任务状态。

## 9. M2 以后再做的内容

### M2：计划和追踪

- 任务依赖；
- Timeline/Gantt；
- 多里程碑视图；
- 版本和发布批次；
- 任务估算和实际耗时；
- 变更历史和审计。

### M3：协作与 Agent 编排

- 项目经理 Agent；
- Agent 之间的讨论和互相审核；
- 用户 `@` 指挥和中断；
- 冲突指令澄清；
- Provider/模型按角色路由；
- 受控共享上下文和 Token 成本记录。

### M4：组织和经营层

- 多项目 Portfolio；
- 团队资源和容量；
- 预算与成本；
- 部门和成员权限；
- 跨项目目标和管理报表。

## 10. 推荐开发顺序

1. 先固定项目进度数据结构，区分项目、里程碑、工作项、更新、风险、决策、Agent Run 和成果物。
2. 改造当前初版进度页，先增加项目概览、当前任务和里程碑，不先做复杂图表。
3. 接入已有 `execution-tracker`、SSE 和会话来源，显示真实 Agent Run；不得用页面轮询时间假装进度。
4. 增加最近更新、风险和决策摘要，并保留历史记录。
5. 将 Artifact、HTML/PDF、Git 提交和来源对话挂到工作项上。
6. 用户实际使用一轮后，再决定是否需要 Gantt、依赖、成本或多项目能力。

## 11. 关键架构约束

- 项目进度页是展示和汇总层，不替代 Codex 的真实执行状态。
- 项目级状态、工作项状态和 Agent Run 状态必须分开存储。
- `lastRealEventAt`、`lastHeartbeatAt`、`lastSnapshotAt` 和 `completedAt` 不得合并。
- 项目更新是追加记录，不覆盖历史；状态变化要保留时间和来源。
- 当前页面显示摘要，完整日志和原始证据进入二级页面。
- 不把用户界面样式、项目数据和 Codex 执行协议混在同一个组件中。
- 首版只支持单项目和少量真人成员，不提前引入企业组织模型。
- AI Agent 的模型、Provider、角色和工具能力解耦，不能把一个模型写死为某个职位。
- 任何“完成”都必须能关联到成果物、提交、测试或用户确认中的至少一种证据。

## 12. 最终结论

主流项目工具的共同核心不是“做一个进度条”，而是建立一条可追溯链：

```text
目标 -> 里程碑 -> 工作项 -> 当前执行 -> 更新/风险/决策 -> 成果物/证据
```

我们的项目进度页应先实现这条链的最小闭环。真正的独特性不在于复制 Jira 的看板，而在于把 Agent 的真实运行状态、项目更新、风险、决策和成果物放到同一条可追溯链中，同时不暴露不必要的内部推理。

当前建议的产品决策是：先把初版从“功能索引”升级为“单项目 AI 开发控制台 M1”，暂不扩展完整企业项目管理系统。
