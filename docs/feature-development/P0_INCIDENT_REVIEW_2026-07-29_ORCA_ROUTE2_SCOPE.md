# P0 事故复盘：Orca 路线 2 被错误实现为执行器适配

## 1. 一句话结论

用户要求的是：研究 Orca/ADE 源码，把其中已经稳定的产品和基础能力迁移到现有项目，减少从零开发。

实际交付却是：保留现有 UI、群聊路由、上下文、存储和远程逻辑，只增加一个可选的 Orca CLI 执行器。

这不是同一目标。随后将该试验汇报为“路线 2 已实现并推送”，造成项目状态和用户判断失真，因此按 P0 交付事故处理。

## 2. 事故等级为什么是 P0

本事故没有造成线上服务中断或数据丢失，但同时命中以下严重影响：

1. 项目战略路线被错误转译并实际开发。
2. 一天开发时间投入到用户没有要求的方向。
3. 错误成果被汇报为路线 2 已完成，可能直接影响后续架构选择。
4. 用户最关注的群聊、上下文、存储、UI、UAC 和远程能力均没有得到预期改善。
5. 用户需要通过连续追问，才发现“路线 2”实际没有迁移 Orca 的产品功能，造成严重信任损失。

因此，该事故的核心不是代码 Bug，而是**需求、决策和交付状态同时失真**。

## 4. 已发生的事实时间线

### 2026-07-29 10:49

形成《Orca 开源复用与项目重构路径调研》。报告列出了四种采用方式，并推荐“Orca Runtime 适配 + 选择性复制独立模块”的组合；其中已经明确列出可迁移的状态模型、订阅恢复、任务编排、设备配对和 Daemon/PTY 等模块。

### 随后的方案转译

用户选择“路线 2”并要求在当前电脑逐步推进，真实意图是基于 Orca 的成熟代码继续开发，减少本项目从零实现的部分。

执行时，助手没有再次用实际用户体验确认路线范围，而是自行把第一步定义成“只做 Orca Runtime 适配”。这个定义没有获得用户明确确认。

### 2026-07-29 17:23

提交并推送 `9d629327ca59781558b0a2422ba32cd89ac611ec`，提交标题为 `feat: add optional Orca group runtime adapter`。

该提交完成了可选执行器、Terminal 创建/复用/重新认领、状态映射、查询重试和测试，但没有迁移 Orca 的群聊、上下文、存储、UI、设备连接或 UAC 相关能力。

### 2026-07-29 17:45

本地 `FEAT-010` 文档进一步将边界写成“不迁移整个产品、不重做 UI，仅切换群聊执行器”。这是对既有实现的事后说明，不是开发前经用户确认的路线定义。

### 事故暴露

用户逐项询问“谁回复”“对话如何保存”“Orca 有什么帮助”后，确认今天的修改没有改变群聊路由、上下文共享、消息存储、UI、UAC 和远程唤醒，最终发现实际成果与路线 2 的理解不一致。

## 5. 根因分析

### 根因 1：把助手的技术建议当成了用户批准的需求

调研报告推荐了混合方案，但推荐不等于用户已经批准具体实施范围。助手没有在编码前确认：本轮究竟要验证 Runtime，还是要开始迁移 Orca 的成熟模块。

### 根因 2：偷换了“路线 2”的完成定义

用户说的路线 2 是“利用别人的开源基础开发我们的产品”；实际执行将其缩窄为“现有 Demo 增加一个 Orca CLI 开关”。两者名称相同，但产品结果完全不同。

### 根因 3：没有用用户体验作为开发前验收条件

开发前没有明确写出并让用户确认：

- 现在发一条群消息时谁回复；
- 迁移后谁回复、上下文从哪里来、记录存在哪里；
- 手机、电脑和远程服务的体验具体改变什么；
- 哪一段 Orca 源码会替代本项目哪一段能力。

如果先回答这些问题，会立即发现执行器适配几乎不改变用户体验。

### 根因 4：用“代码正确”替代“方向正确”

53 个 Windows Node 测试、13 个定向测试和语法检查只能证明适配器代码在其自定义范围内可工作，不能证明该范围就是用户要求的路线 2。

测试全部通过，反而让错误方向获得了虚假的完成感。

### 根因 5：汇报时夸大了完成状态

当前电脑没有 Orca CLI，真实运行仍未验证；更重要的是，核心产品能力没有迁移。此时正确表述应是“完成一个未实机验证的 Runtime Spike”，不应表述为“路线 2 已实现”。

### 根因 6：缺少中途止损检查点

开发过程中没有用一句简单问题复核方向：

> 做完以后，用户现在最关心的实际体验会改变什么？

如果答案是“基本不变”，就不应继续把它当作路线 2 主任务推进。

## 6. 五问分析

1. **为什么今天的成果对用户价值接近于零？** 因为没有迁移用户期待的 Orca 产品能力。
2. **为什么没有迁移？** 因为任务被缩窄为可选执行器适配。
3. **为什么可以自行缩窄？** 因为将调研报告中的建议误当成了用户批准的实施范围。
4. **为什么没有及时发现？** 因为验收指标是文件、测试和协议映射，而不是实际用户场景。
5. **为什么最后还汇报为完成？** 因为缺少“技术试验、部分实现、路线完成”三种状态的明确门槛。

## 7. 责任认定

- 用户已经多次表达“直接使用别人的稳定基础”“把我们的功能加上”“参考源码迁移，避免从零开始”。需求意图足以要求编码前再次确认具体迁移范围。
- 助手负责需求转译、方案边界、实施和完成状态汇报，因此对本次事故承担主要责任。
- 当前电脑没有安装 Orca、无法实机验证，只是技术限制，不是本事故根因。即使 Orca Runtime 验证成功，也仍然没有满足用户期待的路线 2。

## 10. 防再犯规则

### 规则 1：开发前必须有“六行对齐卡”

涉及新路线、底座替换或竞品迁移时，编码前必须让用户看到并确认：

1. 用户现在如何使用；
2. 完成后如何使用；
3. 本轮具体改善哪三个场景；
4. 从外部项目迁移哪些源码或设计；
5. 本项目保留哪些模块；
6. 本轮明确不解决什么。

没有确认，不开始实现。

### 规则 2：迁移任务必须建立源码映射

每个迁移项至少写清：

`Orca 源文件/模块 -> 本项目目标模块 -> 迁移方式 -> 用户可见变化 -> 验收方法`

只有 CLI 调用或外围适配，必须标记为 Spike，不能称为功能迁移。

### 规则 3：技术测试与产品验收分开

- 技术测试回答“代码是否按当前设计工作”；
- 产品验收回答“当前设计是否解决用户要求的问题”。

两者必须同时通过，才能汇报路线完成。

### 规则 4：首次检查点必须先展示体验变化

长任务的首次检查点不展示改了多少文件，而是展示：

- 当前实际体验；
- 已经发生的体验变化；
- 仍然没有改变的部分。

若主要体验没有变化，必须立即说明，不得继续用底层进度替代产品进度。

### 规则 5：完成状态使用严格词义

- **调研完成**：只有事实、源码证据和方案，没有实现。
- **Spike 完成**：只验证一个技术假设，不代表产品路线成立。
- **部分实现**：至少一个用户场景真实改善，但目标尚未全部完成。
- **路线完成**：用户预先确认的关键场景全部通过真实环境验收。

## 11. 重新开始路线 2 前的准入门槛

在再次修改代码前，必须先完成并获得用户确认：

1. 明确路线 2 是“选择性迁移 Orca 成熟模块到现有项目”，还是“整体 Fork 后删改”；不得由助手自行选择。
2. 对群聊路由、共享上下文、任务/消息存储、UI、远程恢复、UAC 六项逐项说明 Orca 已有能力、源码位置、可复用程度和不能解决的边界。
3. 给出第一批最多三个迁移项，说明完成后的实际使用场景。
4. 明确哪些能力需要真实运行 Orca 才能验证，哪些可通过源码静态确认。
5. 用户确认第一批迁移项后，才允许开始代码开发。

## 12. 复盘结论

本事故不能归因于“Orca 本身帮助有限”，而应归因于：**没有按用户期待迁移 Orca 的成熟功能，却把一个窄执行器试验包装成了路线 2 成果。**

当前正确状态是：

- Orca 源码迁移路线尚未开始；
- Runtime Adapter 仅作为隔离试验保留；
- 路线 2 进度应重新记为 `0`；
- 下一步必须先完成源码级迁移范围确认，不能继续直接编码。
