## 3. 用户发现的问题

### BUG-20260722-001：网页端无法启动当前 Codex 任务

- 严重程度：P0，核心路径不可用
- 当前状态：已修复并由用户完成浏览器实测
- 发现入口：手机浏览器和电脑浏览器

### BUG-20260722-002：网页写入同一 Thread 后，Desktop 当前页面不热刷新

- 严重程度：P1，双端体验不完整并存在并发使用风险
- 当前状态：已定位，尚未修复
- 用户表现：网页中测试消息执行成功并显示完成，但 Codex Desktop 已打开的同名任务中没有出现该消息和回复
- 已验证证据：Web API 在 Thread `019f84c5-eb00-75d2-8726-fa8a11339e53` 中读取到浏览器测试消息及 Codex 回复，没有创建另一条假会话
- 原因判断：Demo 使用独立 app-server 进程；它与 Desktop 共用持久化 Thread，但 Desktop 当前视图不订阅该进程的 Notification，也没有监视外部追加记录并热刷新
- 影响：持久记录是一致的，但 Desktop 画面可能滞后；如果网页和 Desktop 同时发送，用户看到的顺序可能和实际 Thread 记录不一致
- 临时约束：同一 Thread 同一时间只使用一个发送入口；需要回到 Desktop 时可尝试重新打开任务，但该刷新行为尚未作为稳定能力验证
- 正确方向：研究 Desktop 自身 daemon/proxy/IPC 或统一 Connector，使两个前端订阅同一运行实例；不能通过直接修改 JSONL 解决

## 4. 排查过程

### 4.1 先定位失败阶段

页面发送路径可以简化为：

```text
浏览器发送消息
  -> Demo 后端接收请求
  -> 启动 Codex app-server
  -> thread/resume 恢复当前对话
  -> turn/start 启动新一轮任务
  -> SSE 把状态和回复推送到页面
```

错误发生在 `thread/resume` 阶段，尚未进入真正的 `turn/start` 执行。因此：

- 消息已经到达 Demo 后端；
- 不是模型执行太慢；
- 不是 SSE 等不到最终回复；
- 不是手机端单独丢失请求；
- 是后端使用的 Codex 运行时无法读取当前 Desktop 会话。

### 4.2 检查 Demo 实际调用的 Codex

当前 `windows/server/app-server-client.mjs` 没有使用 Codex Desktop 当前管理的运行时，而是硬编码到全局 npm 安装：

```text
%APPDATA%\npm\node_modules\@openai\codex\bin\codex.js
```

该路径当时对应：

```text
codex-cli 0.122.0
```

当前需要恢复的 Desktop 会话元数据显示，其创建运行时为：

```text
codex-cli 0.145.0-alpha.18
```

两者在会话文件格式或解析逻辑上不兼容。

### 4.3 旧运行时恢复当前会话的实测

使用 `codex-cli 0.122.0` 恢复当前 Desktop 会话时，约 221ms 即返回错误：

```text
failed to load rollout ... failed to parse thread ID from rollout file
```

这个错误证明旧运行时在解析 rollout 文件时失败，任务还没有真正开始。

### 4.4 对照测试

为了区分“0.122.0 完全不能恢复会话”和“0.122.0 不能恢复新格式会话”，使用旧运行时自己创建的 `0.122.0` 会话进行对照：

- 运行时：`codex-cli 0.122.0`
- 会话来源：`codex-cli 0.122.0`
- 恢复结果：成功
- 用时：约 606ms

因此故障不是 `thread/resume` 调用方式普遍错误，而是跨版本兼容问题。

### 4.5 更新 Codex Desktop 后的复查

Codex Desktop 更新后的已验证状态：

| 检查项 | 结果 |
| --- | --- |
| Desktop 包版本 | `OpenAI.Codex 26.715.10079.0` |
| 当前会话元数据版本 | `codex-cli 0.145.0-alpha.18` |
| Desktop 管理的可执行文件 | `C:\Users\Hans\AppData\Local\OpenAI\Codex\bin\e2d6a5ee2cac801c\codex.exe` |
| 该运行时版本 | `codex-cli 0.145.0-alpha.30` |
| 恢复当前会话 | 成功，约 486ms |
| 恢复结果 | 正确 Thread ID，73 个 turns |
| Desktop 基础目录中的运行时 | `0.130.0-alpha.5`，版本较旧 |
| WindowsApps 中的直接执行 | `Access is denied` |

这说明更新后的 Desktop 已经包含可以读取当前会话的运行时。当前问题不需要修改 JSONL，也不应通过篡改会话元数据解决；需要修正的是 Demo 选择 Codex 运行时的方式。

## 5. 根因分析

### 5.1 直接根因

Demo 将 Codex app-server 的入口固定为全局 npm 包路径。全局版本是 `0.122.0`，而当前 Desktop 会话来自 `0.145.0-alpha.18`。旧运行时不能解析新会话的 rollout 文件，因此 `thread/resume` 失败，页面统一显示“Codex 启动任务失败”。

### 5.2 代码层根因

`windows/server/app-server-client.mjs` 目前存在以下限制：

1. 只知道一个固定的全局 npm 路径；
2. 不检查该运行时是否存在、完整、可执行；
3. 不比较运行时和会话格式的兼容性；
4. 不支持通过环境变量明确指定运行时；
5. 启动失败时没有自动尝试 Desktop 管理的更新运行时；
6. 用户侧只看到统一错误，无法区分“运行时不存在”“版本不兼容”和“任务启动超时”。

### 5.3 降级逻辑的放大问题

`windows/server/conversation-service.mjs` 当前使用进程级变量 `primaryAvailable`：

- 初始值为 `true`；
- 任意一次 app-server 读取失败后永久改为 `false`；
- 后续所有会话都不再尝试 app-server；
- 发送功能会直接被禁用，直到整个 Demo 服务重启。

这会把“某一个会话暂时不兼容”放大成“整个服务所有会话都不能发送”。正确粒度应该是单次请求或单个会话，而不是整个进程。

### 5.4 架构层根因

UI、会话读取、任务控制目前直接依赖某个具体 Codex 可执行文件的位置和版本。运行时发现、兼容性判断、失败降级没有集中在独立 Connector 中。因此 Codex Desktop 一更新，Demo 就可能再次被旧全局 CLI 拖住。

## 6. “15 秒”是什么意思

`app-server-client.mjs` 中的 `requestTimeoutMs = 15000` 是单次 app-server 协议请求等待确认的上限，适用于：

- `initialize`
- `thread/read`
- `thread/resume`
- `turn/start`

它不是 Codex 完成整个任务的最长时间，也不会在 15 秒后强行终止正在执行的模型任务。

正常流程中，`turn/start` 只需要在 15 秒内确认“任务已经开始”；之后任务可以继续运行更长时间，状态和增量回复由事件流持续传回页面。

本次错误与 15 秒无关：旧 CLI 在约 221ms 内已经明确返回 rollout 解析失败，远未到超时上限。

后续维护时应把两类错误分开：

- 协议请求超过 15 秒：显示“Codex 服务未及时响应”；
- app-server 明确返回解析或兼容性错误：显示“当前 Codex 运行时无法恢复此对话”。

## 8. 已实施的初步解决方案

### 8.1 第一阶段：最小修复运行时选择，不动 UI（已完成）

在 app-server 客户端前增加一个轻量运行时解析器，候选顺序如下：

1. 如果设置了 `CODEX_APP_SERVER_BIN`，优先使用明确指定的可执行文件；
2. 扫描 `%LOCALAPPDATA%\OpenAI\Codex\bin\*\codex.exe`；
3. 对候选文件执行轻量版本和可运行性检查，选择最高的可用兼容版本；
4. 再尝试 Desktop 基础目录中的 `bin\codex.exe`；
5. 全局 npm Codex 只作为最后兜底，并且必须先检查安装是否完整。

用户侧预期变化：继续打开同一个 Demo 页面、选择同一个真实对话并发送指令时，后端会使用能够读取该对话的 Desktop 运行时，不再因为旧全局 CLI 而立即失败。

这一阶段不修改：

- Codex 风格 UI；
- 现有组件视觉结构；
- 对话内容渲染规则；
- JSONL 文件及其元数据；
- 项目依赖；
- 多人群聊架构。

### 8.2 第二阶段：把降级改为单请求或单会话（已完成）

移除“一次失败后永久设置 `primaryAvailable = false`”的进程级行为：

- 当前请求失败时只对当前请求回退；
- 某个会话格式不兼容时只标记该会话；
- 其他会话仍可继续尝试 app-server；
- 兼容运行时恢复后，不需要重启整个 Demo 才能重新发送。

用户侧预期变化：一个旧会话或异常会话不会让整个项目里的发送功能全部失效。

### 8.3 第三阶段：细化错误信息和状态

保持现有 UI 样式不变，只在功能数据层提供明确的错误类型：

- `runtime-not-found`
- `runtime-incomplete`
- `thread-incompatible`
- `request-timeout`
- `turn-start-failed`

页面只显示简短、可理解的状态；版本、路径和原始协议错误留在服务日志中。这样可以定位问题，又不会把技术堆栈暴露到主要对话界面。

## 9. 长期维护方案

### 9.1 固定边界

长期结构建议保持为：

```text
UI / 后续协作层
        ↓
稳定的 Codex Connector
        ↓
运行时适配器
        ↓
Codex Desktop 管理的 app-server 运行时
```

各层职责：

| 层 | 职责 | 不负责 |
| --- | --- | --- |
| UI | 展示对话、输入指令、展示状态 | 查找 Codex 安装位置、解析 CLI 版本 |
| 功能层 | 发送、取消、重试、执行状态 | 视觉样式和会话文件格式兼容 |
| Connector | `initialize`、`thread/resume`、`turn/start`、事件转发、错误归一化 | 页面布局 |
| 运行时适配器 | 发现、检查、选择和启动兼容 Codex | 对话内容渲染 |
| 会话读取层 | 读取真实项目会话，提供列表和消息 | 启动模型任务 |

这样做的目的不是重写当前 Demo，而是把最容易随 Codex 更新变化的部分集中到一个边界内，避免再次牵连 UI、内容渲染和协作功能。

### 9.2 版本更新后的最低维护检查

每次 Codex Desktop 更新后只做以下轻量检查：

1. 记录 Desktop 包版本和候选 `codex.exe --version`；
2. 使用只读方式恢复一个当前项目会话；
3. 确认 `thread/resume` 返回正确 Thread ID；
4. 确认运行时选择日志没有退回不完整的全局 npm 包；
5. 用项目规定的 `pnpm` 命令做基础构建；
6. 页面实际效果由用户验收，不擅自增加浏览器自动验收流程。

不应通过编辑 append-only JSONL、伪造元数据或把旧会话重新写一遍来解决兼容问题。

### 9.3 后续可调研但不应阻塞当前修复的方向

新版 app-server 帮助中出现了 `daemon` 和 `proxy`。后续可以单独评估它们是否提供更稳定的官方连接方式，但当前没有足够证据直接把 Demo 切换过去。

当前优先级仍然是先完成轻量运行时适配器，让单项目、单对话的网页控制路径稳定可用。`daemon/proxy` 调研不能阻塞这个最小修复。

## 10. 尚未执行、需要确认的环境恢复

以下操作会改变用户本机全局环境，本文只记录，不执行：

1. 重新检查 PID `25808`、`2656` 是否仍存在以及是否确属本轮 npm/npx 操作；
2. 如仍存在，在确认后停止对应进程；
3. 删除不完整的 `@openai\codex` 新目录；
4. 将原有完整 `0.122.0` 目录和三个 shim 从 npm 备份名恢复；
5. 删除本轮明确产生的三个临时目录；
6. 验证 `Get-Command codex`、`codex --version` 和全局目录状态；
7. 不删除其他历史 npm/npx 缓存，不改 WindowsApps，不重新安装新全局依赖。

在用户明确批准前，不应执行这些删除、移动和停止进程操作。

## 11. 后续开发顺序

1. 只读验证 Desktop 重新打开任务后的刷新行为，明确它是可用的手动恢复方式还是偶发现象。
2. 调研 Desktop 自身 daemon/proxy/IPC，判断网页能否连接同一个运行实例；如果不能，明确保持网页与 Desktop 分离使用。
3. 在统一同步前禁止同一 Thread 双端并发发送，并在后续功能层提供占用或冲突提示。
4. 单独获得确认后恢复本机全局 Codex/npm 环境；该操作不与产品开发混在一起。
5. 正式远程开放前先修复固定 token、监听范围、审批和权限问题。
6. 完成单项目同步与安全边界后，再进入多人群聊和多 Agent 协作层。

## 12. 维护约束

后续处理这类问题时固定遵守以下边界：

- 项目依赖和构建使用 `pnpm`，不再擅自执行全局 npm 安装；
- 不修改 UI 文件，除非用户明确授权 UI 变更；
- UI、内容读取、任务执行和运行时适配分别维护；
- 不修改 Codex 会话 JSONL；
- 不伪造对话、状态或项目内容；
- 不因一个会话失败永久禁用全部发送能力；
- 不自动清理全局目录、缓存或进程；
- 运行服务前先确认是否已有可用实例，避免重复端口和残留服务；
- 修改后只做与风险匹配的基础代码和构建检查，具体页面效果由用户验收；
- 遇到新版 Codex 格式变化，优先升级或切换兼容运行时，不向 UI 和内容层扩散兼容代码。

## 13. 结论

本次“Codex 启动任务失败”已经完成闭环：根因是 Demo 使用 `codex-cli 0.122.0` 恢复由 `0.145.0-alpha.18` 创建的 Desktop 会话，旧运行时在约 221ms 内解析 rollout 失败。后端已增加 Desktop 运行时选择并调整按请求降级，服务重启后用户已在电脑浏览器成功发送消息、收到回复并看到完成状态。

修复同时证明了新的边界：网页和 Desktop 可以指向同一持久化 Thread，但两个独立运行进程没有共享实时视图。网页写入成功不代表 Desktop 当前页面会立即显示。下一阶段应解决统一运行实例或明确分离使用，而不是继续把“写入 JSONL”误当成双端同步。

同时，本轮排查错误执行的全局 npm 升级留下了不完整安装和临时残留。这是需要单独处理的本机环境问题，不能和产品 Bug 混为一谈，也不能未经确认直接清理。
