- 用户当前截图中的直接故障；

## 2. 当前截图问题结论

截图地址为：

```text
http://127.0.0.1:4173
```

页面显示：

```text
Unexpected token '<', "<!doctype "... is not valid JSON
```

这不是 JSONL 会话内容损坏，而是前端请求 `/api/project`、`/api/sessions` 时收到了 HTML 页面，然后直接调用 `response.json()` 导致解析失败。

当前实测证据：

| 请求 | HTTP 状态 | Content-Type | 实际内容 |
| --- | ---: | --- | --- |
| `http://127.0.0.1:4173/api/project?token=demo123` | 200 | `text/html` | `<!doctype html>...` |
| `http://127.0.0.1:9360/api/project?token=demo123` | 200 | `application/json; charset=utf-8` | 正确的项目 JSON |

端口状态：

- `4173`：旧的 Vite Preview，PID `2256`，启动时间 `2026-07-21 21:46:10`。
- `9360`：新的同源 UI + API 服务，PID `17524`，启动时间 `2026-07-21 23:02:26`。
- 当前 `vite.config.ts` 已配置把 `/api`、`/events` 代理到 `9360`，但运行中的 `4173` 进程早于该配置，因此没有加载新代理。
- 截图地址还缺少 `token=demo123`。即使重启后代理生效，没有令牌也会收到 `401`。

因此当前截图的根因是两个问题叠加：

1. 用户打开了旧入口 `4173`，该进程仍使用旧配置，把未知 `/api/...` 路由回退成 `index.html`。
2. 地址没有访问令牌，而当前 API 仍要求查询参数 `token`。

## 3. Bug 清单

### BUG-001：存在两个可访问入口，旧入口返回错误内容

- 严重程度：P0
- 状态：未修复
- 用户表现：页面框架能打开，但项目名、会话列表和对话全部加载失败。
- 直接原因：`4173` 和 `9360` 同时存在，职责不清；旧的 `4173` 没有有效 API 代理。
- 深层原因：交付时给过两个链接，开发过程中没有收束成唯一入口，也没有关闭或明确废弃旧服务。
- 建议：只保留 `9360` 作为正式 Demo 入口；`4173` 要么停止，要么明确仅用于前端开发并在启动时加载正确代理。

### BUG-002：链接依赖手工携带 token

- 严重程度：P0
- 状态：未修复
- 用户表现：直接打开 `http://127.0.0.1:9360/` 或旧收藏链接时，API 返回 `401`。
- 原因：前端只从当前 URL 查询参数读取 token，没有缺失令牌时的恢复路径。
- 建议：短期由唯一启动命令打印完整可点击链接；中期改为服务端同源会话或一次性 cookie，避免用户维护查询参数。

### BUG-003：开发服务生命周期不可控

- 严重程度：P0
- 状态：未修复
- 用户表现：旧进程继续占用端口；修改配置后页面仍表现为旧版本。
- 原因：没有统一的启动、停止、端口检测和 readiness 检查；不同 Node 运行时启动了不同服务。
- 建议：增加一个最小启动入口，启动前检查 `4173/9360`，只管理本项目创建的 PID，并在就绪后输出唯一 URL。

### BUG-004：前端把 HTML 解析错误原样暴露给用户

- 严重程度：P1
- 状态：未修复
- 用户表现：出现 `Unexpected token '<'`，无法判断是链接错误、服务未启动还是权限问题。
- 原因：`fetchJson()` 只检查 HTTP 状态，没有检查 `Content-Type`，随后直接调用 `response.json()`。
- 建议：解析前验证 `application/json`；若收到 HTML，显示“当前链接未连接到项目数据服务”；保留技术详情到日志，不在主界面重复显示原始异常。

### BUG-005：同一个错误在侧栏和中央区域重复显示

- 严重程度：P1
- 状态：未修复
- 用户表现：截图中相同错误出现两次，页面视觉噪音较大。
- 原因：项目、会话列表、会话详情共用一个 `error` 状态，同时传给 `Sidebar` 和 `Conversation`。
- 建议：拆成 `projectError`、`listError`、`sessionError`，或统一成一个全局错误状态，只在最相关区域显示一次。

### BUG-006：新版会话元数据超过 32KB，导致真实会话遗漏

- 严重程度：P0
- 状态：本轮已修复
- 原表现：项目实际有 8 个 JSONL，会话列表只显示 4 个。
- 原因：服务只读取文件前 32KB，但新版 `session_meta` 首行约 40KB，整行被截断后无法 JSON 解析。
- 已做处理：按块读取，直到获得完整首行，并设置 1MB 上限。
- 后续风险：如果未来 `session_meta` 超过 1MB，仍会漏掉；应考虑基于流的首行读取和明确错误日志。

### BUG-007：同时读取两套消息事件，造成重复内容和内部摘要混入

- 严重程度：P0
- 状态：本轮已修复
- 原表现：同一条用户消息或最终回复重复出现；内部 handoff summary 被当成真实回复。
- 原因：同时读取 `response_item/message` 和 `event_msg`，而两者描述同一轮 UI 消息但文本长度可能不同，简单文本去重无法识别。
- 已做处理：只保留 UI 可见的 `event_msg/user_message` 和最终 `event_msg/agent_message`。
- 后续风险：需要用旧版会话样本确认所有历史版本都提供这两类事件；否则需按 CLI 版本设计兼容分支。

### BUG-008：会话标题曾由硬编码关键词生成，不完全是真实内容

- 严重程度：P1
- 状态：本轮已修复
- 原表现：当前对话被概括成通用主题，无法直接对应真实首问。
- 原因：标题规则扫描整段会话后匹配“summary”“Happy Coder”等关键词。
- 已做处理：标题直接取首条有效用户消息；没有用户消息时取首条真实助手回复。

### BUG-009：冷启动仍需解析全部项目会话

- 严重程度：P2
- 状态：部分优化，未完全解决
- 当前数据：只扫描本项目 8 个文件，冷请求约 0.35 秒，热请求约 1 至 10 毫秒。
- 已改善：不再解析全部约 1.28GB 会话；只识别本项目约 28MB；增量读取追加内容。
- 仍有问题：第一次 `/api/sessions` 仍解析所有项目文件以计算标题、计数和预览；`readAppend()` 会按追加长度一次性分配 Buffer。
- 建议：维护轻量索引（文件大小、偏移、标题、计数、最后消息）；冷启动流式读取，避免按完整文件大小分配单个 Buffer。

### BUG-010：后台轮询仍周期性遍历整个 sessions 目录

- 严重程度：P2
- 状态：未修复
- 原因：项目文件缓存 5 秒过期后重新递归遍历 `~/.codex/sessions`，虽然命中的文件头已缓存，但目录仍会重复扫描。
- 建议：按日期目录增量发现新文件，或使用文件系统 watcher，并保留低频兜底扫描。

### BUG-011：页面依赖运行时错误信息判断服务状态

- 严重程度：P1
- 状态：未修复
- 用户表现：项目名和标题长期停留在“正在读取”，底部显示“正在连接本地服务”，但没有明确指出入口错误。
- 原因：没有独立的启动状态机和健康检查结果；项目请求、列表请求和 SSE 状态相互独立。
- 建议：定义 `starting / ready / unauthorized / wrong-endpoint / offline` 状态，并用单一、可操作的提示展示。

## 4. 本轮开发过程中的低效问题

### EFF-001：没有先确定唯一入口和验收 URL

最主要的效率损失。UI 曾运行在 `4173`，真实 Demo/API 后来运行在 `9360`，但旧服务没有收束。开发者内部验证了 `9360`，用户仍可能打开先前的 `4173`，导致“代码已修但用户看到错误”。

改进：任何合并前先确定一个 canonical URL，后续所有构建、启动、说明和链接都只围绕这个入口。

### EFF-002：服务启动方式反复失败，且第一次没有日志

出现过以下问题：

- 前台命令受工具超时影响，被误认为服务崩溃；
- `Start-Process` 因环境里同时存在 `Path/PATH` 触发字典重复异常；
- 尝试用 `.NET ProcessStartInfo` 时参数传递错误，短暂启动了无参数 Node；
- 第一次后台启动没有重定向日志，无法快速判断退出原因。

改进：项目内提供一个受控启动脚本；日志固定写入临时目录；启动后只做一次 `/api/project` readiness 检查。

### EFF-003：没有先检查真实 JSONL 首行尺寸和事件类型

最初假设 32KB 足够容纳 `session_meta`，也同时纳入两套消息事件。直到列表只出现 4 个会话、内容重复后，才对真实文件逐个统计。

改进：实现前先抽取 8 个项目文件的最小样本矩阵：首行长度、CLI 版本、事件类型、用户消息数、最终回复数。用样本决定解析规则，再写代码。

### EFF-004：PowerShell 命令与当前版本不兼容

本轮出现多次无效命令：

- 在 Windows PowerShell 5 中使用 `??`；
- `foreach { ... } | Format-Table` 触发空管道解析错误；
- 使用 `Get-NetTCPConnection` 时触发不可用的 CIM/WMI；
- 之后才切换到 `netstat` 和先收集数组再输出。

改进：固定使用兼容 Windows PowerShell 5 的语法；端口检查优先 `netstat -ano`；复杂诊断拆成短命令。

### EFF-005：读取输出过宽，造成截断和二次检查

曾用 `rg -n "."` 输出整个服务脚本和多个文件，结果被截断；还出现 `Get-Content` 对无 BOM UTF-8 的乱码显示，短暂干扰判断。

改进：先搜索目标符号和行号，再读取局部范围；中文源码优先使用 `rg` 或明确 UTF-8 编码。

### EFF-006：构建工具链没有在开始时锁定

用户要求 `pnpm build`，但 pnpm 因非 TTY 环境和 store/node_modules 状态试图重建依赖，构建没有按原命令完成；后来直接调用本地 `tsc` 和 `vite` 二进制完成了等价构建。

改进：开始时记录 Node、pnpm、store 路径和现有 `node_modules` 来源；修复 pnpm 的 store 一致性后，再把唯一构建命令固化为 `pnpm --dir web-ui build`。

### EFF-007：渲染检查工具链不稳定，产生无效尝试

Browser 插件和项目 Playwright 都不可用；随后尝试 Chrome/Edge headless 截图时又遇到沙箱、既有浏览器进程和等待时机问题，生成了多次无效命令。用户随后明确要求由用户自行验收。

改进：本项目不把浏览器自动验收作为默认阻塞项。开发者只做构建、接口和最小启动检查；页面视觉及交互由用户验收，除非用户明确要求自动化浏览器检查。

### EFF-008：改动范围在诊断过程中持续扩大

修复真实数据接入时，同时处理了移动侧栏、错误状态、标题规则、重复消息和服务启动。虽然问题相关，但增加了变量数量，使“当前页面为什么打不开”的主线不够清晰。

改进：分为三个独立阶段：

1. 唯一入口可打开并获取 JSON；
2. 真实会话数据正确；
3. 移动端和视觉细节。

每阶段完成后停止扩展，由用户决定是否进入下一阶段。

## 5. 建议修复顺序

### 第一阶段：先恢复唯一可用入口

1. 停止或废弃旧的 `4173` 进程。
2. 明确 `9360` 是唯一 Demo 入口。
3. 增加统一启动命令，输出完整带 token 的链接。
4. 在启动脚本中检查根页面和 `/api/project` 是否同源可用。

用户侧预期变化：只需要记住和打开一个链接，不再出现“页面能开但数据接口是 HTML”的情况。

### 第二阶段：让错误信息可理解

1. `fetchJson()` 检查 `Content-Type`。
2. 将 HTML 响应、401、离线、会话不存在分别转成清晰提示。
3. 避免侧栏和中央区域重复显示同一错误。

用户侧预期变化：即使链接或服务有问题，也能直接知道原因和下一步，不会看到底层 JSON 解析异常。

### 第三阶段：固化开发与启动流程

1. 统一 Node/pnpm 版本和 pnpm store。
2. 使用 `pnpm build:ui`、`pnpm start:demo` 两个稳定命令。
3. 记录 PID、端口和日志位置；启动前识别旧进程。
4. 不自动启动 `9350` summary observer，避免额外模型调用。

### 第四阶段：再继续性能优化

1. 为 8 个项目会话维护增量索引。
2. 改成流式读取追加数据。
3. 减少全 sessions 目录遍历。
4. 用真实文件样本覆盖不同 CLI 版本。

## 6. 当前建议的最小修复范围

为了尽快恢复可用状态，下一轮建议只处理以下四项，不扩大范围：

1. 收束到唯一 `9360` 入口；
2. 解决 token 传递；
3. 增加 JSON Content-Type 防护；
4. 将重复错误改成单一明确提示。

完成这四项后，由用户打开页面验收；确认入口和真实数据正常后，再决定是否继续处理启动脚本和性能索引。
