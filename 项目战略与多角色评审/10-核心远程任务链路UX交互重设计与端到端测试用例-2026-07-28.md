# 核心远程任务链路 UX 交互重设计与端到端测试用例

日期：2026-07-28

适用范围：当前项目的项目群、单人 Codex 会话、远程执行、多 Agent 协作、审批、中断恢复和成果验收

文档性质：产品交互目标与验收测试，不代表当前功能已经实现

本次重审重点：各 UI 组件之间的职责、状态来源、操作优先级和空间占用。目标不是继续增加卡片和面板，而是确保同一时刻只有一个主要上下文、一个主要操作和一个权威状态，避免不同组件互相覆盖、重复或给出矛盾信息。

## 最新需求校正（2026-07-28 15:47 +08:00）

以下边界优先于本文后续较早的理想化设计：

1. Codex Desktop 是用户在原电脑前的正常入口，Web 是远程补充，不存在“只使用 Web”的要求。
2. Web 第一阶段只需提示“Desktop 正在同一任务内工作”；暂不要求 Desktop 反向提示 Web。
3. “修改文件、测试、构建”属于 Codex 原有过程事件同步，不单独建立“正在修改”功能或另一套任务状态。
4. 当前最严重体验问题是执行约 1–2 分钟后过程停止更新，必须先修复持续事件与重连补偿。
5. 群聊特有能力仍需定义，但消息、过程、附件、断线恢复、停止/追加和失败反馈等基础能力必须先与单人 Codex 看齐。
6. 正常远程开发应通过用户级工具链尽量不触发 UAC；真实 UAC 只作为极少数本机维护的兜底，不建设 UAC broker。
7. 项目进程退出时优先研究最小“启动项目”入口；如果无法保证入口独立存活，向日葵等远程桌面是可接受兜底。不提前加入电脑重启恢复、双 Worker 和自动回滚。

## 一、设计目标

本轮不追求增加更多 Agent、更多入口或复杂页面，而是把一条最重要的用户链路做完整：

```text
用户提出目标
  -> 系统确认任务已接收
  -> 项目经理 Agent 澄清并拆解
  -> 专业 Agent 执行
  -> 用户随时查看、追加、暂停或审批
  -> 断线后自动恢复
  -> 项目经理汇总成果与风险
  -> 用户验收或要求修改
```

理想效果是：用户无论在电脑、网页还是手机上，都能在 10 秒内回答五个问题：

1. 现在是谁在做什么？
2. 已经完成了多少？
3. 为什么停住了？
4. 现在需要我做什么？
5. 最终产生了什么结果和证据？

## 二、竞品启示转化

本方案参考既有竞品调研，但不直接复制界面。

### Happy：跨端连续性

借鉴：电脑、网页和手机看到同一任务状态；控制权切换明确；审批和错误能够主动通知；断线后可以恢复。

转化为本项目要求：用户离开电脑后，任务、审批和结果不能留在电脑端成为孤岛。

### OpenClaw：Gateway 与事件化审批

借鉴：渠道只是入口，任务和审批由常驻 Gateway 管理；审批是有 ID、状态、有效期和结果的正式对象。

转化为本项目要求：审批显示为任务时间线中的行动卡片，而不是依赖本机弹窗。

### OpenAgents Workspace：持久工作空间

借鉴：成员、消息、任务、文件和 Agent 状态分开建模；Agent 离线不影响工作空间和历史。

转化为本项目要求：聊天只是入口，任务不能仅以聊天气泡存在。

### ChatGPT Work：从过程走向成品

借鉴：用户最终需要的是可以审阅和继续使用的成果，不是大量工具日志。

转化为本项目要求：完成状态必须包含成果、摘要、验证证据、风险和下一步，而不是只有一段 Agent 回复。

### Harness：可恢复、可审计的工作流

借鉴：任务有阶段、依赖、审批、失败原因、重试和证据。

转化为本项目要求：失败、拒绝和中断都必须有明确后续动作，不能只有红色错误提示。

## 三、核心 UX 原则

### 3.1 用户看任务，不看底层协议

默认界面显示目标、负责人、阶段、进度、阻塞和成果。命令、原始日志和 Thread ID 放入“查看详情”，供需要时核查。

### 3.2 所有等待都必须说明责任人

禁止只显示“等待中”。必须明确显示：

- 等待 Agent；
- 等待项目经理审查；
- 等待用户授权；
- 等待本机操作；
- 等待网络恢复；
- 等待其他任务完成。

### 3.3 用户最新指令优先

执行中输入新消息时，系统必须让用户知道该消息会：

- 追加到当前任务；
- 修改任务方向；
- 新建独立任务。

默认选择“追加到当前任务”，但涉及目标改变时提示用户确认。

### 3.4 审批不阻塞整个产品

一个任务等待审批时：

- 当前任务进入“需要你处理”；
- 其他不依赖该审批的 Agent 可以继续；
- 用户仍可查看历史、成果和其他项目；
- 系统发送跨端通知；
- 超时后明确拒绝或取消，不永久悬挂。

### 3.5 中断必须可恢复

暂停、断网、页面关闭、设备切换和服务重启后，用户重新进入时，应看到同一任务及最后确认状态。系统不得因为前端重连而重复提交命令。

### 3.6 高风险操作优先解释影响

审批卡片先回答“会影响什么”，再展示“底层执行什么”。按钮不能只有模糊的“确认”。

### 3.7 一个屏幕状态只保留一个主要动作

普通执行状态的主要动作是“追加指令”；等待审批状态的主要动作是“处理审批”；成果待验收状态的主要动作是“验收成果”。

暂停、切换模式、选择 Agent、查看日志等操作不得与当前主要动作争夺同等视觉权重。审批属于明确的二选一决策状态时，“允许一次”和“拒绝”可以作为同级动作。

### 3.8 同一事实只能有一个 UI 所有者

- 设备是否在线：由全局连接状态负责；
- 任务是否阻塞：由任务状态条和任务卡片负责；
- Agent 正在做什么：由 Agent 状态负责；
- 谁可以操作：由控制权状态负责；
- 是否需要用户行动：由待处理中心负责；
- 成果是否通过：由成果验收负责。

其他组件可以引用这些状态，但不能各自计算并显示不同结论。

## 四、主要界面与信息结构

### 4.1 总体布局：主画布加上下文检查器

当前群聊界面已经存在左侧项目与成员、中间消息流、右侧 Agent 列表。如果再增加永久任务详情栏，会形成四套竞争信息。理想布局应收敛为：

1. 左侧导航：只负责项目、会话、未读和待处理数量，不显示详细执行状态。
2. 中央主画布：只显示当前项目或当前任务的时间线，是用户主要阅读和操作区域。
3. 右侧上下文检查器：根据当前选择切换“任务、Agent、成果”内容，不同时展示三套面板。

右侧默认显示当前任务。用户主动点选 Agent 时，检查器才切换到 Agent 详情；关闭后恢复任务详情。不得因为点选 Agent 就暗中改变输入框发送对象或执行模式。

在 901–1200 像素宽度下，右侧检查器改为抽屉；不继续压缩中央阅读区。在 900 像素以下，左侧导航和右侧检查器都使用互斥抽屉。

手机端使用单主画布：

- 顶部：项目身份和最高优先级状态；
- 中部：当前时间线；
- 底部：输入区；
- 任务、Agent、待处理和成果详情使用全屏页或互斥抽屉。

手机端任何时刻只能打开一个临时表面：提及菜单、任务抽屉、审批页、成员设置或成果详情不能叠加。

### 4.2 状态区域分工

状态必须分层显示，禁止把不同层级压缩成一个“在线”或“正在运行”：

| 状态层 | UI 所有者 | 位置 | 回答的问题 |
| --- | --- | --- | --- |
| Gateway / 电脑连接 | 全局连接状态 | 顶部导航或标题栏 | 电脑和服务能否接收操作？ |
| 当前任务 | 任务状态条 | 主画布标题下方 | 当前任务做到哪一步、是否阻塞？ |
| 待用户行动 | 待处理条 | 任务状态条下方，阻塞时置顶 | 用户现在必须做什么？ |
| 控制权 | 控制权标签 | 输入区上方或任务检查器 | 谁可以追加、暂停或审批？ |
| Agent 活动 | Agent 列表或任务步骤 | 次级区域 | 每个 Agent 正在做什么？ |

全局连接断开时，不得直接把任务显示为“失败”；任务应显示“状态待同步”。任务等待审批时，设备仍然可以显示在线，二者不得互相覆盖。

### 4.3 顶部栏

当前顶部栏同时容纳项目名、活动 Agent、设备状态、单人/群聊切换和用户身份，移动端容易拥挤。

调整为：

- P0：当前项目或任务名称；
- P0：阻塞或离线状态，仅在发生时显示；
- P1：待处理数量；
- P2：设备名称、身份、视图切换放入一个更多菜单或桌面端次级区域。

“几个 Agent 正在工作”不再占用顶部主状态，因为它可能与“任务等待审批”产生矛盾。该信息放入任务步骤或 Agent 检查器。

### 4.4 时间线

时间线继续作为中央主画布，但消息、任务事件、审批和成果必须有清晰类型：

- 对话消息：表达讨论和指令；
- 任务事件：表达开始、阶段变化、阻塞和完成；
- 审批事件：表达请求和最终决定；
- 成果事件：表达可验收产物。

禁止每次状态更新都新增一条相似聊天消息。任务卡片原位更新，关键状态变化另记审计事件。

当用户正在阅读历史时：

- 普通新消息显示“新消息”；
- 新审批显示“1 项待处理”，优先级高于“新消息”；
- 点击后跳到审批上下文，但不永久改变用户当前任务；
- 审批完成后返回原阅读位置，或提供“回到刚才位置”。

### 4.5 输入区

当前群聊输入区同时存在“商讨 / 开发”切换、Agent 下拉框、`@Agent`、右侧 Agent 选择和发送按钮，多个入口可能决定不同发送对象。

理想输入区只保留一个明确目标：

- 默认：发送到当前任务；
- 无当前任务：发送给项目经理；
- 用户主动使用 `@Agent`：显示目标标签，并覆盖默认目标；
- 需要新建任务：通过发送后的意图识别或明确“新任务”入口处理。

删除“点击右侧 Agent 自动进入开发模式”的隐式联动。选择 Agent 只查看详情；只有在输入区明确选择“交给此 Agent”后才改变发送目标。

输入框上方显示一行上下文标签，例如：

> 追加到：登录错误修复 · 当前由开发 Agent 执行

如果用户只有观察权限，输入区仍可允许普通评论，但暂停、转向和审批动作独立受权限控制。

发送按钮不得在输入为空时自动变成“停止”。停止属于高影响动作，应放在任务状态条的更多菜单或明确的“暂停任务”按钮中，避免用户把同一位置误认为发送。

### 4.6 任务卡片与任务状态条

任务卡片负责历史和摘要；任务状态条负责当前主要操作。两者引用同一任务状态，不各自维护状态。

每个真实执行任务都显示：

- 目标；
- 当前负责人；
- 当前阶段；
- 最近完成的动作；
- 下一动作；
- 是否需要用户介入；
- 开始时间和最近更新时间；
- “查看过程”和“打开任务”操作。

不建议显示不可靠的百分比。使用阶段和已完成子任务表达进展，例如“研究完成，正在修改代码，等待测试”。

对于单人 Codex Web，这些文字必须来自 Codex 已有过程事件，不得另建一套推测性的“任务阶段”。群聊未来是否需要独立任务卡片，等基础能力对齐后再定义。

任务状态条只在存在当前任务时显示，包含：任务名称、状态、责任人和一个主要动作。暂停和取消收进次级菜单，等待审批时主要动作替换为“处理审批”。

### 4.7 Agent 状态与 Agent 检查器

Agent 头像旁只使用可验证的状态：

- 空闲；
- 正在确认范围；
- 正在执行；
- 正在审查；
- 等待审批；
- 等待补充信息；
- 已暂停；
- 失败；
- 已完成；
- 离线。

“正在思考”不能长时间作为唯一状态。超过合理时间后应展示最近事件或提示连接异常。

Agent 检查器可以展示职责、当前子任务、最近事件和产物，但不得提供与任务状态条重复的暂停、审批和验收按钮。任务级操作始终回到任务 UI。

### 4.8 审批 UI

审批卡片固定包含：

- 谁发起、属于哪个任务；
- 操作类型；
- 用户可理解的目的；
- 影响范围；
- 风险等级；
- 命令、路径或网络目标；
- 有效期；
- 推荐动作及推荐原因。

按钮按风险提供：

- 允许一次；
- 本次任务允许；
- 拒绝；
- 查看详情。

只有规则足够窄且风险可控时，才出现“本次任务允许”。默认不提供永久全局允许。

审批请求出现时，同时使用两种互补表面：

- 主画布顶部显示紧凑待处理条，保证用户不会错过；
- 点击后打开审批详情页或抽屉，展示完整命令和决策按钮。

不在聊天流、右侧面板和输入区同时放置三套批准按钮。所有入口打开同一个审批对象，提交后所有引用位置同步变为只读结果。

执行授权用词固定为“允许执行 / 拒绝执行”；成果验收用词固定为“通过成果 / 要求修改”。两者不得都使用“批准”。执行授权使用风险色和盾牌语义，成果验收使用质量检查语义。

### 4.9 Windows UAC 预防与兜底

正常开发先自动改用项目级、用户级或 WSL2 等不需要管理员权限的实现，目标是根本不出现 UAC，也不让用户处理权限细节。

只有驱动、系统服务或系统安全策略等确实没有普通用户替代方案的操作，才显示：

> 此操作需要在电脑本机完成管理员确认，远程端无法安全代替。当前任务已暂停，其他任务不受影响。

此时只提供：

- 改用不需要管理员权限的方案；
- 保留任务，稍后本机或通过向日葵维护；
- 取消该步骤并让 Agent 调整方案。

如果系统无法确认弹窗类型，显示“可能需要本机操作”，不得伪装成可远程审批。

UAC 与 Codex 内部审批不得放进同一“允许一次”组件。当前不建设 UAC broker、远程 UAC 批准或自动点击能力。

### 4.10 成果卡片与成果验收

完成后不直接淹没在聊天流中。成果卡片显示：

- 完成了什么；
- 主要文件或产物；
- 验证结果；
- 未解决问题；
- 风险和影响范围；
- 谁执行、谁审查；
- 通过成果、要求修改、打开产物操作。

成果卡片可以出现在时间线中，详细预览在右侧检查器或独立页面打开。成果验收按钮只存在于成果卡片详情和对应任务状态条，不与执行审批按钮共用组件、文案或颜色。

### 4.11 浮层、抽屉和滚动规则

必须建立统一的临时表面管理器和层级规则：

1. 普通浮层：提及菜单、下拉菜单；
2. 上下文抽屉：任务、Agent、成果；
3. 行动抽屉或全屏页：审批、UAC、本机操作；
4. 阻断对话框：仅用于不可逆取消或身份设置。

高层表面打开时关闭低层表面，并正确转移键盘焦点。手机键盘打开时，审批主要动作不能被输入区或安全区遮挡。审批页的决策按钮固定在安全区上方，详情内容独立滚动。

### 4.12 UI 协同优先级

当多个事件同时出现时，按以下顺序决定主界面：

```text
安全或权限行动
  > 任务阻塞
  > 当前任务主要操作
  > 新成果验收
  > 普通新消息
  > Agent 活动更新
```

高优先级只改变状态条和待处理入口，不强制关闭用户正在编辑的文字。用户草稿必须保留；点击待处理后再进入决策界面。

### 4.13 协同布局线框

桌面端：

```text
┌─────────────────────────────────────────────────────────────┐
│ 全局栏：项目名 · 连接异常/待处理角标 · 更多菜单             │ P0/P1
├────────────┬──────────────────────────────┬─────────────────┤
│ 项目导航   │ 当前任务状态条 [一个主操作] │ 上下文检查器    │
│ 未读/待处理├──────────────────────────────┤ 任务/Agent/成果 │
│            │ 待处理条（仅在需要行动时）   │ 三者只显示一个  │
│            ├──────────────────────────────┤                 │
│            │ 时间线 [独立滚动]            │                 │
│            ├──────────────────────────────┤                 │
│            │ 发送目标标签                 │                 │
│            │ 输入区 [草稿不丢失]          │                 │
└────────────┴──────────────────────────────┴─────────────────┘
```

手机端：

```text
┌──────────────────────────────┐
│ 项目名 · 阻塞/待处理入口     │ P0 [sticky]
├──────────────────────────────┤
│ 当前任务 · 状态 · 主操作     │ P0
├──────────────────────────────┤
│ 待处理条（按需出现）         │ P0
├──────────────────────────────┤
│ 时间线                       │ [scroll]
│ 消息 / 任务 / 审批结果 / 成果│
├──────────────────────────────┤
│ 发送到：当前任务             │ P1
│ 输入区                       │ [sticky]
└──────────────────────────────┘

审批详情、任务详情和成果详情使用互斥全屏页或抽屉，不再挤入这个主结构。
```

### 4.14 关键设计决策

| 决策 | 未采用方案 | 采用方案 | 原因 |
| --- | --- | --- | --- |
| 右侧区域 | 永久同时显示 Agent 与任务面板 | 单一上下文检查器 | 避免四栏和重复操作 |
| Agent 选择 | 点击后自动改变输入模式 | 只切换详情，发送目标需明确选择 | 消除隐式状态变化 |
| 停止任务 | 复用发送按钮 | 独立暂停入口 | 避免同位置动作语义变化 |
| 审批呈现 | 聊天流内直接堆多个按钮 | 待处理条加唯一详情页 | 保证可发现且只有一个决策源 |
| 新消息与审批 | 共用“新消息”提示 | 待处理优先，普通消息次级 | 安全行动不能被聊天淹没 |
| 执行授权与成果验收 | 都使用“批准” | “允许执行”与“通过成果” | 避免用户误判操作对象 |
| 手机端详情 | 多个底部浮层叠加 | 单一全屏页或互斥抽屉 | 解决键盘、安全区和短屏冲突 |

### 4.15 视觉、层级与无障碍约束

- 全局连接、任务状态、待处理和成果验收必须使用不同图标和文字，颜色不能作为唯一差异。
- 执行审批使用 `--color-access` 或专门风险令牌；成果通过使用 `--color-success`。应新增危险、警告和浮层层级令牌，避免继续在组件 CSS 中各自写颜色和 `z-index`。
- 主操作按钮在同一屏幕模式中只能有一个高强调样式；审批二选一状态除外。
- 手机点击区域建议不小于 44×44 CSS 像素；Web 最低满足 WCAG 2.2 目标尺寸和间距要求。
- 打开审批页时焦点进入标题；关闭后返回触发入口。状态变化通过文字和辅助技术播报。
- 200% 字体缩放时，待处理原因和主要动作不得被截断；允许内容滚动，但主操作必须可达。
- 动画只用于说明抽屉打开、状态确认和重连恢复，时间使用现有 `--duration-fast` 或短时过渡；减少动态效果设置下关闭非必要动画。
- 手机输入法打开时，输入区遵循安全区；高优先级待处理条不得覆盖文本光标或发送按钮。

## 五、核心交互逻辑

### 5.1 进入项目

用户进入页面后，顶部首先显示连接状态：

- 电脑在线，可执行；
- 电脑在线，服务正在恢复；
- 电脑离线，只能查看；
- 权限不足。

如果正在恢复任务，显示“正在恢复 1 个任务”，而不是让用户误以为任务已经停止。

### 5.2 发起任务

用户发送目标后，界面立即生成任务卡片并显示“已接收，正在确认范围”。

理想反馈时限：

- 300 毫秒内显示本地已发送状态；
- 3 秒内显示服务端已接收或明确失败；
- 不允许因为发送超时自动重复提交。

### 5.3 澄清与拆解

项目经理 Agent 只询问会明显改变结果的问题。非关键缺失信息使用明确假设继续，并把假设展示在任务卡片中。

拆解完成后显示精简执行计划：

- 子任务；
- 负责人；
- 依赖；
- 哪些动作可能需要用户审批。

用户可以“开始执行”或直接补充限制。对于低风险、用户已经明确授权的任务，可以自动开始，但需要在卡片上说明。

### 5.4 执行与介入

执行过程中，时间线只展示对用户有意义的里程碑：开始、产生方案、修改文件、验证、阻塞、审批、失败和完成。

用户发送新指令时：

- 同一目标的小调整直接作为“追加指令”；
- 会推翻已有工作的调整，提示“这会改变当前计划”；
- 无关目标建议新建任务，但不强迫用户重新输入。

### 5.5 审批

出现 Codex 内部审批时：

1. 当前任务变为“需要你处理”。
2. 手机和 Web 收到包含任务名称和风险等级的通知。
3. 点击通知直达审批卡片。
4. 系统保留输入草稿，关闭提及菜单等低层浮层，打开唯一审批详情页。
5. 用户查看影响并选择允许一次、本次任务允许或拒绝。
6. 按钮点击后立即锁定，显示“正在提交决定”。
7. 服务端确认后显示审批结果和执行恢复状态。
8. 关闭审批页后恢复原滚动位置和输入草稿。
9. 网络超时时不自动重复提交允许决定；系统先查询审批状态。

### 5.6 暂停、取消和恢复

- “暂停”保留任务上下文和已完成成果，可以继续。
- “取消”终止当前运行，但不删除历史和产物。
- “重新执行”必须说明从头开始还是从失败步骤继续。
- 用户刷新或切换设备后，系统恢复到服务端确认状态。
- 暂停或取消不复用发送按钮；操作前后输入框内容保持不变。

### 5.7 完成与验收

项目经理 Agent 汇总专业 Agent 的结果，形成成果卡片。用户选择：

- 通过成果；
- 要求修改；
- 新建后续任务。

“要求修改”默认关联原任务、原成果和审查意见，不创建失去上下文的新对话。

### 5.8 跨 UI 切换

- 从任务切到 Agent 检查器：不改变当前任务、不改变输入目标。
- Web 打开单人任务时：如果可靠检测到 Codex Desktop 正在同一任务执行，显示明确提示并避免直接重复发起；暂不要求 Desktop 反向提示 Web。
- 从群聊切到单人会话：不假设两者是同一运行实例；群聊特有映射在基础能力对齐后再定义。
- 从历史消息打开成果：成果详情覆盖右侧检查器，但关闭后恢复原上下文。
- 审批到达时：只提升待处理条，不强行抢走输入焦点；用户主动点击后才进入审批页。
- 连接断开时：全局状态改变，任务状态进入“待同步”，Agent 状态不擅自改成失败。

## 六、统一状态模型

```text
draft
  -> scoping
  -> ready
  -> running
  -> waiting_user_input
  -> waiting_approval
  -> waiting_local_action
  -> reviewing
  -> completed

任意执行状态
  -> paused
  -> failed
  -> cancelled

paused / failed
  -> running（恢复或重试）
```

要求：服务端状态是唯一事实来源；前端可以显示临时反馈，但重连后必须以服务端状态校正。

## 七、端到端核心测试用例

### 用例编号

`UX-E2E-001`

### 用例名称

用户在手机远程发起开发任务，处理中完成审批、追加指令、断线恢复和成果验收

### 测试目标

验证核心链路是否真正支持“离开电脑仍可监督和控制任务”，并确认 Codex 内部审批不会让整个远程产品失效。

### 参与角色

- 用户 A：手机端主要操作者；
- 用户 B：Web 端观察者；
- 项目经理 Agent：澄清、分派和汇总；
- 开发 Agent：真实执行；
- 审查 Agent：检查修改和证据；
- Windows 执行节点：运行 Codex app-server。

### 前置条件

1. 用户 A 和用户 B 已进入同一项目空间。
2. Windows 执行节点在线，Codex app-server 可用。
3. 两名用户拥有查看权限，用户 A 拥有任务审批权限。
4. 准备一个会触发安全命令审批、但不需要真实 UAC 的测试命令。
5. 网络测试工具可以模拟手机短暂断网。
6. 项目中存在一个可安全修改并可运行测试的样例文件。

### 主流程与预期效果

| 步骤 | 用户或系统操作 | 理想交互与预期结果 | 验收重点 |
| --- | --- | --- | --- |
| 1 | 用户 A 用手机进入项目群 | 顶部显示“电脑在线，可执行”；正在运行和待处理数量可见 | 5 秒内确认真实连接状态 |
| 2 | 用户 A 输入“修复样例页面中的登录错误，并运行测试” | 消息立即显示发送状态，同时创建独立任务卡片 | 不依赖 Agent 回复才表示已接收 |
| 3 | 项目经理 Agent 判断目标基本明确 | 卡片进入“确认范围”，展示必要假设，不提出无关问题 | 用户阅读负担低 |
| 4 | 系统展示执行计划 | 显示开发、测试、审查三个阶段及负责人，并标记可能需要审批 | 用户知道接下来会发生什么 |
| 5 | 开发 Agent 开始工作 | 卡片显示“正在执行”，时间线出现开始事件；原始日志默认折叠 | 状态真实，不用虚假百分比 |
| 6 | 用户 B 从 Web 进入同一项目 | 看到相同任务、负责人和阶段，并显示“用户 A 当前拥有控制权” | 多端状态一致、责任清晰 |
| 7 | 用户 A 追加“不要改动登录页面布局” | 输入被标记为当前任务的追加限制；Agent 收到后卡片显示“限制已更新” | 新指令不丢失、不新建错误任务 |
| 8 | 开发 Agent 请求执行待审批命令 | 任务状态条主操作变为“处理审批”；待处理条置顶；输入草稿保留；其他页面仍可使用 | 审批不遮挡输入、不复制按钮 |
| 9 | 用户 A 打开审批详情 | 关闭低层浮层并显示目的、命令、目录、影响、风险和有效期；时间线位置不丢失 | 同时只存在一个审批决策界面 |
| 10 | 用户 A 点击“允许一次” | 按钮锁定并显示提交中；服务端确认后显示“已允许，任务已恢复” | 不重复审批，结果可追溯 |
| 11 | 审批提交后手机断网 20 秒 | 页面显示离线但保留最后状态，不重新发送允许决定或任务指令 | 无重复命令、无状态倒退 |
| 12 | 网络恢复 | 自动重连并从服务端恢复；显示断线期间发生的关键事件 | 不要求用户刷新或重新输入 |
| 13 | 开发 Agent 完成，审查 Agent 发现一个问题 | 任务进入“正在审查”，显示问题摘要并自动回到开发修正 | 用户知道任务未完成的原因 |
| 14 | 所有验证通过 | 项目经理生成成果卡片，列出修改文件、测试证据、限制和风险 | 成果与过程、证据关联 |
| 15 | 用户 A 点击“通过成果” | 任务进入“已完成”；保留参与者、执行授权、审查和成果记录 | 不与“允许执行”混淆 |

### 通过标准

必须全部满足：

1. 任意时刻都能明确看到当前状态和下一责任人。
2. 手机可以完成 Codex 内部审批，不需要回到电脑。
3. 审批期间其他功能仍可使用。
4. 网络断开和恢复不会重复发送任务、追加指令或审批。
5. 用户 B 不会误以为自己拥有审批权。
6. 最终成果包含可打开的产物和可核查的验证证据。
7. 所有关键动作都有时间、操作者和结果记录。
8. 用户不需要查看底层日志即可完成整个任务。
9. 选择 Agent、打开成果或切换面板不会暗中改变输入目标。
10. 同一时刻只有一个主要操作和一个审批决策界面。
11. 执行授权和成果验收的文案、颜色和图标不会混淆。
12. 审批到达、断线和恢复都不会清空用户草稿或抢走输入焦点。

## 八、关键异常测试用例

### `UX-AP-001` 审批被拒绝

操作：用户点击“拒绝”。

预期：任务显示“审批已拒绝”，Agent 尝试安全替代方案；没有替代方案时进入可解释的失败状态，而不是继续等待。

### `UX-AP-002` 审批过期

操作：用户在有效期内没有处理。

预期：请求自动过期并安全拒绝；任务显示下一步，可重新发起新审批，但不能复用旧 ID。

### `UX-AP-003` 两端同时审批

操作：手机和 Web 几乎同时提交不同决定。

预期：第一个有效决定成功；另一端收到“该请求已由用户 A 处理”，不能覆盖结果。

### `UX-AP-004` 审批提交超时

操作：用户点击允许后网络中断。

预期：客户端先查询服务端状态；不能自动重复发送允许决定。

### `UX-UAC-001` 遇到真实 Windows UAC

操作：测试步骤触发真实系统提权。

预期：远程端明确显示“需要本机操作”，不提供虚假批准按钮；当前任务暂停，其他任务和查看功能继续可用。

### `UX-REC-001` 服务重启恢复

操作：任务执行中重启 Gateway 服务。

预期：恢复后显示最后确认事件和当前真实状态；未确认执行不得显示为成功。

### `UX-CTRL-001` 控制权冲突

操作：用户 A 正在控制任务，用户 B 尝试暂停。

预期：系统显示当前控制者和权限；有权限时记录控制权变更，无权限时明确拒绝。

### `UX-RESULT-001` 任务完成但验证失败

操作：代码修改完成，但测试失败。

预期：不得显示“已完成”；状态进入“验证失败”，成果卡片区分已完成修改和未通过验证。

### `UX-UI-001` 点击 Agent 不改变输入目标

操作：输入框目标为“当前任务”，用户点击右侧审查 Agent。

预期：右侧显示审查 Agent 详情，输入框仍显示“发送到当前任务”；只有用户明确选择“交给审查 Agent”后目标才改变。

### `UX-UI-002` 输入提及过程中到达审批

操作：用户正在输入 `@开发 Agent`，提及菜单打开时产生审批。

预期：待处理条出现但不抢焦点，草稿和提及位置保留；用户点击待处理后提及菜单关闭，审批结束后草稿恢复。

### `UX-UI-003` 新消息与审批同时到达

操作：普通群消息和高风险审批几乎同时到达。

预期：界面主提示为“1 项待处理”，普通消息计入次级未读；处理审批后仍能返回新消息位置。

### `UX-UI-004` 等待审批时连接断开

操作：审批尚未处理时 Gateway 连接断开。

预期：顶部显示连接异常，任务仍显示“等待审批，状态待同步”；不能显示为失败，也不能允许提交决定，恢复连接后重新校验审批是否有效。

### `UX-UI-005` 执行审批与成果验收同时存在

操作：任务 A 等待“允许执行”，任务 B 等待成果验收。

预期：待处理中心分别显示“执行授权”和“成果验收”；按钮分别为“允许执行”和“通过成果”，图标和颜色不同。

### `UX-UI-006` 手机键盘与审批详情

操作：手机键盘打开时用户进入审批详情。

预期：输入草稿保存，键盘正确收起，审批内容可滚动，决策按钮位于安全区上方；关闭后键盘不自动弹出，用户点击输入框后继续编辑。

## 九、体验指标

建议用以下指标判断是否达到理想效果：

- 用户操作后 300 毫秒内出现本地反馈；
- 3 秒内确认任务是否被服务端接收；
- 审批产生后 5 秒内到达在线远端；
- 断线恢复后 10 秒内完成状态校正；
- 任务等待超过 30 秒时，必须显示原因和责任人；
- 任何审批、取消和重试都不得重复执行；
- 一个核心任务最多保留一个主任务卡片，不因状态变化反复新增聊天消息；
- 正常开发不需要打开原始日志或返回电脑端；项目入口完全离线或确需系统级维护时允许使用向日葵兜底。
- 任何操作入口不得因为另一个面板的选择而隐式改变语义；
- 手机端临时表面同时打开数量为 1；
- 执行授权和成果验收在 5 秒识别测试中不得被用户混淆。

这些数值是产品验收目标，实施时可根据真实网络和运行环境调整，但不能取消“明确反馈、可恢复、不重复”的原则。

## 十、当前版本与理想效果的主要差距

| 能力 | 当前状态 | 理想状态 |
| --- | --- | --- |
| 任务表达 | 以聊天和执行状态为主 | 持久任务卡片与完整生命周期 |
| 等待审批 | 仅提示回电脑确认 | 远程审批卡片、通知、超时和审计 |
| 控制权 | 多入口状态不够明确 | 显示当前操作者、权限和控制权变更 |
| 断线恢复 | 已有部分实时与重连逻辑 | 服务端状态校正且绝不重复提交 |
| 多 Agent | 展示成员和执行状态 | 子任务、依赖、审查和责任关系 |
| 完成结果 | 主要表现为回复和附件 | 成果卡片、验证证据和验收动作 |
| Windows UAC | 一旦出现会使普通远程流程停止 | 用户级工具链使正常开发不出现 UAC；真正系统级维护使用本机或向日葵兜底 |
| 状态所有权 | 设备、执行和 Agent 状态分散显示 | 分层状态且由统一数据源驱动 |
| 输入目标 | 模式切换、Agent 选择和 `@` 可能竞争 | 单一目标标签，改变目标必须显式操作 |
| 停止操作 | 发送按钮可能根据输入状态变为停止 | 独立暂停入口，发送按钮语义固定 |
| 审批与验收 | 都可能使用“批准” | “允许执行”与“通过成果”分离 |
| 面板协同 | 左右面板和时间线可能重复状态与操作 | 单一上下文检查器和任务操作所有者 |
| 浮层层级 | 组件分别维护弹层与 `z-index` | 统一临时表面管理和焦点恢复 |

## 十一、建议实施顺序

1. 先修复单人 Codex Web 执行 1–2 分钟后过程停止更新的问题，保证事件持续到达并能自动补齐。
2. Web 增加“Desktop 正在同一任务工作”的单向提示，不先改 Desktop。
3. 群聊基础能力逐项与单人 Codex 对齐，再定义群聊特有的分工、讨论和审查功能。
4. 验证普通用户权限下的修改、依赖、测试、构建、Git 和必要重启，减少 Codex 内部审批并避免 UAC。
5. 研究最小项目启动入口；无法独立存活时明确使用向日葵兜底。
6. 再根据真实需要处理成果验收、多人权限和 Codex 内部远程审批；不建设 UAC broker。

在 `UX-E2E-001` 能稳定通过之前，不建议把主要精力用于增加更多 Agent 角色、复杂动画或大范围视觉重做。

### 11.1 现有组件调整边界

| 当前组件 | 调整后的职责 | 必须避免 |
| --- | --- | --- |
| `GroupHeader` | 项目身份、异常和待处理入口 | 同时展示设备、Agent 活动、身份和全部导航 |
| `DeviceStatus` | 只表达 Gateway / 电脑连接 | 推断任务成功、失败或审批状态 |
| `ExecutionStatus` | 演化为当前任务状态条 | 与 Agent 列表各自显示不同任务结论 |
| `MessageTimeline` | 统一渲染消息与类型化事件 | 为每次状态变化新增重复消息 |
| `JumpToLatest` | 区分普通新消息与高优先级待处理 | 用“新消息”掩盖审批 |
| `GroupComposer` | 固定发送语义和明确目标标签 | 模式、下拉框、`@` 和 Agent 面板同时决定目标 |
| `AgentRoster` | 选择检查对象 | 点击后自动切换发送或开发模式 |
| `ArtifactReviewActions` | “通过成果 / 要求修改” | 使用执行授权的“批准”语义 |
| 新增 `PendingActionBar` | 汇总当前需要用户处理的行动 | 在多个区域复制完整按钮 |
| 新增 `ContextInspector` | 互斥展示任务、Agent、成果详情 | 永久增加第四栏 |
| 新增 `SurfaceManager` | 管理抽屉、审批页、焦点和层级 | 组件各自任意设置 `z-index` |

### 11.2 UI 评审停止条件

出现以下任一情况时，设计不得进入代码实现：

- 无法明确某个状态由哪个组件负责；
- 同一屏幕存在两个竞争的主要操作；
- 点选一个只读对象会暗中改变执行目标；
- 移动端需要同时打开两个抽屉或浮层才能完成操作；
- 关闭审批后不能恢复草稿、滚动位置或焦点；
- 连接状态变化会把任务错误标记为失败；
- 执行授权和成果验收仍使用相同文案或视觉语义。
