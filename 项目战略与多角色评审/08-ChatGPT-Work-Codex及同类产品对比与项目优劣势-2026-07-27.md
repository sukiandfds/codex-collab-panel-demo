# ChatGPT Work、Codex 及同类产品对比与项目优劣势

> 调研日期：2026-07-27  
> 项目：Codex Collab Panel  
> 文档性质：当前竞品更新、产品定位与差异化判断  
> 研究边界：本报告不修改项目功能，不把市场宣传直接等同于经过独立验收的能力。

## 一、执行摘要

ChatGPT Work 是 OpenAI 在 ChatGPT 中提供的通用工作智能体，目标是把文件、应用和业务上下文转化为文档、表格、幻灯片、研究报告、网站等可交付成果。Codex 是软件工程智能体，重点是代码仓库、终端、Git、测试、审批和真实文件修改。

两者的根本区别是：

```text
ChatGPT Work：完成一个跨应用的知识工作成果
Codex：完成一个软件工程任务
Codex Collab Panel：组织多名真人和多个执行 Agent 共同推进一个项目
```

本项目不可能在模型、通用连接器、办公成品生成、代码执行深度或消费级体验上正面超过 OpenAI、Anthropic、字节、腾讯、Cursor 等平台。项目当前真正有价值的组合是：

> 多名真人进入同一个项目群，实时观看、点名、指挥、打断和审查多个真实 Codex Agent；项目经理 Agent 负责分派与汇总，完整过程可以被追溯。

如果项目继续被定义为“网页版 Codex”“手机控制 Codex”或“群里放几个 Agent”，差异化不足。下一阶段需要证明的不是更多页面，而是一条稳定的多人监督真实 Agent 团队的闭环。

## 三、ChatGPT、ChatGPT Work 与 Codex

| 维度 | 普通 ChatGPT | ChatGPT Work | Codex |
| --- | --- | --- | --- |
| 核心目的 | 回答、解释、创作和即时协助 | 推进多步骤知识工作并交付成品 | 在真实软件工程环境中执行任务 |
| 典型用户 | 所有个人用户 | 运营、销售、财务、研究、市场、管理人员 | 开发者和技术团队 |
| 主要输入 | 当前对话、上传内容 | 文件、应用、浏览器、工作区和企业上下文 | 代码仓库、项目规则、终端和开发工具 |
| 主要输出 | 文本、图像和即时回答 | 文档、表格、幻灯片、报告、网站等成果 | 代码、Diff、测试、命令结果和提交 |
| 任务长度 | 通常较短 | 长时间、多步骤、可持续推进 | 中长时间的工程 Turn 和任务 |
| 过程展示 | 以回答为主 | 计划、进度、提问和关键确认 | 文件修改、命令、工具活动、审批和结果 |
| 专业边界 | 通用 | 通用知识工作 | 软件开发与工程执行 |
| 多 Agent | 不是主要用户概念 | 可以组合多种能力，但公开 Agent 群不是核心 | 支持子 Agent、并行任务和隔离执行 |
| 多真人协作 | 通过分享和工作区实现 | 依赖 ChatGPT 工作区和组织能力 | 不提供完整项目群聊模型 |

### ChatGPT Work 的核心价值

1. 用户给出目标，而不是逐步手工提示每一个动作。
2. Agent 可以从连接的文件和应用收集上下文。
3. 任务被拆成多个步骤并持续执行。
4. 输出目标是可使用的业务成果，而不仅是解释性回答。
5. 用户可以查看进度、补充信息并在关键外部操作前确认。
6. 长期和定时任务使产品从“聊天”转向“持续工作”。

### Codex 的核心价值

1. 深度理解真实代码仓库和项目规则。
2. 可以修改文件、运行终端、执行测试和处理 Git 工作流。
3. 支持审批、沙箱、工具调用和增量过程展示。
4. Thread、Turn 和 Item 适合表达一个执行型工程会话。
5. 子 Agent、并行执行和隔离工作区适合拆分复杂工程任务。

### 二者的关系

ChatGPT Work 可以吸收 Codex 的智能体执行思想，但它不会向普通用户暴露大量代码和终端细节。Codex 也可以处理非代码文件，但它的产品中心仍然是工程环境。不能因为二者使用同一模型家族或共享部分智能体基础设施，就把它们当成同一产品。

## 四、同类产品全景

### 4.1 通用工作智能体

| 产品 | 主要能力 | 优势 | 局限 | 对本项目威胁 |
| --- | --- | --- | --- | --- |
| ChatGPT Work | 跨文件和应用完成研究、文档、表格、幻灯片和网站 | OpenAI 模型、生态、分发、企业能力和多端入口 | 不是以公开多人 Agent 项目群为核心 | 极高 |
| Claude Cowork | 使用 Claude Code 的智能体架构处理非代码知识工作，支持长任务、文件和跨端使用 | 文档理解、写作质量、任务连续性和简洁体验 | 多 Agent 组织和多人项目监督不是核心 | 高 |
| Manus | 云端浏览器、研究、数据处理、建站和成果交付 | 自主执行感强、云端环境完整、面向普通用户 | 本地私有代码、多人治理和过程透明度有限 | 高 |
| Genspark | AI Workspace、研究、文档、表格、幻灯片及后台多 Agent 协作 | 成品类型丰富，演示效果和任务覆盖广 | 后台 Agent 组织较黑盒，不是项目成员共同监督 | 高 |
| TRAE Work | Work/Code 双模式，连接知识工作和软件开发，多端协同 | 与本项目“办公+开发”扩张方向重合 | 新产品的稳定性、权限和长期治理仍需验证 | 极高 |
| WorkBuddy | 多专家、多模型、桌面和即时通信入口，服务中文办公任务 | 中文市场、本地办公场景和专家组合清晰 | 真实代码执行、过程证据和项目群治理仍需观察 | 高 |

共同趋势是：通用助手正在从“给答案”升级为“访问上下文、持续执行、交付成品”。因此，单纯增加文件上传、长任务或多个专家角色，不足以构成项目壁垒。

### 4.2 软件工程智能体

| 产品 | 主要能力 | 优势 | 局限 | 对本项目威胁 |
| --- | --- | --- | --- | --- |
| OpenAI Codex | 本地/云端代码执行、终端、测试、审批、子 Agent | 模型和工程闭环强，是当前项目的执行基础 | 不是多人项目群 | 极高，但也可作为底层 |
| Cursor | IDE 内多 Agent、并行方案、代码审查和云端执行 | 开发者工作流成熟、交互效率高 | 主要面向工程师，不管理真人和 Agent 组织 | 高 |
| Devin | 云端软件工程任务、计划、实现和 PR 交付 | 长任务和团队工程流程成熟 | 成本、云端环境和过程控制边界 | 高 |
| GitHub Copilot Agent | 从 Issue 到分支、代码修改和 PR | 天然连接代码、权限、CI 和审查 | 工作单位是 Issue/PR，不是群聊和组织讨论 | 高 |
| OpenHands | 开源软件工程 Agent、沙箱执行和可自托管运行时 | 开源、可扩展、可替换模型和运行环境 | 完整多人项目协作体验需另建 | 中高，可作为底层参考 |

这些产品意味着：本项目不应自行重做代码编辑器、终端、Git 平台或通用编码 Agent。应复用 Codex/OpenHands 等执行能力，把精力集中到多人组织和监督层。

### 4.3 Agent 工作空间与远程控制

| 产品 | 主要能力 | 优势 | 局限 | 对本项目威胁 |
| --- | --- | --- | --- | --- |
| OpenAgents Agent IDE | 持久会话、Agent/子 Agent 拓扑、停止、引导、审批、历史、恢复和证据 | 与“可监督 Agent 工作环境”高度接近，边界清晰 | 当前仍偏单一操作者的 Agent IDE；多人参与仍强调未来授权 | 极高 |
| Happy | 手机/Web 控制本地 Codex 和 Claude Code、加密同步、通知和设备切换 | 单人跨设备体验成熟，开源且目标明确 | 不解决项目成员、Agent 组织和群聊治理 | 对本项目单人功能极高 |
| OpenAgents Workspace 类产品 | 频道、线程、文件、成员和 Agent 共同存在 | 最接近人类与 Agent 共处的工作空间 | 真实工程执行、审查和组织决策仍需外部能力 | 高 |
| Slack/飞书 + Agent | 成熟群聊、成员、权限、通知、文档和企业连接 | 企业分发和组织能力极强 | 深层 Agent 执行依赖第三方系统 | 极高 |

如果本项目只是“让手机看到 Codex”，Happy 已经是更成熟的替代。如果只是“群里加几个 Agent”，飞书、Slack 和企业 Agent 平台很容易复制。

### 4.4 多 Agent 框架

| 产品 | 适合解决的问题 | 不适合直接解决的问题 |
| --- | --- | --- |
| CrewAI | 角色、任务、Crews、Flows、状态和生产工作流 | 多人实时协作产品和完整前端体验 |
| AutoGen | Agent 对话、编排、实验和开发者原型 | 直接作为稳定企业群聊产品 |
| MetaGPT | 按软件公司角色和 SOP 生成软件项目 | 真实多人长期协作、权限和跨设备交接 |
| OpenClaw | 常驻 Agent、渠道、身份、记忆、工具和监督 | 成熟的多人项目治理和天然无污染记忆 |
| Harness | CI/CD、验证、审批、治理和失败恢复 | Agent 群聊和通用知识工作入口 |

这些框架适合借鉴或局部复用，但不能代替产品层的成员、权限、消息、任务、状态、证据和人工控制设计。

## 五、本项目当前真实能力

### 已实现、等待持续体验确认

1. 浏览器读取真实 Codex/Happy 会话、选择对话、加载历史和发送指令。
2. Web 任务使用 Codex app-server，运行中可追加引导和停止。
3. SSE 增量回复、中文状态、执行活动、断线补偿和上下文管理。
4. 真实项目群、持久化群消息和四个 Codex Agent：项目经理、研究、开发、审查。
5. 支持讨论/开发模式，以及 `@` 一个或多个 Agent。
6. Agent 使用有限群聊上下文进行有限轮次讨论。
7. 支持 Markdown、代码、表格、图片、音频、视频和普通文件。
8. PWA、设备名称、手机在线状态、手机/iPad 布局以及单人/群聊切换。

### 尚未完成

1. 正式用户账号、成员邀请、角色权限和操作审计。
2. 可恢复的持久任务队列、失败重试和冲突仲裁。
3. Desktop/Web 的统一运行实例、控制权和事件恢复协议。
4. 稳定公网域名、正式登录、系统服务和开机自动恢复。
5. 邮件、日历、CRM、Drive、Slack、飞书等业务连接器。
6. 文档、表格、幻灯片等成品的完整编辑和协同环境。
7. 系统通知、可靠后台任务和定时任务。
8. 对多 Agent 讨论质量、Token 成本和真实收益的稳定评估。

## 六、本项目相对优势

### 6.1 多真人和多 Agent 共处

现有主流产品多数仍围绕“一名操作者控制一个 Agent 或一个 Agent 团队”。本项目允许用户、朋友、项目经理 Agent 和专业 Agent 共同存在于同一个项目群。

### 6.2 过程公开而且可干预

用户可以看到任务被分给谁、Agent 提出什么意见、何时开始执行、项目经理如何汇总，并能随时补充、改变或停止任务。这比完全后台化的多 Agent 编排更适合需要人工判断的工作。

### 6.3 连接真实 Codex 执行

群聊不是纯角色扮演。Agent 可以通过真实 Codex Thread 执行任务，项目有机会把对话、代码修改、工具活动和结果证据关联起来。

### 6.4 本地优先和可控部署

代码、工具和敏感项目环境可以保留在用户电脑，由 Web/PWA 提供远程入口。与纯云端 Agent 相比，这有利于私有项目和个人开发者。

### 6.5 可形成项目级组织记忆

如果把群聊、任务、Agent 状态、审查、失败和最终成果建立稳定关系，项目可以形成超过单一聊天摘要的长期记忆。

## 七、本项目相对劣势

### 7.1 产品成熟度差距很大

ChatGPT Work、Cowork、Manus、Happy、Cursor 等在实时性、恢复、跨端、通知、错误处理和用户体验上都有更成熟的投入。本项目目前仍是功能 Demo。

### 7.2 单人 Codex Web 缺少独立壁垒

远程查看和控制 Codex 很有使用价值，但 Happy 和官方产品可以更直接地覆盖。继续投入大量资源逐像素复刻 Codex，无法形成长期优势。

### 7.3 多 Agent 仍是有限调度

当前四个 Agent、有限轮次和共享上下文证明了功能可行，但还不能证明 Agent 真的通过讨论提高质量。缺少独立判断、证据、审查、冲突解决和结果评分时，多 Agent 容易变成昂贵的轮流发言。

### 7.4 正式多人协作基础缺失

没有账号、权限、审批、控制权、审计和可靠队列时，产品不能安全承载真实团队工作。群聊外观不能替代协作系统。

### 7.5 通用工作成品和连接器不足

ChatGPT Work 的核心是把多来源上下文变成成品。本项目目前更擅长展示对话和 Agent 过程，还没有成熟的工作成果编辑、连接器和业务自动化能力。

### 7.6 Desktop/Web 连续性未解决

同一 Codex Thread 不等于同一运行实例。Desktop 已打开页面不能热刷新 Web 消息，缺少统一 Connector 和控制权时容易造成用户不确定当前由哪个入口控制任务。

## 八、容易被竞品吞噬的功能

以下能力适合作为必要基础，但不能作为产品定位：

- 手机查看 Codex 对话。
- 网页发送 Codex 指令。
- 文件和图片上传。
- Agent 在线状态和思考动画。
- 在群聊中 `@` 一个机器人。
- 多个角色使用不同系统提示词。
- 自动生成对话摘要。
- 普通定时任务和通知。
- 通用文档、表格或幻灯片生成。

这些能力分别会被 Happy、ChatGPT Work、飞书、Slack、Cursor 和其他 Agent 平台覆盖。

## 九、可能成立的差异化定位

推荐定位：

> 面向小团队和个人创业者的真人与 Agent 项目协作房间：用户共同监督一支真实执行的 Agent 团队，随时介入任务，并保留可追溯的决策和工作记录。

这个定位包含五个不可缺少的部分：

1. 多名真人进入同一个项目空间。
2. 项目经理 Agent 负责澄清、分派、跟进和汇总。
3. 专业 Agent 有真实工具、职责、上下文和执行 Thread。
4. 用户能看到状态、过程、结果、阻塞和审查意见。
5. 用户最新指令拥有最高优先级，可以暂停、引导或否决。

项目不应把“AI 公司”解释为堆叠大量 Agent 头像，而应把它落实成可监督、可恢复、可审计的工作关系。

## 十、下一核心 Demo 建议

下一核心 Demo 应只证明一条链路：

```text
用户 A 和用户 B 进入同一个项目群
  -> 向项目经理 Agent 提出真实目标
  -> 项目经理澄清并分派研究、开发、审查任务
  -> 三个 Agent 在群内给出意见和状态
  -> Agent 在独立真实 Thread 中执行
  -> 两名用户可以随时插入、引导或停止
  -> 项目经理汇总成果、问题和待决定事项
  -> 系统保留任务、过程、结果和审查记录
```

必须优先解决：

1. 持久任务与 Agent 状态，而不是只在内存排队。
2. 明确的运行、等待、阻塞、失败、完成状态。
3. 用户插入、`turn/steer`、停止、重试和审批。
4. 两名真人的身份、基本权限和控制权提示。
5. Agent 结果、附件、代码或产物与群消息的关联。
6. 稳定的跨端实时事件和断线恢复。

暂不优先：

- 增加更多 Agent 职位。
- 重新设计整套 UI。
- 重做在线 IDE。
- 大量企业连接器。
- 完整 CRM、Jira 或文件管理系统。
- 无限自主讨论。
- 多个团队 PK 或大规模平行方案。

## 十一、商业与投资判断

### 当前状态

当前项目具备真实功能雏形和清晰的探索价值，但尚未形成可证明的产品壁垒，也不应把 Demo 描述为成熟多人 Agent 平台。

### 有价值的部分

- 多名真人共同监督真实 Agent 团队的体验仍未被主流产品完整占据。
- 小团队和个人创业者确实需要在离开电脑时观察和控制本地执行 Agent。
- 当 Agent 数量增加后，任务归属、过程透明、人工干预和项目记忆会成为真实问题。

### 投资人最可能质疑的问题

1. 为什么不用 ChatGPT Work、飞书 Agent 或 Slack？
2. 为什么不用 Happy 远程控制 Codex？
3. 为什么不用 OpenAgents、Cursor 或现有多 Agent 框架？
4. 多 Agent 讨论是否真的提高结果，而不是增加 Token？
5. 多人共同控制 Agent 时如何处理权限和冲突？
6. 项目如何在 OpenAI 官方产品快速扩张时保持独立价值？

### 应当用 Demo 回答的问题

不是展示更多功能列表，而是让投资人亲眼看到：两个真人如何在一个项目群中监督项目经理和专业 Agent 完成真实任务，并且任何人都能理解当前状态、介入方向、查看证据和追溯责任。

## 十二、最终判断

ChatGPT Work 把 AI 从聊天工具推进到通用工作执行者；Codex 把 AI 变成软件工程执行者；OpenAgents 正在建设可监督的 Agent IDE；Happy 已经解决单人跨设备控制。

本项目若要继续成立，不能与这些产品分别竞争它们最强的部分。它应成为它们上方的协作和监督层：

> 不负责制造更强的模型，而是让一群真人能够共同、清楚、安全地管理一支真实工作的 Agent 团队。
