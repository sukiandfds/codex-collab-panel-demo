# Codex Collab Panel：项目风险、目标偏移与批判性评审

更新日期：2026-07-22

评审负责人：Codex

身份与职责：AI 项目负责人，统一协调产品、技术、兼容、质量、安全和市场意见，并负责主动指出目标偏移、伪进展、交付风险和未经验证的假设。

本文用途：只记录项目风险和批判性意见。产品目标、理想功能、适用场景和竞争定位以同目录的 `01-产品目标、理想功能、适用场景与竞品优势-2026-07-22.md` 为准。

## 本文件的作用

本文件用于持续检查项目是否朝真实目标前进，而不是只记录完成了多少界面和代码。

评审立场：优先挑出目标偏移、伪进展、安全风险、不可交付点和未经验证的假设。提出问题时必须同时给出可验证的下一步，避免只有批评没有行动。

评审范围同时参考：

- `main`：当前公开默认分支和本地总结面板原型。
- `origin/codex/publish-current-panel`：截至 2026-07-22 尚未合并的结构化网页会话 UI。

## 一、项目目标

### 1. 长期目标

让 Codex 从个人代码助手变成围绕真实项目工作的共享研发空间。团队成员能够理解：

- 谁正在做什么。
- Agent 当前处于什么状态。
- 项目形成了哪些结论、风险和待确认事项。
- 哪些信息可以共享，哪些必须留在本机。

长期目标不是单纯做一个聊天软件，也不是做 Codex 换肤工具，而是把 Agent 的隐性工作过程转化为团队可观察、可讨论、可追踪的项目状态。

### 2. 当前阶段目标

当前首先要完成一个稳定、有独立价值的本地项目控制台：

- 自动识别当前项目和任务。
- 准确展示目标、进度、结论、风险和待确认事项。
- 不展示内部推理，不泄露密钥或无关会话。
- 安装、启动、停止和恢复过程足够稳定，普通用户不需要手工填写任务 ID 或修改作者路径。

### 3. 第一个跨电脑证明

用户 A 使用 Codex 工作时，用户 B 在另一台电脑上能看到：

- A 是否正在工作。
- A 当前大概在做什么。
- Agent 所处阶段。
- 最近更新时间。

第一版只共享经过筛选的项目状态，不共享完整原始对话、文件内容、API Key、内部推理，也不提供未经确认的远程控制。

### 4. 当前明确不是目标的内容

在上述证明完成前，不应优先扩展：

- 完整企业协作平台。
- 飞书式群聊和组织系统。
- 多项目管理后台。
- 无人工确认的远程指令执行。
- 大而全的完整会话、媒体和文件浏览器。
- 只改善视觉、但不能提高状态准确性和交付稳定性的功能。

## 二、截至 2026-07-22 的真实状态

### 已经证明

- 能从本地 Codex JSONL 中提取用户消息和最终回复。
- 能调用模型生成结构化摘要，并注入 Codex 右侧面板。
- 注入方案不修改官方 `app.asar`，可使用隔离配置启动。
- 最新开发分支已尝试通过 Codex `app-server` 读取结构化任务，并保留 JSONL 降级路径。
- 最新开发分支已有 React UI、会话列表、分页、虚拟渲染、媒体处理和 SSE 更新。

### 尚未证明

- 陌生用户能否在干净电脑上一键运行。
- 能否自动、可靠地跟随当前打开的 Codex 项目和任务。
- 摘要是否长期准确，是否会遗漏关键风险或制造错误状态。
- 每日模型调用成本和延迟是否可接受。
- 两台真实电脑之间能否只同步筛选后的状态。
- 身份、项目成员、授权、撤销、离线和租约过期模型是否成立。
- Codex 升级后 `app-server` 和 CDP 注入是否仍能兼容。
- 局域网或远程访问时，会话和媒体数据是否真正受到保护。

## 三、主要挑刺

### P0：产品身份混乱

默认 README 的主体仍是 Codex Dream Skin、主题预设和宣传图片。仓库名称和 `PROJECT.md` 表达的是协作面板，但新用户进入仓库后首先看到的是换肤工具。

这会造成三个问题：

- 用户不知道项目到底卖什么价值。
- 贡献者无法判断应维护换肤功能还是协作功能。
- 安全边界、安装说明和验收标准被两套产品目标混在一起。

建议：协作项目应拥有独立、目标明确的 README；Dream Skin 只作为原型来源和注入能力说明，不应继续占据产品主叙事。

### P0：最新有效代码不在默认分支

结构化网页 UI 和新数据层在 `origin/codex/publish-current-panel`，而 `main` 仍是较早的本地面板版本。别人正常克隆后无法得到开发日志所描述的最新体验。

建议：在合并前明确 PR 的验收清单；通过后合并，未通过则标明实验分支，不应让文档同时把未合并能力描述成当前产品能力。

### P0：当前网页服务的安全边界与项目原则冲突

最新分支中的网页服务监听 `0.0.0.0`，启动脚本默认使用 `demo123`，并把令牌放在 URL 查询参数中。服务还提供完整会话和媒体读取接口。

这与“第一版只共享筛选后的项目状态”不一致。查询参数可能进入浏览历史、日志和分享链接；局域网监听意味着防火墙允许时其他设备可能访问服务。

建议：当前版本默认只监听 `127.0.0.1`。跨电脑功能必须使用新的、专门的状态接口，只暴露白名单字段；认证、项目授权和令牌撤销完成前，不开放原始会话和媒体接口。

### P0：项目尚不能在别人的电脑上可靠启动

`windows/scripts/start-collab-panel.ps1` 硬编码了 `C:\Users\Hans\...\node.exe`。`app-server` 客户端也假设 Codex CLI 位于固定的全局 npm 路径。

这说明目前验证的是作者环境，而不是可交付产品。

建议：所有运行时路径必须探测或由明确配置提供；干净 Windows 环境的一键启动测试应成为合并门槛。

### P1：开发路线正在偏离第一个跨电脑证明

项目文档规定的下一步最小动作是：研究 Happy，然后完成 A 产生状态、服务端同步、B 显示状态的一条链路。

最新分支却投入了较多工作建设完整会话浏览器，包括 Markdown、表格、图片、音频、视频、文件下载、历史分页和虚拟列表。这些能力本身有价值，但不是第一个跨电脑状态 Demo 的必要条件。

风险是项目会在“把本地聊天记录展示得更完整”上持续优化，却一直没有证明多人协作价值。

建议：冻结新的内容类型和视觉扩展，先完成两台电脑的只读状态同步实验。

### P1：缺少明确的共享状态数据契约

当前文档有状态示例，但没有可执行的数据结构。若不先定义契约，后续很容易直接同步原始对话，再依赖前端临时过滤。

最小状态建议包含：

```json
{
  "projectId": "stable-project-id",
  "memberId": "stable-member-id",
  "displayName": "Hans",
  "phase": "executing",
  "summary": "正在调整首页 Banner 的移动端尺寸",
  "needsConfirmation": false,
  "updatedAt": "ISO-8601 timestamp",
  "leaseExpiresAt": "ISO-8601 timestamp",
  "schemaVersion": 1
}
```

契约中不应出现完整 prompt、完整回复、文件绝对路径、API Key、工具参数和内部推理。

### P1：摘要质量和成本尚未形成产品指标

当前通过额外模型调用生成摘要，但没有持续衡量：

- 摘要是否忠于原始对话。
- 状态更新是否及时。
- 是否漏掉等待确认和失败状态。
- 单个工作日调用次数、token 和成本。
- 模型不可用时产品如何退化。

建议：建立 20 至 30 条真实会话的固定样本，人工标注目标、进度、风险和待确认项，形成可重复的摘要验收集。

### P1：Happy 仍是方向判断，不是已经完成的技术决策

项目提出优先复用 Happy，但目前没有形成源码研究结论、适配成本、协议边界和“不采用”的退出条件。

建议：把 Happy 调研限制为一个短期技术验证，输出以下结论后立即决策：

- 能否复用传输和设备配对，而不暴露完整会话。
- 多用户项目授权是否需要改动其核心模型。
- 自托管、升级和维护成本。
- 直接扩展与旁路项目状态服务的工作量比较。

### P1：测试覆盖与新代码规模不匹配

最新分支新增约 5,000 行代码，但现有 CI 主要检查语法和原 Dream Skin 回归测试。网页 UI 构建、API 鉴权、目录越权、媒体访问、分页一致性、SSE 重连和 app-server 降级没有成为 CI 门槛。

建议：在继续扩功能前，先补最小集成测试和安全测试。

## 四、建议路线

### 里程碑 A：可交付的本地控制台

完成标准：

- 干净 Windows 环境可用一条命令启动。
- 无作者用户名和固定安装路径。
- 自动识别当前项目和任务，或提供明确、低成本的选择方式。
- 只有一个正式入口，启动、停止、日志和健康检查明确。
- `app-server` 不可用时能明确降级，不能静默显示错误状态。
- 默认只绑定本机回环地址。

### 里程碑 B：定义隐私安全的状态层

完成标准：

- 状态 schema 固定并有版本号。
- 明确字段白名单和禁止字段。
- 真实事件驱动更新，并有租约过期机制。
- 有摘要准确性、隐私过滤和离线状态测试。

### 里程碑 C：两台电脑只读 Demo

完成标准：

- A 的真实工作事件能到达 B。
- B 只看到项目状态，不看到原始对话和文件。
- 断网、退出和异常关机后，状态能正确变成离线或可能离开。
- 无权限用户不能订阅项目。
- 能撤销设备或成员访问权。

### 里程碑 D：再决定是否扩展协作功能

只有里程碑 C 得到真实用户认可后，才评估：

- 项目群聊。
- 历史决策和任务管理。
- 人工确认后的指令转发。
- 多 Agent 分工。
- 完整会话和媒体共享。

## 五、下一步最小动作

建议严格按以下顺序推进：

1. 决定并处理最新 PR：明确它是本地控制台基础，完成便携性、安全和集成测试后再合并。
2. 新增 `project-status.schema.json`，固定第一版允许跨电脑传输的字段。
3. 用两个本地进程模拟电脑 A/B，只传一条白名单状态事件，验证租约过期。
4. 对 Happy 做限时源码核查，只验证传输、配对、授权和加密是否可复用。
5. 再将同一条状态链路放到两台真实电脑验收。

在第 3 步完成前，不建议继续增加新的会话内容类型、页面区域或视觉功能。

## 六、以后每项开发的判断标准

任何新功能开始前，至少回答：

1. 它直接服务哪个里程碑？
2. 用户侧可观察到的结果是什么？
3. 如何验证它真的工作，而不是只有代码存在？
4. 是否增加了原始对话、文件或密钥泄露面？
5. 是否引入新的后台进程、端口、模型费用或维护负担？
6. 如果不做它，第一个跨电脑 Demo 是否仍能完成？

如果第 6 项答案是“能”，而当前里程碑仍未完成，该功能默认延后。

## 七、初次评审结论

项目已经从概念图进入真实数据原型阶段，技术上不是空壳。最有价值的资产是：Codex 会话读取、结构化消息适配、本地面板注入和对隐私边界的初步认识。

当前最大问题不是缺功能，而是目标收束不足。产品叙事仍被 Dream Skin 占据，最新代码未合并，启动方式依赖作者环境，网页能力开始暴露完整会话，同时跨电脑状态链路仍未证明。

下一阶段的成功标准不应是“网页聊天界面更像 Codex”，而应是：

> 两台真实电脑之间，安全、准确、低成本地共享一条经过筛选的项目工作状态。

在这条链路成立之前，应克制所有大平台式扩展。
