## 一、执行结论

### 1. 路线 2 可行，但定义必须修正

路线 2 不应再理解为：

> 从 Orca 找几个模块，搬进当前 Demo。

更合理的定义是：

> 以 Orca 的完整开源工程作为新版本底座，保留其桌面、Runtime、daemon、网页、移动端和任务恢复主链路；在此基础上精简产品界面，并迁入我们已有的群聊产品能力。

原因不是 Orca 的单个模块更漂亮，而是它最有价值的能力跨越了：

- Electron 桌面端；
- Renderer 与 Preload；
- Runtime RPC；
- WebSocket 与设备配对；
- 独立 daemon 和 PTY；
- 网页端；
- 原生移动端；
- Codex/Claude 聊天记录解析；
- 工作区、终端、任务与恢复状态。

这些部分高度耦合。零散迁移会重新制造多套状态、多套事件源和大量兼容层，风险高于在 Orca 上做受控精简。

### 2. Orca 已经接近我们需要的“双端工作底座”

源码确认 Orca 已经具备：

- 完整桌面开发端；
- 浏览器端复用同一个 React 主应用；
- 手机 Companion；
- 设备配对、设备 Token 和端到端加密；
- 断线重连、心跳与订阅恢复；
- 在桌面、网页和手机之间查看、继续同一个终端任务；
- Codex/Claude 原生聊天记录读取和实时状态追踪；
- 独立 daemon，允许界面进程退出后保留正在运行的终端和 Codex 进程；
- 多 Agent 任务、分派、消息、依赖、决策门和完成回执的持久化编排基础。

因此，Orca 不是单纯的“多开 Codex 窗口工具”，也不是只有桌面 UI。它已经覆盖了我们旧 Demo 最薄弱的远程任务主链路。

### 3. Orca 没有直接完成我们的核心产品

Orca 仍未提供以下完整产品能力：

- 面向用户的群聊房间；
- 用户发一条消息后“谁应该回复”的群聊路由；
- 多 Agent 共享上下文策略；
- 每个 Agent 使用不同厂商、不同模型和不同 API Key 的统一配置体验；
- 群聊消息、任务消息和共享记忆之间的产品化关系；
- 我们设想的“五人小公司”角色协作体验；
- Windows 服务守护、远程紧急拉起和 Wake-on-LAN；
- 完全无感的 UAC 处理。

结论是：**Orca 可以成为稳定底座，但不能替代我们的核心群聊产品设计。**

### 4. 对昨天结论的正式修正

2026-07-29 的初步报告曾建议“不整体 Fork Orca，优先抽取模块”。在完成 v1.4.161 源码链路审计后，这一建议不再成立。

修正后的判断是：

> 对路线 2，优先采用“受控整体 Fork”；不再以旧 Demo 为主工程逐个搬运 Orca 的核心运行模块。

“受控整体 Fork”不等于原样发布 Orca，也不等于立即删除大量源码，而是：

1. 先保留完整主链路；
2. 用实际验收证明跨端任务连续性；
3. 再隐藏或裁剪不需要的产品入口；
4. 最后迁入我们的群聊和多模型能力。

## 二、用户真正需要的目标体验

本项目当前目标不是做一个纯网页聊天产品，也不是要求用户放弃桌面端，而是：

| 使用场景 | 理想体验 |
|---|---|
| 在开发电脑前 | 使用完整桌面端，体验应接近或优于单人 Codex |
| 临时离开电脑 | 手机打开一个链接，直接看到同一个任务的进度 |
| 手机补充要求 | 在原任务内继续发送消息，不重新建立上下文 |
| 回到电脑前 | 桌面端已经同步显示手机期间的任务变化 |
| 网页端正在操作 | 桌面端明确提示同一任务正在被远程控制或输入 |
| 网络短暂中断 | 自动重连并补回状态，不出现“看起来卡死但其实仍在运行” |
| 界面被关闭 | 后台任务尽量继续；重新打开后接回原进程 |
| 群聊 | 用户只面对一个房间，系统负责角色选择、上下文和协作过程 |

Orca 对前七项已有不同程度的基础支持；第八项仍是我们的主要开发内容。

## 三、Orca 的真实跨端链路

### 1. 桌面端启动任务

Orca 在桌面端创建 Agent 任务时，会：

1. 创建或选择工作区；
2. 创建终端标签；
3. 生成 Codex、Claude 或其他 CLI Agent 命令；
4. 将终端交给独立 daemon；
5. daemon 使用稳定的会话标识创建或重新连接 PTY；
6. Runtime 向桌面、网页和手机发布终端及 Agent 状态。

这意味着任务的主要执行实体不是 React 页面，而是 daemon 管理的真实终端进程。

### 2. 网页端连接

Orca 的网页端不是独立做的一套简化 Demo。源码入口：

`src/renderer/src/web/main.tsx`

该入口加载与桌面端相同的主 `App`，再用 Web 适配层替代 Electron IPC。Runtime 同时提供：

- 浏览器静态资源；
- WebSocket RPC；
- 配对链接；
- 设备凭证；
- E2EE 公钥；
- 工作区、终端、文件和聊天记录接口。

网页打开配对链接后，凭证被保存到浏览器本地，并从地址栏中清除，避免配对 Token 长期暴露在历史记录和代理日志中。

### 3. 手机端连接

原生手机端使用权限较窄的 mobile scope。它可以：

- 查看项目和任务；
- 查看终端；
- 查看原生 Chat UI；
- 发送后续指令；
- 上传图片；
- 接收任务完成或需要处理的通知；
- 查看和处理部分 Git、Diff、PR 工作流。

手机主动向某个终端输入时，Orca 会将该终端的控制权标记为手机占用。桌面端显示：

- “Your phone is in control”；
- “Take back this terminal”。

桌面键盘会暂时停止向该终端输入，用户可以在桌面主动取回控制权。这一设计直接解决了“两个 UI 同时输入、相互打架”的一部分问题。

### 4. “同一会话”的准确含义

Orca 可以继续的是：

> Orca 中由 daemon 管理的同一个 Codex CLI/Claude CLI 进程、PTY 和任务上下文。

Orca不能直接继续的是：

> OpenAI 官方 Codex 桌面应用中已经存在的原生任务或 Thread。

因此，如果采用 Orca 作为底座，跨端任务需要从我们的 Orca 派生桌面端中启动。用户仍然使用 Codex 能力，但桌面工作入口将是我们的应用，而不是官方 Codex 桌面应用的原界面。

这不是小差异，必须在路线决策和实机验收中明确。

## 四、哪些状态真正共享，哪些状态相互独立

| 状态 | 桌面、网页、手机关系 | 结论 |
|---|---|---|
| Codex/Claude CLI 进程 | 同一宿主进程 | 共享 |
| PTY 输出和输入 | Runtime 统一转发 | 共享 |
| 工作区文件 | 都操作宿主电脑文件 | 共享 |
| Git 状态和 Diff | 从宿主 Runtime 读取 | 共享 |
| Agent 运行状态 | Runtime 发布 | 共享 |
| 原生聊天记录 | 从宿主记录读取和订阅 | 共享 |
| 编排任务、消息和决策门 | SQLite 持久化 | 共享 |
| 当前正在浏览哪个项目 | 每个客户端默认独立 | 不强制同步 |
| 当前激活哪个标签 | 每个客户端默认独立 | 不强制同步 |
| 部分 UI 偏好 | 浏览器本地保存 | 独立 |
| 手机终端控制权 | Runtime 中有明确 driver 状态 | 共享且可见 |
| 普通网页客户端身份提示 | 有设备身份，但缺少完整产品化提示 | 需要改造 |

这种设计总体合理：手机查看另一个项目时，不应强迫桌面跳走；但当手机或网页真的向同一个任务发送指令时，桌面必须给出明确提示。

我们后续需要增加的不是“所有页面强制同步”，而是：

- 同一任务的远程活动提示；
- 当前控制端提示；
- 最后一次远程指令；
- 远程端在线/离线状态；
- 用户可以主动取回控制权。

## 五、Orca 已经解决的关键问题

### 1. 远程端不是旁路 Demo

旧 Demo 的桌面端和网页端没有统一的权威事件源。Orca 中，桌面、网页和手机都围绕同一个 Runtime 工作，网页操作最终落在宿主电脑的真实项目和真实终端上。

### 2. 长任务断线恢复

网页客户端具备：

- 自动重连；
- 心跳检测；
- 半开连接识别；
- 订阅重放；
- 终端流恢复；
- 文件监听恢复；
- Runtime 重启后的状态重新同步。

这比旧 Demo 的简单轮询更接近真实远程开发需要。

### 3. 界面与任务进程分离

Orca daemon 是独立、隐藏且 detached 的进程。在 Windows 上，Electron main 退出后，daemon 和其中的 PTY 可以继续存活。再次启动 Orca 时，可以重新连接现有 daemon 和终端。

这解决了：

> UI 或主进程退出，不应直接杀死正在进行的 Codex 任务。

但它没有解决：

> Orca 主进程退出后，网页端仍然可以继续连接。

因为 Runtime RPC 仍运行在 Electron main 中。主进程真正退出后，手机和网页入口会消失，只是后台 Codex 进程可能仍然活着。

### 4. 手机与桌面输入冲突

Orca 已有手机 presence lock 和桌面取回控制权机制。这是当前项目可以高比例复用的成熟设计，不应重新从零设计。

### 5. 多 Agent 编排的后台基础

Orca 的 orchestration 模块已经提供：

- 持久化消息；
- 任务和分派；
- 任务依赖；
- worker 完成回执；
- 心跳；
- 升级与求助；
- 决策门；
- coordinator 状态；
- SQLite 存储。

这些能力可以成为我们的“群聊后台任务账本”，但不能直接当作群聊产品界面。

## 六、Orca 没有解决或只解决一半的问题

### 1. 群聊产品逻辑

Orca 的多 Agent 能力主要服务于结构化任务分派，不会自动回答：

- 用户发一条消息后谁先回复；
- 哪些 Agent 只旁听；
- 哪些 Agent 需要互相质疑；
- 什么时候只显示一个综合答案；
- 哪些上下文对所有 Agent 可见；
- 如何控制重复回复和 Token 成本；
- 一个 Agent 使用 Codex，另一个使用 Claude、Kimi 或中转模型时如何统一管理。

这部分仍是我们的核心自研范围。

### 2. 官方 Codex 桌面会话同步

Orca 运行的是 Codex CLI，不是官方 Codex 桌面应用的内部任务。用户无法自然地在官方 Codex 桌面端开一个任务，再期待 Orca 手机端无缝接管同一原生 Thread。

可接受的目标应调整为：

> 在我们的 Orca 派生桌面端中提供接近 Codex 的单人体验，同时获得网页、手机和群聊能力。

### 3. Windows 主进程自动恢复

源码确认：

- Renderer 崩溃可以自动重载；
- daemon 可以在 main 退出后继续；
- Main 崩溃或真正退出后不会自行重新启动；
- 未发现 Windows Service；
- 未发现登录自启实现；
- 未发现手机远程启动离线 Orca 的能力；
- 未发现 Wake-on-LAN。

因此仍需单独设计：

- Windows 登录自启；
- 用户级守护进程；
- Runtime 健康检查；
- 主进程异常后的自动拉起；
- 网页端“紧急恢复”按钮；
- 无法恢复时跳转向日葵等兜底工具。

### 4. UAC

Orca 的普通运行尽量使用用户级操作，不会日常主动请求管理员权限。但 Windows 防火墙修复仍使用标准 `RunAs`，会触发 UAC；网页端明确不能代替本机确认。

所以准确结论是：

> Orca 通过减少需要提权的操作降低 UAC 出现概率，但没有绕过或远程处理 UAC。

我们的目标也不应是“远程点击 UAC”，而应优先做到：

- 安装阶段一次性完成必要配置；
- 日常功能全部使用用户权限；
- 公网入口不依赖临时修改防火墙；
- 更新过程不请求管理员权限；
- 只有极少数明确维护操作才可能出现 UAC。

### 5. 手机直接打开网页的体验

Orca 有完整浏览器客户端，但当前网页端复用桌面主应用。它在手机浏览器上的真实可用性尚未实机验证。

必须区分：

- “源码可以在浏览器运行”；
- “手机浏览器上足够轻便、清晰、好用”。

如果 Orca 完整网页端在小屏上过重，可以保留 Orca Runtime，同时将我们现有的移动网页 UI 改造成轻客户端。这仍然属于以 Orca 为底座，不代表退回旧 Demo 主干。

## 七、两种路线重新对比

| 对比项 | A：受控整体 Fork Orca | B：旧 Demo 逐块迁入 Orca 能力 |
|---|---|---|
| 跨端主链路 | 原生保留 | 需要重接 |
| daemon/PTY | 原生保留 | 需要重接 |
| 网页端 | 与主应用同源 | 需要维护两套 UI/适配 |
| 手机端 | 已有原生实现 | 需要重新接入 |
| E2EE 与设备配对 | 原生保留 | 迁移容易遗漏边界 |
| 断线恢复 | 已有大量测试 | 需要重写 |
| 当前群聊 UI | 需要迁入 | 可直接保留 |
| 当前产品外观 | 需要改造 | 变化较小 |
| 初期工程体量 | 大 | 表面较小 |
| 隐性耦合风险 | 中 | 高 |
| 上游升级成本 | 高 | 中高 |
| 再次发生“适配器替代迁移” | 较低 | 很高 |
| 达到稳定双端体验的概率 | 较高 | 较低 |

推荐 A。

不推荐 B 的主要原因不是旧 Demo 完全无价值，而是它的运行主干不足以承接 Orca 的复杂状态模型。保留旧主干会让我们同时维护：

- 旧群聊服务；
- 旧 Web 状态；
- Orca Runtime；
- Orca daemon；
- Orca 会话；
- 两套恢复逻辑；
- 两套消息或任务状态。

这与“直接站在稳定基础上继续开发”的初衷相反。

### 4. 必须自研

- 群聊房间数据库；
- Agent 身份、角色和模型配置；
- 多厂商 API Key 管理；
- 群聊路由；
- 共享上下文和摘要；
- Agent 间可见性规则；

- 群聊与 Orca 编排任务之间的桥接；

- Windows 守护和紧急恢复；
- 面向手机浏览器的轻量入口。

综合判断：

> 运行与跨端基础可以高比例利用 Orca；我们的主要开发量应转移到产品层，而不是继续重复开发终端、远程连接和会话恢复。

## 九、推荐的第一阶段

### 1. 第一步做什么

在用户确认后，新建一个以 Orca v1.4.161 为起点的独立路线 2 分支。

第一阶段只做一条纵向链路，不先做 UI 大改，也不先删功能：

1. Windows 上构建 Orca；
2. 启动一个 Codex CLI 任务；
3. 生成网页访问链接；
4. 电脑浏览器接入同一任务；
5. 手机浏览器接入；
6. 从远程端发送后续要求；
7. 验证桌面显示同一任务变化；
8. 验证网络中断后恢复；
9. 关闭窗口、结束 Renderer、结束 Main 后分别观察任务和入口；
10. 验证 Cloudflare Tunnel 或其他 `wss` 公网入口。

### 2. 第一步会得到什么结果

不是得到一个“完成的新产品”，而是得到一份真实的可行性判定：

- Orca 是否能在当前 Windows 环境稳定构建；
- 是否能使用现有 Codex/中转配置；
- 手机是否真的能通过链接继续同一任务；
- 网页和桌面是否会相互打架；
- Main 退出后任务和远程入口分别发生什么；
- 是否可以沿用现有 Cloudflare Tunnel；
- 日常链路是否会触发 UAC；
- 手机浏览器是否需要单独轻量 UI。

### 3. 第一步的用户体验改善

如果验收通过，用户将获得：

> 在开发电脑上使用完整桌面端；离开电脑后，手机打开固定链接，看到原任务当前状态并继续补充要求；回到电脑后，桌面端已显示远程期间的结果，不需要重新解释上下文。

与旧 Demo 相比，主要改善不是“多几个按钮”，而是：

- 任务有一个真实权威来源；
- 网页刷新后仍能接回；
- 网络断开不等于任务丢失；
- UI 退出不必然杀掉 Codex；
- 手机控制时桌面明确提示；
- 任务状态不再依赖猜测。

### 4. 第一阶段停止条件

出现以下任一情况，应暂停整体迁移并复盘：

- Windows 无法稳定构建；
- 手机网页无法完成基本输入；
- 通过公网入口后 WebSocket 长时间不稳定；
- 同一任务出现重复输入或状态分叉；
- Codex 中转配置无法沿用；
- Orca 上游结构导致基础品牌改造成本失控；
- 关键能力实际依赖未开源服务。

失败后的退路不是回到旧 Demo 继续堆功能，而是：

> 保留 Orca Runtime 和 daemon，只把我们现有 PWA 改造成轻量客户端。

## 十一、主要风险

### 1. Fork 维护成本

Orca 代码量大、更新频繁。整体 Fork 会产生上游同步成本。应对方式不是先删代码，而是：

- 尽量通过功能开关隐藏；
- 将我们的产品代码放在明确模块中；
- 避免无必要修改 Runtime 核心；
- 定期按版本批量同步；
- 对关键链路保留上游测试。

### 2. 产品范围失控

Orca 自带大量 IDE 功能，容易让项目再次陷入“什么都想保留”。首版只围绕：

- 单人 Codex；
- 远程继续任务；
- 群聊；
- 多模型；
- 文件和结果查看；
- 稳定恢复。

其他能力先隐藏，不因源码存在就全部暴露给用户。

### 3. 手机入口选择

用户希望手机打开链接即用，不希望强制安装 Orca。原生移动端功能更成熟，但会增加安装和发布成本；网页端更符合项目初衷，但小屏体验待验证。

推荐顺序：

1. 先验证 Orca 网页端；
2. 小屏不合格时开发轻量 Web 模式；
3. 原生移动端作为增强入口，而不是唯一入口。

### 4. 安全

Runtime 具备设备 Token 和 E2EE，但公网部署仍需处理：

- 链接泄露；
- 设备撤销；
- HTTPS/WSS；
- Tunnel 权限；
- API Key 不下发到浏览器；
- 日志和地址栏不暴露配对凭证；
- 远程执行的危险操作提示。

### 5. “任务存活”被误解为“服务存活”

daemon 可以让 Codex 进程在 UI/Main 退出后继续，但远程网页依赖 Runtime RPC。必须分别显示：

- Codex 任务是否还活着；
- Runtime 是否在线；
- 公网 Tunnel 是否在线；
- 手机是否能连接。

不能再用一个模糊的“在线/离线”概括全部状态。

## 十二、最终建议

### 推荐

1. 正式将路线 2 调整为受控整体 Fork Orca；
2. 旧 Demo 停止继续扩充运行主干；
3. 保留旧 Demo 的群聊产品设计和部分 UI；
4. 第一阶段只验证真实跨端纵向链路；
5. 验证通过后再迁入群聊；
6. Windows 守护、远程拉起和低 UAC 作为独立能力开发；
7. 未完成实机验收前，不宣称 Orca 已经解决全部问题。

### 不推荐

- 再做一个 Orca CLI 适配器；
- 只复制 daemon 而保留旧 Web 状态；
- 只复制网页 UI 而不使用 Runtime；
- 先大规模删除 Orca 代码；
- 把 orchestration 直接包装成群聊；
- 把“源码中有测试”当成“Windows 实机已经可用”；
- 为了保留官方 Codex 桌面 UI，而继续维护不稳定的双主干。

### 产品定位上的直接影响

采用 Orca 底座后，本项目的价值不再是：

> 再做一个终端和多 Agent IDE。

而应明确为：

> 一个以群聊和角色协作为核心、同时具备稳定桌面开发与随时随地远程继续能力的 AI 工作平台。

Orca 提供“稳定工作的骨架”；我们的价值必须集中在：

- 更简单的使用方式；
- 群聊协作；
- 多模型组合；
- 角色和组织模拟；
- 共享上下文；
- 跨端连续性；
- 面向普通用户的低配置体验。

## 十四、可信度说明

### 已由源码确认

- 桌面、网页、手机连接同一 Runtime；
- 网页复用主 React 应用；
- 同一 PTY/CLI 任务可被远程查看和继续；
- daemon 与 Electron main 分离；
- 终端和部分任务状态可以恢复；
- 手机控制权和桌面取回机制；
- 多 Agent 编排状态持久化；
- UAC 仍用于主动防火墙修复；
- Main 退出后远程 Runtime 不再可用；
- Windows 缺少完整自动守护和远程拉起。

### 基于源码的方案判断

- 受控整体 Fork 比逐块迁移更适合路线 2；
- Orca Runtime 可替换旧 Demo 的运行主干；
- 旧 Demo 的群聊 UI 和产品规则仍有迁移价值；
- 群聊应作为 Orca 上层产品能力，而非简单复用编排 CLI。

### 必须实机验证

- Windows 构建和安装；
- 现有中转站与 Codex 配置；
- 手机浏览器实际布局；
- Cloudflare Tunnel；
- 多客户端并发输入；
- 长任务断线恢复；
- Main 强杀后重新接回；
- 普通链路是否完全不触发 UAC；
- 上游 Orca 更新后的维护成本。

在实机验证完成前，以上待验证项不得写成已交付能力。
