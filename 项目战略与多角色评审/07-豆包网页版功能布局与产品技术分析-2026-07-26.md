# 豆包网页版功能、布局与产品技术分析

文档日期：2026-07-26
调研对象：豆包网页版、移动端响应式页面、AI 创作页，以及豆包官方桌面端功能说明
文档性质：竞品实测与分析，不是本项目已经确认的产品定案
适用范围：`codex-collab-panel-demo` 后续单人对话、群聊、多 Agent、任务状态和移动端体验设计

## 一、核心结论

豆包网页版的本质不是“聊天框加很多按钮”，而是以同一个自然语言输入框为入口，承载三个不同层级的工作空间：

1. 通用对话：快速问答、专家问答和各种轻量技能。
2. 办公任务：由 Agent 拆解并执行长任务，进一步连接浏览器、本地电脑、Skills 和办公产物。
3. AI 创作：面向图片和视频的参数化创作工作台。

最值得本项目借鉴的不是豆包的功能数量，而是它对“模式、技能、工具、产物”的分层：

- 模式决定 AI 采用什么工作方式。
- 技能决定用户要完成哪类任务。
- 工具负责真正执行浏览器、文件、Office、图片或视频操作。
- 产物使用适合自身类型的界面呈现，而不是全部退化成长篇聊天文字。

豆包主要解决“一个用户使用一个全能助手”的问题。本项目如果继续发展，差异不应落在重复增加 PPT、生图、写作等入口，而应落在“真人与多个 Agent 共同监督项目、共享进度和组织记忆”上。

## 三、功能全景

### 3.1 通用对话

未登录首页可以确认的入口包括：

- 新对话。
- 文本输入。
- 麦克风语音输入。
- 附件入口。
- 动态推荐问题。
- 模式选择。
- 快捷技能栏。
- 下载电脑版。
- 登录与账号切换入口。

首页推荐问题覆盖资讯、写作、知识整理、编程、汇率、语言学习等场景。推荐内容会动态变化，其作用不是保存固定模板，而是持续告诉用户“豆包现在可以做什么”。

### 3.2 模式选择

实测模式菜单中包含：

| 模式 | 页面说明 | 产品含义 |
| --- | --- | --- |
| 快速 | 适用于大部分情况 | 默认低门槛问答 |
| 专家 | 研究级专业问答，2.1 Turbo | 更强推理和专业回答 |
| 办公任务 Turbo | 执行 Agent 任务，2.1 Turbo | 快速执行型 Agent |
| 办公任务 Pro | 执行 Agent 任务，2.1 Pro | 更高成本、更复杂的 Agent 任务 |

这里体现了一个重要设计：用户先选择“AI 怎么工作”，再选择具体技能。模式不是某一个功能按钮。

### 3.3 快捷技能

当前实测到的技能包括：

- PPT 生成。
- 图像生成。
- 帮我写作。
- 视频生成。
- 翻译。
- 深入研究。
- 录音转写。
- 音乐生成。
- 解题答疑。
- AI 播客。
- 数据分析。

页面没有同时展示全部入口。高频技能直接显示，其他能力收进“更多”，降低输入区的视觉负担。

### 3.4 附件与多模态输入

输入框左侧存在附件入口。未登录点击后会直接打开登录界面，说明附件能力与用户身份、存储和任务记录绑定。

本次只确认入口存在，没有确认全部文件类型。不能仅凭按钮推断它一定支持任意图片、音频、视频、HTML、压缩包或大型表格。

登录方式包括：

- 中国大陆手机号。
- 抖音一键登录。
- 飞书企业账号登录。
- 豆包或飞书 App 扫码登录。

飞书企业账号入口表明豆包不仅面向个人消费者，也在向企业办公身份和协作场景延伸。

### 3.5 办公任务

网页版的“新办公任务”不是普通聊天标题，而是独立工作模式。当前页面可确认的控制项包括：

- 办公任务 Turbo。
- 本地电脑。
- 技能。

官方桌面端说明进一步列出了：

- Agent 自主拆解工作任务。
- 操作本地电脑和浏览器。
- 整理、归类、总结本地文件。
- 调用 Skills。
- 定时写周报、追踪热点、发布社交媒体内容。
- 生成文档、表格和 PPT。
- 在线多人协同编辑和导出。
- 生成仪表盘、看板、报名页等在线应用。
- 热点分析、个股监测、海报视频制作和数据可视化。

这些能力不能全部视为纯网页版能力。浏览器受到沙箱限制，无法自由访问本地文件或控制其他应用。“本地电脑”合理的实现方式必须依赖桌面客户端、本地服务或受授权的执行桥接。

### 3.6 AI 创作

AI 创作使用独立页面，而不是继续堆叠在普通聊天流里。页面分为图像和视频两个标签。

图像生成控制项包括：

- 文本描述。
- 参考图。
- 模型选择。
- 输出比例。
- 风格选择。
- 语音输入。
- 案例瀑布流。
- “做同款”。

当前模型菜单显示：

- Seedream 5.0 Pro：专业出图，4 倍消耗。
- Seedream 5.0 Lite：进阶效果，3 倍消耗。
- Seedream 4.5：日常生成。
- Seedream 4.0：基础生图。

支持的比例包括：

- `1:1`：正方形、头像。
- `2:3`：社交媒体、自拍。
- `3:4`：经典比例、拍照。
- `4:3`：文章配图、插画。
- `9:16`：手机壁纸、人像。
- `16:9`：桌面壁纸、风景。

风格菜单覆盖人像摄影、电影写真、中国风、动漫、3D 渲染、赛博朋克、水墨、油画、水彩、像素、版画、绘本等约三十种风格。

图像后期能力包括：

- AI 抠图。
- 擦除。
- 标记改图。
- 扩图。
- 变清晰。

官方说明中的 Seedance 2.0 支持文生视频、图生视频、多种比例、最长 10 秒输出和角色一致性。本次没有登录生成，具体质量和限制没有实测。

### 3.7 研究、办公与内容产物

官方功能说明还确认了：

- 联网搜索。
- 深入研究报告。
- 会议纪要、总结和汇报。
- 图片与视频生成。
- PPT、文档和表格处理。
- 手机与电脑同步对话记录。

这些能力的共同点是“最终交付物”不再只是聊天文字。产品需要针对报告、表格、PPT、图片、视频和网站提供独立的内容渲染器、编辑器或预览界面。

## 四、布局与视觉设计

### 4.1 桌面端整体布局

桌面端采用固定三段式布局：

1. 左侧导航栏。
2. 顶部状态栏。
3. 中央工作区和底部输入框。

在本次 `1440px` 宽度实测中：

- 左侧栏宽约 `280px`。
- 顶部栏高约 `56px`。
- 输入容器宽约 `1000px`。
- 文本编辑区宽约 `960px`。
- 输入框贴近底部，但保留稳定外边距。

左侧栏负责长期导航：豆包、新对话、新办公任务、AI 创作、历史记录和关于豆包。中央区域只显示当前任务，避免把导航和内容混在一起。

### 4.2 首页信息结构

首页主区域只有三个重点：

- “有什么我能帮你的吗？”
- 动态推荐问题。
- 底部输入框。

页面大面积留白，不使用营销式卡片或复杂装饰。推荐问题使用浅灰色胶囊标签，输入框使用蓝色轻描边和柔和阴影，视觉注意力自然落在输入动作上。

### 4.3 输入框设计

输入框是豆包网页版的核心控制台，而不是单纯文本框。它同时容纳：

- 文本与语音输入。
- 附件。
- 模式选择。
- 技能入口。
- 发送按钮。

功能按使用频率逐级展开。默认状态只显示常用能力，“更多”承担溢出菜单。用户不需要先理解全部产品架构，就可以直接输入问题。

### 4.4 AI 创作布局

AI 创作页改变了中央内容结构：

- 顶部是标题和创作说明。
- 中间是大型参数化输入框。
- 输入框下方是图像编辑快捷入口。
- 下方使用瀑布流展示案例。

这种设计承认不同任务需要不同界面。图片创作需要参考图、模型、比例、风格和案例，不适合全部藏在聊天消息中。

### 4.5 移动端布局

在 `390 × 844` 的实测视口中：

- 桌面侧栏隐藏。
- 顶部下载、登录等次要入口隐藏。
- 输入容器左右各保留约 `16px`。
- 输入容器宽约 `358px`。
- 技能栏仅保留“快速”和“更多”。
- 推荐问题采用横向溢出方式。

移动端的优点是界面非常轻，缺点是高级能力更难被发现。推荐问题横向裁切也会让用户不知道还有多少内容可以滑动。

## 五、用户使用体验分析

### 5.1 优点

#### 低学习成本

用户可以先输入，再决定是否选择模式、技能或附件。产品没有要求用户先理解模型、工作流和工具体系。

#### 渐进式展示

高频功能直接出现，低频功能放入“更多”。普通用户看到的是一个简洁输入框，专业用户仍然可以进入复杂模式。

#### 普通问答与 Agent 任务分开

“快速”“专家”和“办公任务”具有不同语义。它提醒用户：有些请求是马上回答，有些请求需要拆解、执行和等待。

#### 结果形态与任务匹配

图像创作使用画廊，办公任务面向文档和网站，研究任务生成报告。豆包没有强迫所有结果使用同一种聊天气泡。

#### 跨设备连续性

官方明确宣传手机与电脑同步对话。对用户来说，设备只是入口，真正持续存在的是账号下的对话和任务。

### 5.2 问题和风险

#### 功能重叠

“专家”“深入研究”“办公任务 Turbo”“办公任务 Pro”对普通用户并不容易区分。功能数量增加后，选择成本也随之增加。

#### 登录前反馈不完整

未登录时可以在输入框填写内容，但尝试发送后页面会跳回登录状态并清空任务。用户容易误以为内容已经提交。

#### 网页与桌面能力边界模糊

网页版展示“本地电脑”入口，但真正操作本地文件必然依赖桌面执行端。若产品不明确显示当前执行节点，用户会混淆“网页在做事”和“某台电脑在做事”。

#### 移动端发现性下降

为了简化移动端，豆包隐藏了多数技能。轻量性得到提升，但用户可能不知道网页还支持 PPT、研究、录音和数据分析。

#### 产品体量带来性能成本

功能模块、图片素材、实验配置和监控体系不断增加，使首屏资源规模变大。即便使用代码拆分，低端手机仍可能出现延迟和卡顿。

## 六、技术实现分析

### 6.1 已确认的前端结构

通过页面资源和 DOM 可以确认：

- 前端使用 React，存在独立的 `lib-react` 资源包。
- 页面以 `/chat` 和 `/chat/create-image` 作为不同路由。
- 使用大量异步 JS 和 CSS 模块。
- 存在聊天运行时、输入引擎、技能栏和消息生命周期等独立模块。
- 页面存在 `__LOADABLE_REQUIRED_CHUNKS__`，说明使用了可加载组件和分包机制。
- DOM 中同时出现 Semi Design、Radix Menu 属性和工具类 CSS。
- 图片、图标和主要静态资源通过字节 CDN 提供。
- 图片资源使用带过期时间和签名的 CDN URL。

这说明豆包并非一个巨大单体聊天组件，而是把输入引擎、聊天运行时、技能、创作页面和业务初始化拆成了不同模块。

### 6.2 会话、监控与实验

未登录页面仍会请求匿名 Web ID，并加载：

- Slardar 前端监控。
- 浏览器监控插件。
- 匿名设备标识。
- A/B 测试配置。
- 页面行为和性能配置。

这使豆包能够在用户登录前维持实验分组、监控错误和分析转化路径。

### 6.3 性能样本

在当前电脑、当前网络和未登录首页的单次样本中，页面加载约五秒后记录到：

- 约 `320` 个资源请求。
- 约 `10.2 MB` 传输量。
- 约 `209` 个脚本资源。
- 约 `43` 个样式资源。
- 约 `20` 个直接图片资源。

这个数字包含异步加载和预取资源，不能直接等同于每次首屏阻塞成本，但足以说明整个产品已经较重。

豆包使用了以下方式降低体感等待：

- CDN 预连接和 DNS 预取。
- React 运行库单独缓存。
- 页面和功能按异步模块拆分。
- 首页预取聊天模块。
- 图片使用专门的图片 CDN。
- 高频入口先显示，复杂功能后加载。

### 6.4 实时通信边界

未登录空闲页面没有建立 WebSocket。本次没有完成登录后的真实对话，因此不能确认正式回复协议。

合理的实现可能是：

- 普通回复使用 SSE 或流式 Fetch。
- 长任务使用事件流持续更新 Task 和 Run 状态。
- 上传和产物使用独立文件接口。
- 跨设备状态通过服务端持久化，而不是依赖某个浏览器内存。

以上属于架构推断，不是本次已经抓取验证的豆包内部实现。

### 6.5 本地电脑能力

浏览器无法直接自由控制用户电脑。合理架构应当是：

```text
网页版任务界面
    ↓
云端任务编排与状态服务
    ↓
桌面客户端或本地执行桥接
    ↓
本地文件、浏览器、Office、定时任务
```

产品必须明确显示：

- 当前任务连接的是哪台电脑。
- 电脑是否在线。
- 当前是否正在执行。
- 哪些操作需要用户批准。
- 网页关闭后任务是否继续。

这与本项目此前遇到的 Desktop/Web 状态不一致问题高度相关。

### 6.6 PWA 状态

本次公开页面没有检测到：

- Web App Manifest。
- 已注册的 Service Worker。

因此豆包网页虽然可以被浏览器创建快捷方式，但当前实测页面不是完整的可安装 PWA，也不能仅凭网页获得可靠离线能力、后台同步和系统级通知。

### 6.7 可访问性问题

实测 DOM 中存在：

- 部分纯图标按钮没有明确的 `aria-label`。
- 模式选择结构中出现嵌套按钮。
- 一些主要导航使用可点击 `div`，而不是原生链接或按钮。

这些实现可能影响键盘操作、屏幕阅读器和自动化测试稳定性。视觉完成度高并不代表语义结构同样完善。

## 七、对本项目的直接启发

### 7.1 应该借鉴的部分

#### 共用基础组件

单人对话和群聊可以共用：

- Composer 输入组件。
- 附件上传。
- Message 消息外壳。
- ContentBlock 内容渲染器。
- Artifact 产物预览。
- TaskStatus 任务状态。

差异放在会话参与者、任务路由和 Agent 调度，不需要维护两套互不兼容的聊天系统。

#### 区分模式、技能和工具

本项目不应把所有东西都做成聊天按钮：

- 对话模式：普通沟通、项目经理、执行任务、审核。
- 技能：开发、研究、设计、测试、总结。
- 工具：Codex、浏览器、文件、Git、图片生成等。

#### 将任务状态结构化

Agent 正在分析、执行命令、等待审批、完成、失败，不应只依赖聊天文字描述。应使用持久化的：

- `Task`
- `AgentRun`
- `ActivityEvent`
- `Approval`
- `Artifact`

群聊只展示经过提炼的进度，完整运行日志进入二级页面或文件记录。

#### 结果按类型展示

消息渲染层应逐步支持：

- Markdown。
- 代码块。
- 图片。
- 音频和视频。
- 文件附件。
- 表格。
- HTML 预览。
- 任务状态。
- 审批卡片。
- 可下载产物。

### 7.2 不应该直接照搬的部分

- 不要一次增加豆包全部技能。
- 不要把本项目变成通用 AI 工具导航页。
- 不要为了展示功能而继续扩大输入框按钮数量。
- 不要把网页和桌面端描述成同一个实时执行实例。
- 不要只复制视觉样式，而忽略任务、运行、设备和状态数据结构。
- 不要使用 Agent 自由文本中的 `@名称` 作为正式调度协议。

### 7.3 当前最有价值的实施顺序

1. 统一单人和群聊的消息、附件、产物和输入组件接口。
2. 建立持久化的 `Task / AgentRun / ActivityEvent`。
3. 让网页真实显示某台电脑和某个 Agent 的在线、执行、等待和完成状态。
4. 建立稳定事件流，避免手机依赖刷新整个对话文件。
5. 再增加图片、文件、表格等内容渲染。
6. 最后才评估 PPT、生图、研究等通用技能入口。

## 八、最终判断

豆包网页版的成熟之处，是把庞大的能力隐藏在一个低门槛入口后面，并为办公任务和创作任务提供不同工作空间。

它的代价同样明显：功能重叠、能力边界复杂、网页和桌面执行容易混淆、前端资源体量较大。

对于本项目，正确借鉴方式是复用其“统一入口、能力分层、任务结构化、产物独立呈现”的思想，而不是复制其全能助手路线。

本项目更值得坚持的独特方向仍然是：

> 用户和朋友可以在同一个项目空间中，看见多个 Agent 的真实工作状态、讨论过程、任务交付和历史经验，并随时介入、纠正或阻止。

这个方向与飞书中简单加入几个机器人、以及豆包式个人全能助手都有明确区别。
