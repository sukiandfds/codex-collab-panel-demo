## 一、执行摘要

本次调研要回答的核心问题不是“市场上有没有多 Agent 产品”，而是以下四个更具体的问题：

1. 现有产品如何让多人和多个 Agent 在同一空间中沟通？
2. 它们是否把 Codex、Claude Code 等原生对话直接当作群聊数据？
3. Codex 自身已经提供了哪些双向控制、多 Agent 和状态能力？
4. 当前项目应继续扩展现有 Codex 对话结构，还是建立独立协作层？

调研结论如下。

### 1. 多人群聊不能直接建立在 Codex 原始对话结构上

Codex 的核心数据模型是：

```text
Thread -> Turn -> Item
```

它表达的是一个用户与 Codex Agent 的工作会话，适合保存用户输入、Agent 回复、命令、文件修改、工具调用和子 Agent 活动，但不负责表达：

- 多个真人成员及其身份；
- 项目群成员关系；
- 真人之间的普通聊天；
- 群消息权限、已读、引用、提及和成员状态；
- 某条群消息由哪个人授权成为 Agent 任务；
- 跨电脑成员和 Agent 的在线状态。

因此，未来的多人项目群需要独立的协作数据模型。Codex Thread 应作为 Agent 执行任务时使用的内部会话，而不是整个项目群的唯一消息记录。

### 2. 最接近本项目的现成参考是 OpenAgents Workspace

OpenAgents Workspace 已经实现：

- 人类和 Agent 共用 Workspace；
- 频道、线程、`@Agent`、文件和状态；
- 不同用户、设备和机器上的 Agent 接入同一工作区；
- 把 Codex CLI、Claude Code、Cursor、Gemini CLI 等作为外部执行 Agent；
- 为每个频道保存独立 Agent 会话；
- 将命令执行、文件修改和最终结果转换成工作区事件。

它证明了一条可行路径：独立协作空间负责多人关系与群聊，运行在用户电脑上的 Connector 负责连接 Codex。

### 3. Codex 已经具备双向控制和多 Agent 底层能力

当前本机安装版本为 `codex-cli 0.122.0`。OpenAI 官方 `app-server` 协议已经支持：

- 创建、恢复和分叉 Thread；
- 从外部客户端发送 Turn；
- 在 Codex 执行过程中继续追加指令；
- 中断执行；
- 实时返回回复、命令、文件修改、工具调用和审批请求；
- 返回 `idle`、`active`、`waitingOnApproval`、`waitingOnUserInput` 和 `systemError` 等状态；
- 创建、控制和观察子 Agent；
- 保存子 Agent 的父子 Thread、角色、昵称和状态。

这意味着当前只读网页升级为“浏览器向真实 Codex 发送指令并显示实时状态”，不需要推翻现有数据基础。

### 4. Codex 的多 Agent 不等于多人群聊

Codex 已具备一位用户控制多个子 Agent 的能力，但尚未发现其原生协议提供完整的多人项目群能力。多真人协作仍需要本项目或外部 Workspace 管理。

### 5. 推荐的长期分层

```text
协作层
  用户、项目、群聊、成员、权限、消息、状态、通知
                  |
                  v
组织与任务层
  项目经理 Agent、专业 Agent、任务、审核、打回、日志、产物
                  |
                  v
Agent Connector 层
  将群消息或任务映射到 Codex Thread，转发指令与状态
                  |
                  v
执行层
  Codex app-server / Codex CLI / 其他 Agent Runtime
```

当前项目已有的真实 Codex 对话页面可以继续保留，不需要因为未来加入群聊而重写。它可以继续承担真实对话查看和执行记录呈现；协作层应通过独立的数据与功能边界增加。

## 二、调研背景与产品目标

用户最初被吸引的体验是：

> 朋友正在持续和 AI 工作，我能够看到他们的对话和状态，因此知道什么时候适合与朋友沟通。

在讨论中，长期愿景进一步明确为：

> 一间专业、有组织架构、开箱即用的 AI 公司，里面有一群随时待命的 AI 员工。

当前较清晰的产品组成包括：

- 真人成员在项目群内沟通；
- 项目经理 Agent 在群内像真实成员一样回复和协调；
- 真人可以直接点名专业 Agent；
- 清晰任务可以直接执行，模糊任务由项目经理 Agent 组织澄清；
- 下属 Agent 的完整工作过程不持续灌入群聊；
- 群内主要看到提炼后的状态、进度和结果；
- 完整工作日志保留，用于定位错误和项目复盘；
- 私人对话默认私密，用户可以把总结助手提炼后的内容共享到项目群。

多个方案或多个团队 PK 属于可能的后续方向，不是当前最优先的技术目标。

## 五、重点竞品一：OpenAgents Workspace

### 1. 为什么它与本项目最接近

OpenAgents 将 Workspace 定义为持久化 Agent 协作中心。人类和 Agent 可以在浏览器或手机中使用同一个地址，进入频道、线程、共享文件和浏览器，并把运行在不同机器上的 Agent 拉入同一个工作空间。

官方 README 明确列出的兼容 Agent 包括 Codex CLI、Claude Code、Cursor、OpenCode、Gemini CLI、GitHub Copilot CLI、Cline、Aider、Goose 等。

截至调研时间：

- GitHub Star 约 3,907；
- Apache-2.0 许可证；
- 2026-07-22 当天仍有更新；
- 仓库同时包含 SDK、Workspace 后端、Web 前端、Launcher 和 Agent Connector。

### 2. Workspace 不是 Agent 进程

OpenAgents 的一个关键设计是：Workspace 本身只是数据库中的持久化协作记录，不为每个 Workspace 启动独立容器或服务器。

```text
Workspace
  = 成员 + 频道 + 消息 + 文件 + Agent 身份 + 状态
  != 一个一直运行的 Agent 进程
```

这样可以让大量 Workspace 长期存在，而 Agent 可以随时上线、离线和重新连接。

### 3. 事件驱动架构

OpenAgents 使用统一事件模型，通信、状态和任务都表示为事件，例如：

```text
agent.message
project.run.completed
channel.message.posted
```

事件具备：

- 来源和目标；
- 频道或 Agent 地址；
- 可见性级别；
- 权限过滤；
- 持久化和订阅；
- HTTP、WebSocket、gRPC 等传输方式。

这种结构比“把所有内容拼成聊天文本”更适合长期维护，因为消息、状态、文件、任务和系统事件可以保持不同的数据类型。

### 4. 本地 Agent 如何连接 Workspace

OpenAgents 使用长时间运行的 Adapter/Connector：

```text
浏览器发送消息
        ↓
Workspace 服务保存消息
        ↓
本地 Connector 轮询新任务
        ↓
Connector 启动或恢复 Codex CLI
        ↓
解析 Codex JSON 事件
        ↓
把状态、文件修改和最终回复发回 Workspace
```

其规划文档选择“自适应轮询 + REST”，而不是把长时间 WebSocket 作为唯一连接：

- 活跃对话约每 2 秒轮询；
- 空闲时退避至约 15 至 30 秒；
- 心跳用于判断 Agent 在线或离线；
- Workspace 历史不因 Agent 离线而丢失。

这是 OpenAgents 自身的产品取舍，不代表 WebSocket 不可用。它选择轮询是为了降低长连接、代理、移动网络切换和重连复杂度。

### 5. Codex Adapter 的实际做法

OpenAgents 的 Codex Adapter 没有把 Codex JSONL 当作群聊数据库，而是：

- 浏览器频道作为外部协作上下文；
- 每个频道保存一个 Codex Thread ID；
- 第一条消息使用 `codex exec`；
- 后续消息使用 `codex exec resume <threadId>`；
- 通过 `--json` 接收结构化事件；
- 把 `command_execution` 转换成运行状态；
- 把 `file_change` 转换成编辑状态；
- 把最终 Agent Message 发送回频道。

关键映射是：

```text
(workspaceId, agentId, channelId) -> codexThreadId
```

这说明一个 Codex Agent 可以同时参与多个频道，但不同频道不会意外共享会话上下文。

### 6. OpenAgents 值得借鉴的部分

- 协作层和执行层分离；
- 频道到 Agent Thread 的稳定映射；
- 人类、Agent 和系统事件使用统一事件总线；
- Agent 离线不影响 Workspace 和消息历史；
- Connector 运行在本地，代码和工具不必全部迁入云端；
- 不同 Agent Runtime 通过适配器接入，而不是要求所有 Agent 使用同一种框架。

### 7. OpenAgents 不应直接照搬的部分

当前 Codex Adapter 使用：

```text
--dangerously-bypass-approvals-and-sandbox
```

这会绕过审批和沙箱。对于多人可以从浏览器下达任务的产品，这是高风险默认值。

此外，其 Codex Adapter 主要通过每次消息启动 `codex exec` 子进程，而不是完整利用 `app-server` 的双向长连接、审批、Turn Steer 和细粒度状态能力。

因此，OpenAgents 更适合作为架构和数据模型参考。是否直接复用其 Workspace，需要另外评估：

- 前后端代码质量和维护成本；
- 身份与权限是否满足产品要求；
- 是否能替换其 Codex Adapter；
- 是否能保持当前 Codex 风格 UI 边界；
- 是否会把项目带入过重的 Python、FastAPI、PostgreSQL、Next.js 技术栈。

## 六、重点竞品二：Happy

### 1. 产品定位

Happy 是 Codex 和 Claude Code 的网页及移动端客户端。用户在电脑上运行 `happy codex`，通过包装器启动 Codex，再从网页或手机查看和控制会话。

截至调研时间：

- GitHub Star 约 22,791；
- MIT 许可证；
- 包含 App、CLI、Agent 和 Server 四个主要部分；
- 支持端到端加密；
- 支持手机、网页和电脑之间切换控制权。

### 2. 核心结构

```text
本地 Happy CLI/Agent
        ↓ 加密会话同步
Happy Server
        ↓
Web / iOS / Android App
```

服务器主要承担同步和连接，不应读取明文代码和对话。用户可以在远端查看 Agent 进展、发送消息、处理权限请求和接收通知。

### 3. 对本项目的价值

Happy 最适合回答当前 Demo 的下一步问题：如何把只读 Codex 会话变成可远程发送指令的双向会话。

可借鉴内容包括：

- 本地 Wrapper/Agent 与远端 UI 分离；
- 会话消息和状态增量同步；
- 控制权从电脑切换到网页或手机；
- 审批和错误通知；
- 端到端加密；
- 断线恢复和会话续接。

### 4. 与本项目愿景的差距

Happy 的核心仍是一个用户在多设备上管理自己的 Agent。它不负责：

- 项目群；
- 多真人成员；
- 项目经理 Agent；
- 多专业 Agent 的组织架构；
- 群消息到任务的协作关系。

因此，Happy 是连接层和安全同步层参考，不是完整产品载体。

## 七、重点竞品三：MetaGPT 与 ChatDev

### 1. MetaGPT

MetaGPT 将软件公司表示为多个角色和标准作业流程：

- 产品经理；
- 架构师；
- 项目经理；
- 工程师。

它强调：

```text
Code = SOP(Team)
```

即团队不是让多个 Agent 自由聊天，而是通过 SOP 产生需求、用户故事、架构、接口、代码和文档等交付物。

对本项目最有价值的启示是：AI 公司不能只靠角色名称成立。每个 Agent 必须拥有：

- 明确职责；
- 输入和输出契约；
- 可使用工具；
- 上下游关系；
- 审核标准；
- 失败和返工路径。

MetaGPT 不适合直接承担多人群聊和跨设备协作载体。

### 2. ChatDev

ChatDev 1.0 以 CEO、CTO、程序员等角色模拟虚拟软件公司；ChatDev 2.0 转向零代码多 Agent 编排平台。

其重要变化是从“多个 Agent 自由对话”转向：

- 中央编排器；
- 可配置 Agent；
- 可配置 Workflow；
- 实时日志；
- 中间产物；
- Human-in-the-loop 反馈。

它还公开研究了 Puppeteer 式中央调度：由中央编排器动态决定何时激活哪个 Agent，以降低无意义的多 Agent 对话和 Token 成本。

对本项目的直接启示是：项目经理 Agent 应当是任务与状态的编排者，不应只是群聊里另一个会说话的 Bot。

### 3. 共同局限

MetaGPT 和 ChatDev 更像 Agent Workflow 或研究框架，而不是供真人团队日常使用的长期项目群。它们可以帮助设计“AI 公司内部如何工作”，但不能替代协作产品的数据和权限层。

## 八、重点竞品四：OpenHands Agent Canvas

OpenHands Agent Canvas 将前端控制台与 Agent Server 分离：

```text
Agent Canvas Frontend
        ↓ REST/API
一个或多个 Agent Server
        ↓
本地、Docker、VM、云端 Agent
```

每个 Agent Server 可以运行多个 Agent。前端可以切换不同本地、远程和云端后端，并通过 Agent Client Protocol（ACP）连接 Codex、Claude Code、Gemini 等第三方 Agent。

对本项目的主要启示：

- 不把 UI 与某个 Agent Runtime 绑定；
- Agent 执行环境可以在本地、服务器或云端；
- 通过统一 Connector/Protocol 屏蔽不同 Agent 差异；
- 一个项目空间可以连接多个执行节点。

Agent Canvas 的重点是工程 Agent 控制台，不是项目群或 AI 公司组织模型。

## 九、Codex 官方能力核查

### 1. app-server 的定位

OpenAI 官方说明：`codex app-server` 用于驱动 Codex VS Code Extension 等富客户端界面。

它使用双向 JSON-RPC 2.0 风格协议，支持：

- `stdio`，默认使用 JSONL；
- WebSocket，当前标记为实验性和不支持生产依赖；
- Unix Socket；
- 关闭监听。

本机 `codex-cli 0.122.0` 还提供 WebSocket 认证参数，包括 capability token 和 signed bearer token。但官方 README 明确说明 WebSocket 仍是实验性能力，正式产品不应直接把它当作跨互联网协作协议。

### 2. Codex 核心模型

```text
Thread
  一个用户与 Codex Agent 的会话

Turn
  一次用户输入到 Agent 完成或中断

Item
  用户消息、Agent 消息、命令、文件修改、工具调用、推理摘要等
```

这个模型非常适合 Agent 执行记录，但没有完整表达多人社交关系。

### 3. 外部发送指令

已确认的关键接口：

| 接口 | 作用 |
|---|---|
| `thread/start` | 创建新 Codex 会话 |
| `thread/resume` | 恢复已有会话 |
| `thread/fork` | 从已有历史分叉新会话 |
| `thread/read` | 读取会话 |
| `thread/list` | 列出会话 |
| `turn/start` | 向指定 Thread 发送新用户输入并开始执行 |
| `turn/steer` | 在正在执行的 Turn 中继续补充输入 |
| `turn/interrupt` | 中断当前执行 |
| `thread/inject_items` | 向模型可见历史注入原始 Item，不启动 Turn |

因此，“浏览器继续当前 Codex 对话”已经有官方协议路径，不需要通过修改 JSONL 或模拟键盘输入实现。

### 4. 实时状态和内容事件

`app-server` 会持续返回：

- Turn Started / Completed；
- Item Started / Completed；
- Agent Message Delta；
- Command Execution；
- File Change；
- MCP Tool Call；
- Plan Update；
- Approval Request；
- Token Usage；
- Error。

Thread 状态定义包括：

```text
notLoaded
idle
active
  - waitingOnApproval
  - waitingOnUserInput
systemError
```

这些状态可以直接支撑“朋友正在让 Codex 工作”“正在等待确认”“已经完成”等用户可见信息，不必依赖 AI 再猜测当前状态。

### 5. Codex 多 Agent 能力

OpenAI 官方协议已经定义：

```text
spawnAgent
sendInput
resumeAgent
wait
closeAgent
```

子 Agent 状态包括：

```text
pendingInit
running
interrupted
completed
errored
shutdown
notFound
```

Thread Item 中还包含：

- `collabAgentToolCall`；
- 发起者 Thread ID；
- 接收者 Thread IDs；
- 发给子 Agent 的 Prompt；
- 请求使用的模型和推理强度；
- 各子 Agent 的最后状态；
- `subAgentActivity`；
- Agent Started / Interacted / Interrupted。

`thread/list` 支持按 `parentThreadId` 和 `ancestorThreadId` 查询子 Agent Thread。返回结果可以包含：

- `parentThreadId`；
- `agentNickname`；
- `agentRole`。

Codex TUI 源码中也存在多 Agent Transcript 和 Collab Agent 渲染测试。由此可以确认：Codex 的本地执行内核和终端界面已经具备多 Agent 表达能力。

### 6. 对“本地 Codex 显示多 Agent”的判断

**已验证：**

- Codex 协议能够表达子 Agent、父子会话、角色和状态；
- Codex TUI 有相关渲染代码；
- 当前 Codex App 会话环境具备子 Agent 调度能力。

**尚未完全验证：**

- Codex Desktop App 当前公开版本是否在所有界面中完整展示所有子 Agent 状态；
- 第三方通过 app-server 创建的子 Agent 是否会以理想形式自动出现在 Codex Desktop App UI；
- Codex 升级时这些实验性接口的兼容性承诺。

因此，可以把“本地 Codex 能看到多 Agent”列为可行方向，但在真实小实验前不能宣称 Desktop UI 已满足产品要求。

### 7. Codex 没有提供的多人能力

当前公开协议没有形成以下完整产品模型：

- 多个人类用户同时作为一个 Thread 的成员；
- 项目群成员和邀请；
- 真人之间的普通聊天；
- 群消息已读、引用、反应和提及权限；
- 跨设备团队在线状态；
- 组织、部门和成员角色；
- 多人对同一 Agent 的任务授权冲突处理。

这些能力必须位于 Codex 之外的协作层。

## 十、当前项目能力与差距

### 1. 当前已完成能力

当前后端已通过 `app-server` 调用：

```text
initialize
thread/list
thread/read
```

已经实现：

- 单项目真实 Thread 列表；
- 使用 `thread.name` 作为真实标题；
- Thread 内容读取；
- JSONL 降级路径；
- Markdown、代码、表格、图片、音频、视频和文件渲染；
- 分页、虚拟列表和会话缓存；
- SSE 页面更新；
- 后端和前端按功能拆分。

### 2. app-server Client 当前限制

当前 `windows/server/app-server-client.mjs` 只处理带 `id` 的请求响应：

```text
收到 JSON -> 查 pending request -> resolve/reject
```

没有把无 `id` 的 `app-server` Notification 分发给上层，因此即使调用 `turn/start`，当前客户端也无法完整处理实时 Agent Message、命令、文件变化和审批事件。

### 3. 当前数据模型仍是只读 Conversation

当前前端和后端围绕以下对象工作：

```text
Project -> Session -> Messages -> ContentBlocks
```

未来多人协作至少需要增加并保持独立：

```text
Workspace / ProjectRoom
Member
RoomMessage
AgentIdentity
AgentRun
Task
ActivityEvent
Artifact
Approval
```

这些对象不应硬塞进现有 `Message` 或 `ContentBlock` 类型。

### 4. 现有页面不需要推翻

未来增加协作层，不等于必须立即重做当前页面。当前页面已经解决真实 Codex 内容查看问题。技术上可以继续保持：

- UI 样式文件不动；
- Conversation 数据与渲染不动；
- 在后端补充双向 Turn 与 Notification；
- 在独立功能域增加 Workspace、Room 和 Agent Run；
- 后续由用户决定这些功能如何进入界面。

## 十一、可选技术路线

### 路线 A：继续把 Codex Thread 扩展成群聊

做法：给现有消息增加用户姓名、成员、Agent 类型和群聊字段，让一个 Codex Thread 看起来像多人群聊。

优点：

- 初期页面改动少；
- 可以快速做出多人消息外观。

问题：

- Codex Thread 本质仍是一名用户与一个 Agent 的模型上下文；
- 真人聊天会污染 Agent 上下文；
- 权限、已读、成员和状态难以正确表达；
- 私人对话和项目群难以隔离；
- 后续迁移成本高。

结论：不推荐作为正式架构，只适合视觉原型。

### 路线 B：自建轻量协作层，Codex app-server 作为 Connector

做法：在当前 Node 服务中增加最小 Workspace/Room/Event 数据层；每台电脑运行 Connector，通过 app-server 管理 Codex Thread。

优点：

- 与当前 Node + React 技术栈一致；
- 可以严格保持 UI、内容和功能边界；
- 充分利用 app-server 的 Turn、Notification、Approval 和多 Agent 能力；
- 第一阶段可以非常轻量。

问题：

- 身份、权限、同步和数据迁移需要自行设计；
- 长期需要承担协作基础设施维护。

结论：最适合当前项目的小步开发路线。

### 路线 C：直接基于 OpenAgents Workspace 二次开发

做法：采用 OpenAgents 的 Workspace、消息、成员、Connector 和数据库，再替换或增强 Codex Adapter。

优点：

- 多人协作和多 Agent 基础较完整；
- 已有本地 Agent Connector；
- Apache-2.0 许可证允许二次开发；
- 能较快验证完整协作形态。

问题：

- 技术栈明显变重；
- 当前项目已有 React/Vite/Node 结构可能需要整合或迁移；
- 必须移除危险的审批绕过默认值；
- 产品视觉和交互可能受其现有 Workspace 结构影响；
- 需要评估代码成熟度、升级成本和社区方向。

结论：适合先做隔离评估，不宜直接替换当前项目。

### 路线 D：采用 OpenHands Agent Server / ACP

做法：把不同 Agent Runtime 统一接入 Agent Server，再在上面建设协作层。

优点：

- 支持多种 Agent；
- 本地、容器、VM 和云端执行边界清晰；
- 长期跨 Agent Runtime 能力较强。

问题：

- 当前项目只需要 Codex，过早引入通用协议可能增加复杂度；
- 仍然需要自己建设多人项目群和组织层。

结论：适合作为长期兼容方向，不是当前第一步。

## 十二、推荐架构

### 1. 总体原则

推荐采用：

> 轻量自建协作层 + Codex app-server Connector，同时深入参考 OpenAgents 的事件和频道模型。

不建议当前直接把项目整体迁移到 OpenAgents，也不建议继续把 Codex Thread 当作群聊数据库。

### 2. 数据所有权

| 数据 | 应由谁拥有 |
|---|---|
| 真人账号、成员、邀请 | 协作层 |
| 项目群消息 | 协作层 |
| 真人之间的聊天 | 协作层 |
| Agent 身份与职责 | 组织层 |
| 任务、审核、打回 | 组织层 |
| Agent 运行状态 | Connector 产生，协作层保存 |
| Codex 原始 Thread/Turn/Item | Codex |
| 提炼后的项目状态 | 总结或项目经理 Agent |
| 完整工作日志索引 | 协作层索引，原始证据保留在执行节点 |
| 文件和产物 | 明确的 Artifact 层，不直接暴露任意本地路径 |

### 3. 最小实体关系

```text
ProjectRoom
  ├── Members
  ├── RoomMessages
  ├── AgentIdentities
  ├── Tasks
  │     └── AgentRuns
  │            ├── ActivityEvents
  │            ├── CodexThreadRef
  │            └── Artifacts
  └── Approvals
```

### 4. Connector 映射

推荐不要简单使用：

```text
Room -> 一个 Codex Thread
```

更合理的是：

```text
(ProjectRoom, AgentIdentity, Task) -> Codex Thread
```

原因：

- 项目经理 Agent 和前端 Agent 需要不同上下文；
- 同一 Agent 的不同任务需要可追溯；
- 群内闲聊不应全部进入每个 Agent 的模型上下文；
- 任务打回时应恢复原执行 Thread；
- 私人对话分享总结时不应复制全部原始上下文。

### 5. 状态事件

状态栏应优先使用真实协议事件，而不是让另一个模型猜测：

```text
turn/started            -> 正在处理任务
commandExecution        -> 正在运行命令
fileChange              -> 正在修改文件
waitingOnApproval       -> 等待批准
waitingOnUserInput      -> 等待补充信息
collabAgentToolCall     -> 正在派发或联系子 Agent
turn/completed          -> 本轮完成
systemError             -> 执行异常
```

项目经理 Agent 可以在这些真实状态之上生成更自然的项目语言，但底层状态必须保留来源。

### 6. 日志分层

```text
第一层：群聊中的项目经理汇报
  只展示结论、风险、待确认和交付结果

第二层：状态栏和任务活动
  展示真实执行阶段和关键事件

第三层：完整工作日志
  保存用户输入、Agent 输出、命令、文件变更、工具调用、审批和错误
```

对于“思考过程”，应保存 Agent 主动输出的推理摘要、方案选择和证据，不依赖不可访问或不可验证的隐藏内部推理。

## 十三、建议的阶段路线

### 阶段 1：双向 Codex 技术闭环

用户可观察结果：

- 浏览器继续现有真实 Codex 对话；
- Codex 开始执行；
- 页面实时显示消息、命令、文件修改和状态；
- 可以停止或补充指令；
- 审批仍由明确授权的人处理。

需要完成：

- app-server Notification 分发；
- `thread/resume`；
- `turn/start`；
- `turn/steer`；
- `turn/interrupt`；
- 状态与审批事件映射；
- 随机认证令牌和默认本机监听。

这一阶段不需要先做多人群聊，但其 Connector 应避免绑定单一页面，以便后续复用。

### 阶段 2：多人观看与成员状态

用户可观察结果：

- 授权成员看到项目内谁正在使用哪个 Agent；
- 看到对方 Agent 是工作、等待还是完成；
- 看到允许共享的对话或提炼结果；
- 私人对话保持私密。

需要增加：

- ProjectRoom；
- Member；
- Presence/Lease；
- 共享范围；
- 最小认证和邀请；
- 状态事件同步。

### 阶段 3：项目群与项目经理 Agent

用户可观察结果：

- 真人成员在项目群聊天；
- 项目经理 Agent 参与群聊；
- 群成员可以点名专业 Agent；
- 模糊任务先澄清，清晰任务可以进入执行；
- 任务状态和结果回到项目群。

需要增加：

- RoomMessage；
- Mention；
- AgentIdentity；
- Task；
- AgentRun；
- PM Agent 的路由与审核规则。

### 阶段 4：AI 公司组织层

用户可观察结果：

- 开箱即用的项目经理、产品、设计、开发、测试等 AI 员工；
- 每个 Agent 有职责、工具、权限和交付标准；
- 项目经理可以审核、打回和重新派发；
- 工作日志、产物和决策长期沉淀。

这一阶段再评估：

- 部门专业 Agent；
- Agent 训练或知识配置；
- Agent 代表部门参加会议；
- 多团队 PK；
- 多项目和企业权限。

## 十四、主要风险

### P0：远程命令执行安全

一旦浏览器可以向 Codex 发送指令，系统就不再是只读 Demo，而是远程代码执行入口。必须保证：

- 默认只监听 `127.0.0.1`；
- 公网访问使用可靠认证；
- Token 不使用固定 `demo123`；
- 不默认绕过 Codex 审批和沙箱；
- 用户、项目和 Agent 权限可撤销；
- 审批请求只发送给有权成员；
- 操作留有审计记录。

### P0：群聊消息污染 Agent 上下文

不能把项目群所有消息自动塞进所有 Codex Thread。必须由任务路由或项目经理 Agent 选择必要上下文。

### P0：私人内容泄露

私人 Codex 会话、文件绝对路径、密钥、工具参数和完整日志不能默认进入项目群。共享应有明确对象和范围。

### P1：实验性协议变化

Codex `app-server` 和部分多 Agent 字段标记为实验性。Connector 必须：

- 记录 Codex 版本；
- 使用版本匹配 Schema；
- 对未知事件保持向前兼容；
- 提供 JSONL 或 CLI 降级；
- 不让协议变化破坏协作层历史。

### P1：过早引入重型平台

直接迁移 OpenAgents、OpenHands 或完整 Agent Framework 可能带来数据库、Python、容器、认证和部署复杂度。当前应先验证最小双向闭环。

### P1：AI 项目经理的错误权力

项目经理 Agent 可以澄清、路由、总结和建议，但关键权限、冲突决定、删除、发布、付费和对外发送必须由真人确认。

### P2：状态过度总结

状态栏如果完全依赖 AI 总结，可能延迟、遗漏或编造状态。真实执行事件应作为基础，AI 只负责翻译成人类可读信息。

---

## 十五、待验证事项

在进入正式开发前，建议用小型技术实验确认：

1. 当前本机 `app-server` 能否稳定完成 `thread/resume -> turn/start -> notification -> turn/completed`。
2. 页面断线重连后，是否能重新订阅正在运行的 Thread。
3. 审批请求能否安全地映射到浏览器，并由正确成员处理。
4. `turn/steer` 在当前 Codex 版本中的实际行为。
5. 子 Agent 的 `collabAgentToolCall`、父子 Thread 和状态是否能完整读取。
6. 第三方 app-server 客户端创建的子 Agent 在 Codex Desktop App 中如何显示。
7. OpenAgents Workspace 的多人邀请、成员权限和频道数据是否达到可复用质量。
8. OpenAgents Codex Adapter 能否替换为 app-server Connector，而不破坏 Workspace 体验。
9. 当前 Node + React 项目实现最小 Room/Event 层的工作量，与复用 OpenAgents 相比如何。

## 十六、最终判断

### 产品层

长期方向“开箱即用的 AI 公司”与现有技术生态并不冲突，但它不能只表现为多个 Agent 在群里说话。真正的产品结构应包含：

- 真人协作空间；
- 项目经理 Agent；
- 有职责和权限的专业 Agent；
- 真实执行状态；
- 审核、打回和审批；
- 可追溯日志与产物。

### 技术层

推荐方向是：

> 不修改 Codex 原始数据结构，不把 JSONL 变成群聊数据库；建立轻量独立协作层，通过 app-server Connector 双向连接 Codex。

### 竞品利用方式

- 深入拆解 OpenAgents 的 Workspace、频道、事件与 Connector；
- 借鉴 Happy 的加密同步、远程控制和设备接管；
- 借鉴 MetaGPT 的角色与 SOP；
- 借鉴 ChatDev 的中央编排、日志和人工介入；
- 把 OpenHands/ACP 保留为未来支持多种 Agent Runtime 的方向。

### 当前最近的一步

从技术依赖关系看，最近的核心验证应是：

```text
浏览器向现有 Codex Thread 发送真实指令
        ↓
Codex 执行
        ↓
浏览器接收真实状态、审批、文件变化和回复
```

这一步完成后，Connector 才具备被多人项目群调用的基础。群聊数据层可以并行设计，但不应在双向执行链路尚未证明时大规模建设完整组织系统。
